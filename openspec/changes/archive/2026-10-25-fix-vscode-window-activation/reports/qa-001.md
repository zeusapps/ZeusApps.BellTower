## Findings

### QA-001: Native show-state, denial and mapping behavior has no executed native test (task 4.1)

- Severity: warning
- Related task / requirement: 2.2, 4.1; spec "Minimized or fullscreen owner", "Activation denied"
- Location: `tests/BellTower.Tests/Hosts/WindowActivationTests.cs`, `VsCodeWindowNavigationTests.cs` (recording fakes); `src/BellTower/Hosts/NativeWindowActivationApi.cs`
- Expected / actual: Task 4.1 asks for native disposable-window process tests for mappings, focus denial and show-state preservation. Actual: all activation, minimized, denial and show-state assertions use a fake desktop; `NativeWindowActivationApi` and `NativeWindowInspector` `Inspect` are never exercised against a real window. The developer's disposable two-window fixture is evidence in a markdown claim only and I did not re-execute it.
- Reproduction: `grep -rn NativeWindowActivationApi tests/` finds no real-window test.
- Evidence: source inspection; test names above.
- Recommended correction: either add a disposable-window native test (own hidden or minimized test window, never the user's) or record 4.1 as partially done and carry the gap into 4.2 explicitly.
- Relationship: none

### QA-002: Failure-path timer preservation (task 2.4) is not directly tested

- Severity: warning
- Related task / requirement: 2.4; spec "Activation denied"
- Location: `src/BellTower/Tray/TrayApplication.cs:300-332` (`Navigate`); `tests/BellTower.Tests/Tray/ViewedTimerTests.cs:75`
- Expected / actual: The developer claims the existing test covers late receipts. It does cover the `StateStore.MarkViewed` episode guard, so a late success cannot hide a newer episode's timer. It does not cover that a failed navigation (the new unverified, denied or reveal-failure results) leaves the viewed state unchanged, nor the `result.Success && hideTimer` branch. That branch is a private `async void` method with no test; I confirmed it only by reading the code (correct: `MarkViewed` is skipped unless `Success`).
- Reproduction: read `Navigate`; search tests for a failed-navigation viewed assertion, none found.
- Evidence: source inspection only.
- Recommended correction: add a test that a failed `FocusResult` from the navigator leaves `ViewedEpisode` unset (extract the decision or drive it through a testable seam).
- Relationship: none

### QA-003: A focused window that is reloaded stays unverified until it loses and regains focus

- Severity: suggestion
- Related task / requirement: 2.1, 3.3; spec "Window behind another app"
- Location: `vscode/service.js:41-56` (windowDirty starts false), `vscode/extension.js:78-80`
- Expected / actual: After `Developer: Reload Window` the reloaded window is typically focused, but evidence is sampled only on an observed focus-gain event, so chips read `terminal only` and clicks fail until the user alt-tabs away and back. This is a deliberate fail-safe and documented ("focus each VS Code window once"), but it makes the first click after every upgrade/reload fail.
- Reproduction: source inspection; not run live (needs real focus changes).
- Evidence: `service.js` constructor comment; `installation.md` diff.
- Recommended correction: consider one guarded initial sample when `isFocused()` is true at start (the existing two-agreeing-sample plus `expectedOwnerPid` checks already protect against a wrong window), or keep as is and state the cost in the live 4.2 checks.
- Relationship: none

### QA-004: `doctor` does not report per-window verification state (limitation 6, task 5.2)

- Severity: warning
- Related task / requirement: 5.2
- Location: `src/BellTower/Diagnostics/DiagnosticsReporter.cs:38` (`VsCode = "requires bundled focus bridge"`)
- Expected / actual: Task 5.2 requires diagnostics to be audited for equal availability and honest reporting. The shared policy applies equally to Claude Code and Codex, so this is not a provider parity gap, but the only explanation for an unverified window after this change is the chip tooltip and failure message; `doctor` shows no per-window state, so the capability matrix is not honest about verified/partial/unverified windows. Developer lists it as a limitation, so 5.2 is not complete.
- Reproduction: read `DiagnosticsReporter.cs`.
- Evidence: source inspection.
- Recommended correction: report registered windows as verified, partial (older bridge) or unverified (never focused/conflict) in `doctor`, or record the deferral as an explicit decision.
- Relationship: none
