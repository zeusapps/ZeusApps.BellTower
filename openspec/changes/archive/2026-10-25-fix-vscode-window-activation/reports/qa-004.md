## How the product ships the bridge

`VsCodeBridgeSetup.Plan` (called from `setup --desktop`) finds `bell-tower-focus-*.vsix` next to the executable and plans one action: `Code.exe cli.js --install-extension <vsix> --force`, run with `ELECTRON_RUN_AS_NODE=1`. With `--home` it appends `--user-data-dir` and `--extensions-dir` pointing at the fixture home. The VSIX is built by `scripts/package.ps1` as a zip of `extension.js`, `service.js`, `focus.js` and a generated `package.json`. Ownership is recorded in `integration.json` (`bridgeInstalled`).

## Assessment and limitations

- All task 3.3 acceptance parts were executed in isolation: matching VSIX content, settings preservation by the bridge install, ownership rules, the deferred-reload notice, and no process start, stop or restart.
- Limitations: the VSIX was assembled with the packaging recipe, not by the full NativeAOT `package.ps1`. The `bell-tower.exe` used is the Release build copied to a disposable folder (a development CLI, so ingress provisioning is skipped by design). The user's VS Code install was used only as read-only installer binaries (`Code.exe` and `cli.js`), with disposable `--user-data-dir` and `--extensions-dir`. The user's extensions, settings, windows and Bell Tower were not touched. Evidence files: `evidence/qa-004-isolated-install.txt` and `evidence/qa-004-direct-cli.txt`.
