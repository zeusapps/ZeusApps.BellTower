# Native adoption binding investigation 001

Date: 2026-10-29. Scope: tasks 1.1 and 1.2, as a bounded investigation before implementation. No provider settings, user sessions, or running Codex daemon were accessed or changed.

## Current installed-version checks

The installed Codex CLI reports 0.165.0. Its local `codex --help` identifies `--no-daemon` as running without the shared background server; `app-server daemon` is available as a separate experimental command. PowerShell resolves a `codex` PowerShell shim, a `codex` command file, and the native executable. Claude Code reports 2.1.312. These version and help checks do not establish native hook ancestry or host attachment.

To inspect the exact installed app-server protocol without starting or connecting to a provider process, I generated its experimental JSON Schema bundle into ignored disposable data using an isolated `CODEX_HOME`:

```powershell
$probeRoot = Join-Path (Get-Location).Path 'artifacts/native-adoption-001'
$env:CODEX_HOME = Join-Path $probeRoot 'codex-home-schema'
codex app-server generate-json-schema --experimental --out (Join-Path $probeRoot 'schema-0.165.0')
```

The bundle was generated by Codex 0.165.0. Its `Thread` definition includes `id`, `sessionId`, `parentThreadId`, `originator`, `source`, `threadSource`, `cwd`, `status`, and `preview`. `sessionId` is documented as shared by threads in the same session tree. Neither the thread nor `ThreadReadResponse` carries the PID or connection identity of the interactive client displaying that thread. `source` and `originator` describe thread origin and are not a live terminal identifier. `thread/read` returns a thread and read-state receipt.

I also checked the full generated v2 request/notification inventory, `codex app-server proxy --help`, and the daemon CLI. The inventory includes `thread/list`, `thread/loaded/list`, `thread/read`, `thread/unsubscribe`, and `server/diagnostics`, but no app-server API that enumerates connected TUI connections or returns their PIDs/subscriptions. `server/diagnostics` returns process-local gauges and one process record, not a client-to-thread table. `thread/unsubscribe` takes a thread ID and has no subscriber inventory. The similarly named `remoteControl/client/list` is scoped by `environmentId`; its `RemoteControlClient` records have client/device metadata but no thread ID or process ID, so it cannot join a TUI to a conversation. `initialize.clientInfo` identifies the client making that handshake; it does not report already-connected clients or their operating-system PIDs. The CLI's `app-server proxy --help` exposes an explicit socket path, not a client lookup service.

I ran `codex app-server daemon version` with a short isolated `CODEX_HOME`; it failed to connect to that private home’s absent control socket. This established no daemon was available in that disposable home. I did not issue daemon lifecycle commands and did not inspect the user's default Codex home or connect to a user daemon.

Relevant primary protocol sources: [thread protocol](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/thread.rs) and [app-server daemon](https://github.com/openai/codex/blob/main/codex-rs/app-server-daemon/README.md). The upstream daemon README says a shared daemon uses the environment inherited at daemon start, not each connecting client's environment. This upstream main-branch document is supporting context; the exact installed-version schema above is the version-specific evidence.

## Host correlation checked

The existing VS Code bridge obtains `Terminal.processId` and publishes those terminal PIDs in its registration (`vscode/extension.js:71`, `vscode/service.js:202`). Registrations contain no provider conversation, app-server thread, or client connection IDs. `VsCodeNavigator` only matches a live attachment shell PID against that fresh list (`src/BellTower/Hosts/VsCodeNavigator.cs:172-179`). The existing capture path finds provider process ancestry and shell evidence, but Codex ingress currently classifies the attachment as dedicated only when the explicit dedicated flag is present (`src/BellTower/Hosts/AttachmentCapture.cs:8-18`, `src/BellTower.Ingress/Program.cs:33`).

Consequently the current thread metadata and host registration have no common key for a shared backend thread. Matching by working directory, title, a static source label, or daemon process/environment could not distinguish two same-directory native TUI clients. Reconnect also supplies no client identity in the thread schema; a remembered registration would not establish that the same client still owns the conversation. The hook session ID needs its own explicit mapping to the exact protocol thread ID; a shared session-tree ID alone cannot select a TUI when several threads or clients are present.

This is an evidence gap for exact shared-Codex client-to-terminal binding, not proof that no host-assisted binder is possible. The 0.164.0 retained probes demonstrated concurrent exact-thread reads and native names, but explicitly left their correspondence to visible terminals unproven (`native-probes/codex-parallel-proof.json`).
