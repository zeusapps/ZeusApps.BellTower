## Task 4.10: every click result is visible (done)

- `NavigationNotice` now decides one thing: every result below an exact tab or terminal is shown in Bell Tower's own notice. The balloon, `SHQueryUserNotificationState`, `UserNotificationState` and the `Decide` branching are removed (ANALYSIS-4600). The notice anchors to the chip strip, or to the Sessions window when the click came from it.
- `NoticeForm` is topmost from creation through the extended style (`WS_EX_TOPMOST | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`) and no longer sets the `TopMost` property, which re-positions without `SWP_NOACTIVATE` and can activate the form (ANALYSIS-4601).
- A click on a session no longer tracked logs `navigation-session-missing` and explains itself; a navigator that throws is caught for the known exception types, logs `navigation-failed` and explains itself (ANALYSIS-4602). `NavigationNotice.RunAsync` is the one place, so both providers and both hosts share it.
- `FocusResult.Normalized()` (QA-5304): a result read from the Windows Terminal helper or a VS Code receipt gets a non-null precision and message. `NavigationNotice.LogCode` writes only a precision from the known set (anything else is `other`), never a message or path.
- ANALYSIS-4603: the Codex navigation cell now reads "the same stated reason and delivery as Claude Code" in the matrix and in `docs/compatibility.md`.
- Tests (QA-5300), `ClickReasonTests`: the notice shows for every non-exact result and not for an exact one; the log code theory including a hostile precision and a null field; a throwing navigator for both providers and both hosts; a stale key; the notice's topmost, tool-window and no-activate style bits, `NeverActivates`, `TopMost` false, lifetime and dismissal.

## Task 4.6: the tray starts as a child of the desktop shell (done; elevation not verified)

- `DesktopShell` (new, `BellTower.Protocol`, plain P/Invoke) finds the process owning the shell window and fails closed with a bounded reason unless its image is the system `explorer.exe`, it has this user's SID and this sign-in session, and it is the same process after it was opened (`shell-none`, `shell-changed`, `shell-image-unverified`, `shell-other-user`, `shell-other-session`). The verification is a pure function over the facts that were read.
- `TrayProcess.Start` now calls `CreateProcessW` with `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` set to that shell, `bInheritHandles = FALSE`, no window, a new process group, the launcher folder as working directory and an environment block built by `CreateEnvironmentBlock` for the shell's token. The child is created suspended, its token's elevation is read, and it is resumed only when it is not elevated while the shell's token is not (`child-elevated` terminates only that owned suspended child). The DEV-056 `IsProcessInJob` check, the linked-token path and `CreateProcessWithTokenW` are removed. The tray command line carries a hidden `--hook-start` marker.
- The tray's own check: `TrayJobGuard` reads the immediate job (`QueryInformationJobObject`). A hook-started tray whose immediate job has KILL_ON_JOB_CLOSE records `hook-start/tray-job.txt` and the log code `tray-start-refused-kill-on-close-job` and exits before taking the tray mutex. Deliberate narrowing of the spec text ("on start"): only a tray started with `--hook-start` checks, so a tray started by hand from a terminal that wraps its children in a kill-on-close job (a libuv host) is never refused. `TrayInvocationCommand` accepts the marker, so a hook-started tray is still classified as that data directory's tray.
- Fallback: `HookStartTask` (Protocol, run by the hook) and `HookStartTaskSetup` (setup) implement the on-demand per-user task `\ZeusApps.BellTower\HookStart-<hash of the data directory>`: the limited interactive principal, no trigger, no execution limit, no battery conditions, ignore-new. Setup (`IngressProvision.Apply`) registers it next to the launcher record, `setup --remove` of the last hook deletes it, preview notes name it, and the hook runs it with `schtasks /run` (bounded wait, no inherited handle) only when the shell start failed and a task is recorded; `HookTrayStart.TryStart` records the route (`started-via-shell` or `started-via-task`) or both failure reasons.
- Doctor `hookStart` reports the latest route, whether a shell can be verified now, the fallback task (`registered`, `not registered`, `recorded but missing`) and any tray job refusal.
- Tests (`HookTrayStartTests`, 61 pass, including the previously failing 11): shell verification table and fail-closed start; hooks of both providers start exactly one tray as the shell's child with the provider environment absent and no pipe standard handle; a hook running inside a provider's kill-on-close job, immediate or nested, starts a tray that survives the job closing (the T-12 regression; for both providers); the fallback runs only after a failed shell start and only with a recorded task, and both failures are named; user stop, burst control and the update gate run before any route; the job guard table; the marker classification; the task definition has no trigger; a real per-user task under the disposable folder `BellTowerTest-DEV059` is registered, run through the product code (the fake launcher starts as the task action, one instance only) and deleted, and the test asserts it is gone. `ProcessStopAuthorityTests` allow-list updated for the two kill sites.
- Not verified here: an elevated hook (token inheritance from the shell, the `child-elevated` guard path), VS Code terminals, other Windows builds, Native AOT publish of the ingress (no native linker on this machine; the new code is plain P/Invoke as before), and hook latency was not re-measured.

## Task 4.7: the opt-in provider title step (done)

Probe result (isolated homes, ConPTY, loopback stand-in endpoints, 2026-11-22):

| Provider and setting | Title writes seen by the terminal |
| --- | --- |
| Codex 0.171.0 `--no-daemon`, no setting | `OSC 0` at start, a spinner frame about 20 times a second during the turn, a final `<thread> \| <project>` |
| Codex `[tui] terminal_title = []` | none (only the shell's own title written before Codex started); `OSC 7501` state messages continue |
| Codex `terminal_title = ["spinner"]` | blank and spinner-only titles still written, so `[]` is the value that stops it |
| Claude Code 2.1.330, no setting | five title writes ("claude" and conversation titles) |
| Claude Code, settings `env` block `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` | none beyond the shell's own |

Both mechanisms work, so the step is offered for both providers.

- `setup --provider-titles [--clients claude|codex|both] [--remove] [--apply]` plans on its own (never together with hooks, profiles or the bridge). The preview names the exact key and carries the consent text (whole provider profile). One key per provider is edited: Claude settings `env` through `JsonSettingsFile`, Codex `config.toml` `[tui] terminal_title = []` through the same Tomlyn syntax-tree edit the footer uses. Ownership is recorded in the integration manifest (`ProviderTitles`: provider, previous value, whether setup created the container); apply backs up the changed file through `SetupPlan`; repeating changes nothing; removal restores the previous value or deletes only what setup added (an `env` block or `[tui]` table setup created is removed), keeps a value the user edited since, and leaves a setting the user made by hand unowned. A provider not in `ProviderTitleSettings.Verified` is not offered.
- Bell Tower writes its title only when the step is owned for that provider: `NativePresentation.Effective(attachment, enabled, providerTitleDisabled)` grants the palette background with the setting and the managed title only with the step. The resolver, `TerminalTitleService` and the writer accept a color-only request (empty title: no title read, written or restored; restore resets only the colors), and Windows Terminal navigation reports `window only` with the new reason `NavigationReasons.WindowOnlyProviderTitle` ("run setup --provider-titles"). Doctor `nativeSessions` reports per provider whether the title is Bell Tower's or provider-owned and the navigation now; the capability matrix and docs state it for both providers.
- Tests (`ProviderTitleStepTests`, 17): preview, apply, repeat and remove for each provider with disposable settings, backups, unrelated settings and the other provider untouched, a created and removed container, restore of a previous value, a user edit kept, a user-made setting left unowned, invalid files fail before any write; policy and writer behavior with and without the step for both providers, a refused titled request without the step, a mixed Claude-with-step and Codex-without case, and the Windows Terminal reason. Existing presentation suites set the step in their fixtures.

## Task 4.9: the shared wait rule with thin adapters (done)

- Shared rule, unchanged in the reducer: a provisional permission wait is confirmed by the existing runtime-approval observation (same stored transition, scope and revision checks, restore silently) and cleared by the existing interrupt observation. Timing never confirms.
- Codex adapter (`CodexApprovalEvidence` plus `CodexPermissionPump`): with no owning runtime and no shared backend the pump reads the end of the hook-named transcript (bounded, in the tray) and takes the turn's `approvals_reviewer`: `user` confirms (the same `Record` path a runtime status uses), another reviewer suppresses (no alert, no chip), no record leaves the wait provisional with the silent 15-second chip. A record of another turn is ignored.
- Claude adapter (`ClaudeDeclineEvidence` plus `ClaudeDeclineWatcher`): while a Claude session has an outstanding wait the watcher reads the transcript end once a second and publishes the interrupt observation at the time the rejection was recorded (so a prompt typed right after is not cleared), once per wait.
- `TranscriptTail` is the one bounded reader: absolute regular files only, last 1 MiB, partial first and unfinished last lines dropped, lines over 256 KiB skipped, no result carries text.
- Doctor `confirmationCoverage.codex` counts sessions with transcript evidence and reports the transcript signal; the matrix row "Human-wait confirmation without an owning runtime" is now supported for both providers with its limits and "live trial 6.1 open"; `docs/compatibility.md` and `docs/installation.md` say the same. The two open-evidence notes were reduced to the version and record-format risk.
- Tests (`WaitEvidenceTests`, 10): fixture parsing through the production adapter, reviewer table, decline table, reader bounds, a held approval confirmed and an automatic review silent in one run, no evidence stays provisional however old, another turn's transcript never confirms, a declined Claude prompt clears through the interrupt rule once, a wait newer than the record is left alone, doctor counts, and a mixed Codex-held, Codex-automatic and Claude-declined case.
