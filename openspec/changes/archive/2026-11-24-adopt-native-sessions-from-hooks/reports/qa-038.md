## Failure investigation: CodexSharedAccessTests.AFailureThatStartedBeforeASuccessDoesNotUndoTheSuccess

- Baseline 0b11026 (clean temp worktree, Release build, test run alone): failed 5 of 5. Current tree: failed 5 of 5 alone. In the current full-suite run it passed. So it is a pre-existing defect, not caused by this diff.
- Cause: a test race. `tests/BellTower.Tests/Providers/CodexSharedAccessTests.cs` lines 330 to 337 wait for `server.Accepted >= 1`, then flip `BehaviorMode` to Normal. `CodexStandInServer` increments `Accepted` at the TCP accept (line 83), before the WebSocket upgrade and before the slow client's `initialize` is read (lines 100 to 138). The Silent check is evaluated per message when it is read (line 138), so when the flip lands first the "slow" connection gets an answer too, succeeds, and `ThrowsAsync<CodexTransportException>` sees no exception (failing in about 70 ms instead of a 2 s timeout).
- Confirmed by experiment in the temp baseline worktree only: waiting until `server.Methods.Contains("initialize")` instead of `Accepted` made it pass 5 of 5 (about 1 s each). The worktree was removed and pruned; the repository was not edited.
- Whether it passes in the full suite depends on load timing; it is not a product defect (the product code under test, `CodexSharedAccess`, behaves per the design in the cases that run correctly).

## Findings

### QA-3800: Shared-access failure-ordering test races the stand-in and fails when run alone

- Severity: warning
- Related task / requirement: task 3.2 test reliability (committed in b669cf8); not caused by task 3.4
- Location: tests/BellTower.Tests/Providers/CodexSharedAccessTests.cs lines 330 to 337; tests/BellTower.Tests/Providers/CodexStandInServer.cs line 83 and line 138
- Expected / actual: the test should deterministically keep the first connection silent until the second open has succeeded. Actual: the wait condition (`Accepted`) is satisfied before the first connection's `initialize` is read, so the Silent-to-Normal flip can answer the slow connection and no exception is thrown. Fails 5 of 5 alone at both 0b11026 and the current tree; passes in some full-suite runs, so a green suite can hide an unsound test.
- Reproduction: `dotnet test -c Release --no-build --no-restore --filter "FullyQualifiedName~AFailureThatStartedBeforeASuccessDoesNotUndoTheSuccess"`
- Evidence: this report (5/5 failures at both revisions; 5/5 passes with the wait on the recorded `initialize` method)
- Recommended correction: wait until the stand-in has recorded the `initialize` request of the first connection (for example `server.RecordedMethods()` contains it) before switching to Normal; then the Silent behavior is bound to that connection deterministically. Needs a developer change outside this task's paths (Providers tests).
- Relationship: new
