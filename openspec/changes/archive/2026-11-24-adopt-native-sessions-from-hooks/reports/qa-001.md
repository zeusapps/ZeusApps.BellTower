## Findings

### QA-001: Bridge-only setup does not configure the VS Code executable or data directory

- Severity: warning
- Related task / requirement: task 5.1; standalone-setup native-command integration without dedicated profiles.
- Location: `src/BellTower/Setup/IntegrationSetup.cs:116`; the existing desktop path writes the corresponding settings in `src/BellTower/Setup/TerminalProfilesEditor.cs:72-73`, while `vscode/extension.js:15-17` reads those settings and otherwise uses environment/default fallbacks.
- Expected / actual: When `setup --host-bridge` runs with a custom `--data-dir`, or the installed executable is not discoverable as `bell-tower`, the bridge should use that selected data directory and executable. The bridge-only path schedules extension installation but does not write `bellTower.dataDirectory` or `bellTower.executablePath`; without a matching inherited environment, the extension looks in another data root or cannot launch Bell Tower. Desktop setup writes these settings, but combining it with `--host-bridge` is rejected.
- Reproduction: With disposable home and data paths, preview `setup --host-bridge --home <home> --data-dir <data>`. The plan configures hooks and the extension action but has no VS Code settings change carrying `<data>` or the selected executable. The extension source then resolves its root/executable from settings, environment or defaults.
- Evidence: CLI/source inspection; fixture tests passed but do not inspect VS Code settings for the bridge-only case.
- Recommended correction: Manage the extension's executable and data-directory settings for bridge-only setup, with the existing ownership and user-edit preservation rules, while leaving terminal profiles and shell imports untouched. Add isolated preview/apply/repeat/remove tests for custom paths.
- Relationship: none.

### QA-002: Removing one provider clears shared native bridge ownership for both

- Severity: warning
- Related task / requirement: task 5.1; provider-specific native setup and removal for both providers.
- Location: `src/BellTower/Setup/IntegrationSetup.cs:108,112,116` and `src/BellTower/Setup/IntegrationOwnership.cs:10`.
- Expected / actual: If native hook setup is installed for Claude and Codex, removing only Claude should preserve the shared VS Code bridge while Codex remains configured. `NativeHostBridge` is a single boolean and each `hostBridge && remove` call sets it false regardless of the selected provider; with no desktop owner, the following plan requests bridge removal even though the other provider's hooks remain.
- Reproduction: In an isolated home/data directory, apply native hook setup for `claude`, then for `codex`; preview `setup --clients claude --host-bridge --remove`. The ownership record clears `nativeHostBridge` and asks `VsCodeBridgeSetup` to remove the bridge. The remaining Codex hooks can no longer use that shared bridge.
- Evidence: Setup ownership and action-planning source inspection. Current tests remove one provider while desktop also owns the bridge, so they do not exercise native-only cross-provider ownership.
- Recommended correction: Track native bridge ownership independently of the selected provider's hooks (or persist the provider owners), and retain the shared bridge until no native provider or desktop profile owns it. Add the native-only Claude/Codex partial-removal sequence to the fixtures.
- Relationship: none.
