## Findings

### QA-2500: A nested `codex app-server` inside an owned backend can take the managed attachment

- Severity: warning
- Related task / requirement: 2.5; QA-2400 fix; "existing launch functions and owned runtimes keep working"
- Location: `src/BellTower/Core/NativeAdoption.cs` `ManagerBehindAgent` (any ancestor within three hops) and `Reconcile`
- Expected / actual: only the real backend of the managed `Start-Codex` runtime binds. With the new rule any provisional `unknown` Codex capture that has the manager within three hops binds if it is the first hook for that attachment. A model-started `codex app-server` (manager -> backend -> nested; or nested under a tool shell, still within three hops) is classified `unknown` (its parent is a backend, not a client), so it binds.
- Reproduction (scratch, valid record, cmd.exe stand-ins): nested hook before the real backend's hook produced `SESSION nested -> managed-id (ended after the nested process exits)` and `SESSION real-backend -> codex-session-<hash>` (shared). `ATT managed-id process = nested pid, host shell = record shell`. Order reversed: the real backend keeps the managed attachment and the nested session is shared (the `profile` guard holds). Same result for the event and ingress entry points.
- What the user sees (nested first): the user's actual Start-Codex conversation ends in the shared shape (no host, no native name write, no pump contact), while the managed attachment, its host shell and its name write belong to a nested process; when that process exits the managed attachment is ended with a conversation that was not the user's. Cause is not a regression: before 2.2 (`2f1de7f`) any `BELLTOWER_DEDICATED=1` hook bound, so this ordering hazard was worse; the developer already lists it as a residual.
- Evidence: scratch run in a copy of the tree; not a repository test.
- Recommended correction: orchestrator decision. Either accept it explicitly as a documented residual, or tighten the proof using relationships already read: refuse the owned-runtime proof when the hooked agent's direct parent is a same-provider agent process (the capture already knows the parent's mode through `ProcessRelations` for backends), and add a matched row (backend -> nested backend, both hook orders). The three legitimate shapes (native, node, powershell [node]) never have a same-provider image between the manager and the backend.
- Relationship: residual of ANALYSIS-1502/QA-2400; not a regression against baseline.

No other findings.

## Assessment and limitations

DEV-030 restores binding for launcher-based managed Codex installs without weakening the fail-closed rules and keeps the wire change additive (two integers per hop, at most three hops, ignored by older consumers). One new warning (QA-2500) documents the nested-backend ordering hazard that the developer had flagged as residual; it predates 2.2 and needs an orchestrator decision. Not performed: real providers, live instance, packaged NativeAOT ingress benchmark and publish. The first full run's only failure was a known timing test that passes alone. No orphaned stand-in processes of mine remain (all were started under disposable workspaces and cleaned by their tests); the user's `codex`, `claude` and `bell-tower` processes were not touched. No unexpected writes; scratch copy only.
