## Findings

### QA-5100: Successful hook-start acceptance remains unverified in real provider hosts

- Severity: warning
- Related task / requirement: task 4.5 and task 6.1; spec scenario “No tray is running when a hook arrives”
- Location: `openspec/changes/adopt-native-sessions-from-hooks/tasks.md:30,41`; `docs/compatibility.md:94` at the reviewed identity
- Expected / actual: after a valid hook persists a capture, a stopped tray starts detached and consumes the queued capture for both clients, except when a current user stop or management gate applies. The final fixture run had 11 ordinary-start assertions fail in the test-host ancestor-job context; the production diagnostic safely refused a child still in a job. No actual provider session has established successful startup outside that constrained context, and the native Codex job has not been probed.
- Reproduction: run the orchestrator's final isolated `HookTrayStartTests` selection (48 tests; 37 passed, 11 failed), then invoke the snapshot ingress with a disposable data root and valid launcher record from the current job-constrained execution context. The diagnostic returned `Failed/provider-job-breakaway-incomplete`, neutral `{}`, exit 0, and no fake-launcher record.
- Evidence: TRX XML inspection confirms the 11 named ordinary-start failures and confirms the new token, immediate/nested refusal and Exit producer cases passed. The separate diagnostic confirms the code fails closed when the new child remains in an ancestor job. These results explain the test-host failures but do not establish an installed provider's job policy or successful start path.
- Recommended correction: keep tasks 4.5 and 6.1 open until user-operated Windows Terminal and VS Code trials cover Claude Code and Codex with no tray after restart and after user Exit. Record provider versions and each outcome. Until then, describe Codex job behavior as unverified; do not label the safe refusal as either successful startup or a proven provider restriction. No code change is proposed by this finding.
- Relationship: new acceptance-evidence finding; no source defect asserted.

## Assessment and limitations

DEV-056's token and process-safety changes now pass their selector and synthetic immediate/nested job cases. QA-4800's CLI and menu producer tests pass, and the management stop remains distinct. The orchestrator's separate diagnostic confirms that the child cannot run when Windows leaves it in an ancestor job; safe refusal keeps the capture and does not claim success.

The 11 failing assertions are important functional evidence, even though they align with the execution host's inherited job restriction rather than a defect in the new fail-closed gate. They mean the successful ordinary-start paths were not demonstrated by this test run. The direct diagnostic ran under that same constrained execution context and therefore also cannot prove those paths in a normal interactive shell.

Recommendation: require the real-shell task 6.1 evidence before marking task 4.5 complete or treating both clients as verified. Keep Codex job behavior unverified until it is directly probed; do not infer a hard provider restriction from missing or constrained test evidence. The actual UAC pair, native Codex job and installed host trials remain unperformed. No source or test was changed by QA; only this report was written.
