### Managed / profile / launcher analysis (Codex, concrete)

Topologies traced:

- PowerShell `Start-Codex` default: a `bell-tower` runtime host starts `codex app-server --listen ws://...` (or `node codex.js app-server` for the npm layout, or an encoded `powershell.exe` wrapper for non-exe installs). The TUI runs as `--remote` under the shell. Hooks fire in the backend, which inherits `BELLTOWER_ATTACHMENT`. The agent's parent is the host (or node/powershell), never a Codex client. Before DEV-028 the mode was shared-backend and `Apply` returned the plain `Shared` capture. Now the mode is unknown. With managed ownership and a captured process, `Apply` returns a provisional capture with a candidate.
- Consumer: `Promote` builds the direct candidate; `AttachmentStore.Adopt` runs `Reconcile`. Verification needs either `previous.Process == backend` (a launch record names the TUI or nothing; `CodexRuntimeHost` records the host and shell, not the backend) or `AgentParent == launchShell` (parent is the host, not the shell). Both fail, so `Reconcile` returns `Shared(..., mode)`. The id changes, so `dedicated` becomes false in `HookIngestor`, and `inherited` is true in `CaptureConsumer`, so palette, name and change are not consumed. This is what the scratch test showed: same shared record, `Process=null`, host `unknown`, no shell, managed title/background false, lifecycle `shared-backend`, ownership `shared-runtime`, launch record bytes unchanged, session live with no waits.
- `bell-tower launch codex` (AgentLauncher): TUI parent is the launcher (not `codex.exe`), no codex child other than the backend. If the TUI is the agent (`--no-daemon`), R2 does not fire and it stays embedded and direct. If the backend is the agent, parent is the TUI (embedded client) and R1 keeps shared-backend. Unchanged.
- PowerShell profile launches (direct `codex.exe` under pwsh, `--no-daemon` standalone): no same-image parent or child, unchanged.

Result: for managed `Start-Codex` the answer to the developer's question is that nothing a user sees or any managed behavior changes (host actions, titles, presentation, lifecycle owner, ownership, launch metadata, ended-state handling). The only differences are the stored `Evidence.Mode` text and transient provisional/candidate fields on the wire and in the spool. The launcher does not need to be accepted as a backend parent for correctness; accepting it would only relabel the mode and is unsafe to do by pid alone. No consumer in `src` reads `Evidence.Mode` today (grep of `src`: only the evidence merge), but see QA-2301 for the planned binder.

## Findings

### QA-2300: Pid-reuse, creation-time and child-bound claims have no tests that can fail

- Severity: warning
- Related task / requirement: 2.5; evidence 028 ("creation-time consistency check against pid reuse", "at most 8 children")
- Location: `src/BellTower/IO/ProcessProbe.cs` `Neighbors` (parent `StartedUtcTicks <= agent`, child `StartedUtcTicks < agent`, `limit`); tests `NativeAgentRelationshipProcessTests.cs`, `ModeCrossCheckTests.cs` at the reviewed identity
- Expected / actual: each guard is a stated safety property, so a test should fail when it is removed. Removing the parent creation check, the child creation check, or the 8-child limit leaves all 142 relationship/resolve/cross-check tests passing.
- Reproduction: in a scratch copy, delete `&& identity.StartedUtcTicks <= agent.StartedUtcTicks`; delete `|| child.StartedUtcTicks < agent.StartedUtcTicks`; change `limit = 8` to a large value; run `--filter NativeAgentRelationshipProcessTests|ModeCrossCheckTests|NativeAgentResolveProcessTests`.
- Evidence: three surviving mutants (all 142 passed each time). Rule mutations (R2 parent narrowing, any-non-headless child) were detected.
- Recommended correction: add direct `ProcessProbe.Neighbors` tests with real sleeper processes: call with an `agent` identity whose `StartedUtcTicks` is set earlier than a real parent (parent younger -> null) and later than a real child (older child -> not listed); spawn 9 same-image children and assert `Complete == false` with 8 listed; also assert the self entry (agent pid) is checked against `agent.StartedUtcTicks` or document why not.
- Relationship: new

### QA-2301: A genuine long-lived shared backend is labeled unknown once its starting client exits, and the label is never corrected

- Severity: warning
- Related task / requirement: 2.5; design decisions 3, 7; task 4.2
- Location: `src/BellTower/Core/NativeAdoption.cs` `CrossCheck` (shared-backend case); `src/BellTower/Core/AttachmentEvidence.cs` `Merge` (stored non-unknown mode wins, unknown is replaced only by a later non-unknown)
- Expected / actual: decision 7 requires the parent to be a client, but evidence 009 and 011 show the backend outlives its starting client and is also restarted by `codex app-server daemon start`. After that the real backend has no live client parent, so every later conversation on it (the normal long-running case) is reported unknown, indistinguishable from an unproven mode, and with no reason code. Fail-closed behavior is correct and nothing user-visible changes today (shared-runtime either way), but task 4.2 and diagnostics (5.2) cannot tell "backend whose launcher exited" from "unrecognized shape".
- Reproduction: `ModeCrossCheckTests` row `codex, shared-backend, parent null -> unknown`; real topology from 009/011.
- Evidence: the developer already lists this under limits; no test or planning text records the consequence for 4.2.
- Recommended correction: record the reason with the mode (the developer's proposed reason code) before 4.2 depends on it, and state in the 4.2/5.2 plan that binder eligibility must not be gated on `mode == shared-backend` alone. Consider treating "no live parent" separately from "parent is a non-client" (the former is unproven, the latter contradicts).
- Relationship: new

### QA-2302: No regression test for the managed `Start-Codex` backend shape; the planning question can be closed

- Severity: suggestion
- Related task / requirement: 2.5 ("unchanged known shapes"); AGENTS.md compatibility with managed runtimes
- Location: `tests/BellTower.Tests/Providers/ModeCrossCheckTests.cs`, `NativeAgentRelationshipProcessTests.cs` (no managed row)
- Expected / actual: the developer asks whether the Bell Tower launcher should count as an accepted backend parent. Traced and tested in scratch (see analysis): it need not. There is no committed test asserting that a managed backend capture (managed id, process, non-client parent) still ends in the identical shared record and leaves the launch record untouched, so a later change to `Reconcile` could silently make it direct.
- Reproduction: scratch `ManagedBackend` test, 10 combinations, all stored fields identical for shared-backend and unknown.
- Evidence: scratch result described in the table above (scratch copy only, not committed).
- Recommended correction: add one parameterized row asserting the equivalence above for both entry paths (consumer and ingestor) and the three launch-record states, and record in evidence that the launcher is deliberately not an accepted backend parent.
- Relationship: new

### QA-2303: Asymmetric failure behavior and avoidable extra snapshot

- Severity: suggestion
- Related task / requirement: 2.5 R5; hook latency
- Location: `src/BellTower/Hosts/AttachmentCapture.cs` `CrossChecked`; `src/BellTower/IO/ProcessProbe.cs` `Neighbors`
- Expected / actual: when the snapshot or `Identify` of a parent or child fails, a backend becomes unknown but a client keeps its mode (a contradicting relative that cannot be opened is silently skipped). Also, `Complete == false` triggers unknown for a client when more than 8 same-image children exist regardless of their modes (headless children alone cannot contradict). Both are low-probability and defensible, but undocumented as intended. Cost is one extra process snapshot (about 14 ms measured, Codex only) on top of the existing ancestry snapshot; `Capture` could pass its snapshot to `Neighbors`.
- Reproduction: source inspection; timing measured in a scratch test (`Ancestors` 11.0 ms, `Neighbors` 13.5 ms, 396 processes).
- Evidence: scratch timing only.
- Recommended correction: document the asymmetry in the design or spec (fail-closed only for the shared-backend claim), count only non-headless children toward incompleteness if desired, and optionally share one snapshot per hook.
- Relationship: new
