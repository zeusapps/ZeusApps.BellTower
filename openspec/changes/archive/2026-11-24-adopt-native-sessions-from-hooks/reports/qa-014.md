## Findings

### QA-1300: A nested client rejected from an inherited managed identity keeps the launcher terminal's host and presentation flags

- Severity: warning
- Related task / requirement: 2.2, ANALYSIS-500 ("cannot transfer another terminal's ownership"), design decision 1
- Location: `src/BellTower/IO/AttachmentStore.cs:41-52` (at 2f1de7f working tree); test `tests/BellTower.Tests/Providers/NativeAdoptionTests.cs:173-196`
- Expected / actual: the process identity and attachment id are re-derived, but `Host` (shell from `BELLTOWER_SHELL_PID`, `WT_SESSION` terminal session, window), `ManagedTitle` and `ManagedBackground` are copied from the captured attachment, which for a nested client are the inherited values of the launching terminal. The own-identity record is therefore saved with `Host.Shell`/`TerminalSession` and the managed title/background flags that belong to another terminal. Task 4.1/4.3 would then route navigation or write title/background through the other terminal. The test builds the capture with `ManagedTitle: true` but asserts only id, process, ownership and lifecycle owner, so the gap is untested.
- Reproduction: source inspection of the `RejectsInheritedManagedIdentity` branch and the test's `Captured(...)` fixture (this is not an executed failing test).
- Evidence: source review only; executed nested-client test passes.
- Recommended correction: in the rejected branch, reset `Host` to unknown (keep only independently verifiable ancestry), clear `ManagedTitle`/`ManagedBackground`, and assert it for both providers. Cover headless and interactive nested clients.
- Relationship: extends ANALYSIS-500 verification; not a duplicate of an existing ID

### QA-1301: A nested client that outlives its inherited-id owner is re-attached to the dead launch record

- Severity: suggestion
- Related task / requirement: 2.2, 2.1 (lifecycle)
- Location: `src/BellTower/IO/AttachmentStore.cs:117-119`, `src/BellTower/Providers/CaptureConsumer.cs:60-67`
- Expected / actual: rejection requires the recorded owner to be live. After the owner dies, the nested client's later hooks (still carrying the inherited id) are no longer rejected. They reach the old attachment, fail the process-conflict check and return the dead launch record, so `attachment.Id == observation.AttachmentId` (the launch id) and the session moves off its own record onto an ended one.
- Reproduction: source inspection; not executed.
- Evidence: source only.
- Recommended correction: make the rejection stable for the session (for example reject whenever the captured process differs from a recorded owner, live or dead, unless it is an explicit resume), or key the redirect on the session.
- Relationship: none

### QA-1302: Codex classification fails open for unlisted subcommands and unknown value-taking options

- Severity: warning
- Related task / requirement: 2.2, design decision 2 (fail closed to shared runtime unless provably direct), AGENTS.md parity
- Location: `src/BellTower/Core/NativeAdoption.cs:53-79`
- Expected / actual: only `app-server`, `exec`/`e`, `review` and the empty case are specially handled; any other non-option token returns `embedded-runtime`, which keeps process and host. A hook from an unverified subcommand (for example `mcp-server`) or from an invocation where an unknown value-taking option's value is read as a "prompt" is classified as a direct client and claims the ancestor shell/host, while the implementation notes say only verified shapes are direct. Positional prompts make a full allow-list impossible, but `resume`/`fork`/no-subcommand are the only verified shapes, and no test covers such rows or `--` handling for Claude.
- Reproduction: `AgentModeClassifier.Classify("codex", true, ["mcp-server"])` returns embedded-runtime by reading `Codex()`.
- Evidence: source and the `Modes` theory (no row for these inputs).
- Recommended correction: decide and document the policy for unlisted subcommands (treat known non-session subcommands as `unknown`, or accept prompts only when no other subcommand-like token matches), add theory rows, and keep the Codex value-option list tied to the probed 0.165.0 help.
- Relationship: none

### QA-1306: "Other Codex subcommands fail closed" does not hold; provider drift fails open, including for app-server

- Severity: warning
- Related task / requirement: 2.2, design decision 2, ANALYSIS-500 (orchestrator addendum 1)
- Location: `src/BellTower/Core/NativeAdoption.cs:53-79` (Codex), `:35-49` (Claude)
- Expected / actual: only `review` and unreadable command lines are `unknown` (fail closed for Codex). Every other positional token is `embedded-runtime` (direct, keeps process and host). A positional prompt and an unknown or future subcommand are lexically identical, so the code cannot tell them apart. Consequences of drift: (a) a new in-process or non-session subcommand (for example `mcp-server`) is treated as a direct client and claims the ancestor shell and host; (b) a new value-taking option not in `CodexValueOptions` has its value read as the first positional, so `codex --new-opt value app-server` or `... exec` is classified `embedded-runtime` instead of `shared-backend` or `headless`. That misclassifies a shared backend as direct, which re-opens the ANALYSIS-500 leak (inherited launcher ancestry and flags claiming the launcher's terminal) without any test failing; (c) a renamed `app-server` does the same. Claude is open by construction: everything except `-p`/`--print` is interactive, so a new headless or SDK flag claims a host. Claude has no shared backend, so there is no ownership leak, only a wrong terminal claim.
- Reproduction: `AgentModeClassifier.Classify("codex", true, ["--new-opt","v","app-server"])` returns `embedded-runtime` by reading `Codex()` (source inspection; no row in the `Modes` theory covers it).
- Evidence: source only.
- Recommended correction: make `app-server` detection independent of option parsing (any token equal to `app-server` before `--` classifies as shared backend), treat an unrecognized option that is not `--name=value` form conservatively (for example `unknown` when an unknown option precedes the first positional), allow-list `resume`/`fork`/prompt-only shapes as direct, and add drift theory rows for both providers. Record the 0.165.0 and Claude version the vocabulary was verified against and surface an unrecognized shape in diagnostics.
- Relationship: supersedes the scope of QA-1302 (keep QA-1302 for the unlisted-subcommand case)

### QA-1307: A managed Codex `--no-daemon` launch loses its terminal binding when the agent is not recognized or its command line cannot be read

- Severity: warning
- Related task / requirement: 2.2, "profile users must see no change" (orchestrator addendum 2)
- Location: `src/BellTower/Hosts/AttachmentCapture.cs` (`Resolve`, agent lookup by exact `<provider>.exe` ancestor name), `src/BellTower/Core/NativeAdoption.cs:176-192`, `src/BellTower/Sessions/AgentLauncher.cs:32`
- Expected / actual: before, `BELLTOWER_DEDICATED=1` made a managed Codex `--no-daemon` launch direct regardless of process evidence. Now, if no `codex.exe` ancestor is found, or its command line is unreadable (`ProcessProbe.CommandLine` returns null for a protected or inaccessible agent), the mode is `unknown`; for Codex that fails closed to shared-runtime. The hook gets a session-derived id, no process, unknown host and no managed title or background, the managed launch record is never adopted, and `CaptureConsumer` skips palette consumption because `Dedicated` is false. The terminal binding and launch presentation the user had are lost. An elevated agent is not a practical cause (the same-user child ingress can read it), but a renamed or wrapped image (name mismatch) and protected processes are. Claude is unaffected: an unreadable command line keeps its direct classification, which is a Codex-only parity asymmetry. Other managed-path changes: Codex managed without `--no-daemon` stays shared (now through `app-server` classification, same result); managed `claude -p` and `codex exec` now drop host, title and background by design (a visible change for profile users who run headless commands); a managed nested client with a live different owner now gets its own identity (QA-1300).
- Reproduction: source inspection; the `PowerShellModuleTests` change (fake agent renamed to `codex.exe`) shows the dependency. Not executed against an installed managed launch.
- Evidence: source and the test fixture change.
- Recommended correction: when `BELLTOWER_ATTACHMENT` names a managed launch and the mode is `unknown`, prefer the managed record's recorded evidence (verify at adoption that the launch record has no live different owner, which QA-1300/1301 already check) over fail-closed shared; or at least add a test for managed plus unknown and decide the rule explicitly. Document the headless-managed change in the compatibility notes.
- Relationship: related to QA-1300

A gate is needed from 2.3 on, as the developer notes.
