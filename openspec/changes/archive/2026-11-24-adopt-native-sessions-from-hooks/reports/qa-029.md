## Findings

### QA-2900: Socket creation-time replacement check is not covered by any test

- Severity: warning
- Related task / requirement: 3.1 (endpoint replacement); design decision 4 and 7
- Location: `src/BellTower/Providers/CodexSharedTransport.cs:111` (`info.CreationTimeUtc != socketCreated`); `tests/BellTower.Tests/Providers/CodexTransportTests.cs:230-246`; `CodexSharedAccess.cs:57-60` (`Replaced` from the socket half of the identity)
- Expected / actual: Expected the recreated-socket detection to be pinned by a test that fails if the comparison is removed. Actual: replacing the comparison with `false` leaves all 19 tests passing. `RecreatedSocketIsDetectedAsReplacement` asserts `ThrowsAnyAsync<Exception>`, which is satisfied by the old server simply closing its connection, and then only reopens without asserting `Replaced` or `EndpointReplaced`. Native evidence also shows a killed backend leaves a stale socket file and implementation-034 notes NTFS tunneling can preserve creation time, so this half of the identity is the less reliable one and the one with least proof.
- Reproduction: in `CodexSharedTransport.EnsureCurrent` change `info.CreationTimeUtc != socketCreated` to `false`, build, run `CodexTransportTests` (all pass). Verified as mutant M4.
- Evidence: this report, Mutants row.
- Recommended correction: make the recreated-socket test deterministic: keep the connection open, delete and recreate the socket file for the same live backend identity (or hold the old server alive while a new file appears), and assert `CodexTransportFailure.EndpointReplaced` on the next call and `Replaced == true` on reopen through the same `CodexSharedAccess`. Also add a case where the same backend identity reopens with a different socket creation time and assert `Replaced`.
- Relationship: new

### QA-2901: Backend identity check does not bind the live process to the connected socket or home

- Severity: suggestion
- Related task / requirement: 3.1 provenance; design decision 4 ("verify its local provenance"), decision 7 (revalidate bindings)
- Location: `src/BellTower/Providers/CodexSharedTransport.cs:125-128` (`IsLiveSharedBackend`), `:88-99` (`VerifyInitialized`)
- Expected / actual: The identity check proves that the supplied PID plus creation time is a live Codex shared-backend command line; it does not prove that this process owns the socket being connected or serves this home (Windows offers no socket owner lookup, as the developer notes). The only home binding is the `codexHome` string reported by whatever answers on the path. A same-user listener at the derived path that echoes the home, together with any live Codex shared backend identity (for another home), passes both checks. The risk is bounded: same-user attacker, derived path under the resolved home, no enumeration, no payload endpoint, and the transport is read/name-only. The refusal strength is nonetheless weaker than the "provenance-checked" wording suggests.
- Reproduction: source inspection plus the `DefaultProvenance...` test, which shows the identity check is independent of the home. Not executed as an attack.
- Evidence: source; native check confirmed that the identity check refuses non-backend processes but cannot tell backends of different homes apart.
- Recommended correction: for 3.2, have the binder resolve the backend identity per home from the process table (command line and, where available, `CODEX_HOME` of the backend) and document that the transport's home match is self-reported. Consider also comparing the socket file's creation time with the backend's creation time (socket must not predate the process) as a cheap extra binding. Keep the diagnostics wording accurate about this limit.
- Relationship: new; complements the developer's stated 3.2 dependency

### QA-2902: Post-handshake read timeout surfaces as `OperationCanceledException`

- Severity: suggestion
- Related task / requirement: 3.1 bounded read budget; reason-bearing refusals
- Location: `src/BellTower/Providers/CodexConnection.cs:117-121` (`CallAsync` read budget); mapping to `Timeout` exists only in `ConnectAsync` (`:91-94`)
- Expected / actual: A request that exceeds `Budget.Read` after the connection is established throws a plain `OperationCanceledException`, indistinguishable from the caller's own cancellation, so a 3.2 consumer cannot report or back off on a `Timeout` reason as it can for handshake failures. No test covers the read budget after the handshake. By source inspection only; not executed.
- Reproduction: stand-in server that answers `initialize` and then stays silent on `thread/read`; call `CallAsync` with a non-cancelled token and observe the exception type.
- Evidence: source inspection.
- Recommended correction: in `CallAsync`, when the transport is strict and the read limit (not the caller token) fired, throw `CodexTransportException(Timeout)`; add a stand-in `Silent`-after-handshake test.
- Relationship: new

### QA-2903: Skip bound is a per-call backlog bound with no test

- Severity: suggestion
- Related task / requirement: 3.1; owned loopback unchanged
- Location: `src/BellTower/Providers/CodexConnection.cs:119`, `src/BellTower/Providers/ICodexTransport.cs:41`
- Expected / actual: Previously unmatched messages were skipped without limit; now 1000 are allowed per call and the 1001st unmatched message throws `InvalidDataException`. Notifications queued between calls on a long-lived connection are consumed by the next call's loop, so a busy runtime plus an idle connection could exhaust the bound. Current callers open a short-lived connection per operation, so the risk is low and the failure is clean; no test pins the bound or the exception.
- Reproduction: not executed; source inspection only.
- Evidence: call sites at `CodexNameService.cs:47`, `CodexPermissionPump.cs:111`, `CodexRuntimeHost.cs:120` all use `using var`.
- Recommended correction: add a stand-in test with 1000 and 1001 unrelated notifications before the response; record in the 3.2 notes that a long-lived pooled connection would need a drain or a per-message-budget approach.
- Relationship: new

### QA-2904: Backoff key and verified-endpoint key use different comparers and unnormalized home text

- Severity: suggestion
- Related task / requirement: 3.1 backoff; "existing backoff reused, no spinning"
- Location: `src/BellTower/Providers/CodexSharedAccess.cs:19-20,30` (`schedule` is `StringComparer.Ordinal`, `verified` is `OrdinalIgnoreCase`; the key is the raw `codexHome` text)
- Expected / actual: Two spellings of the same home (case, trailing separator) get independent backoff entries, so a caller that passes differently spelled homes can bypass the failure backoff; the same spellings share one `verified` entry. By source inspection only; not executed. The derived endpoint itself is normalized, only the keys are not.
- Reproduction: fail `OpenAsync` for `<home>` then call again with `<home>\`; expect `BackedOff`, source suggests a fresh attempt.
- Evidence: source inspection.
- Recommended correction: normalize the home once (the same full-path/trim rule as `CodexSharedEndpoint`) and use it for both keys, with a case-insensitive comparison on Windows for both; add a test.
- Relationship: new

## Assessment and limitations

Acceptance covered for task 3.1: owned loopback behavior is unchanged in code and tests; the shared transport derives the endpoint only from the resolved home, refuses with distinct content-free reasons, bounds connect and handshake, reuses the existing backoff without spinning, detects backend replacement, fails closed on an overlong path, is non-owning in code and tests, and was exercised natively against a private Codex 0.166.0 backend without any model request or egress. Mutation testing killed five of six key checks; the surviving one is the socket creation-time replacement check (QA-2900), which I recommend fixing before 3.2/3.3 rely on `Replaced`. QA-2901 to QA-2904 are suggestions for 3.2 hardening and none blocks the boundary.

Limitations: a `Replaced == true` result across a real backend restart was not natively exercised (my restart used a fresh opener), and the live NTFS tunneling case was not probed; both remain stand-in only. Claude Code was not part of this task (no Claude shared backend exists); mixed Claude/Codex simultaneous-session checks are not applicable until 3.2 wires the transport. The full-suite load failure was a Tray audio timing test, passing alone, and the developer's earlier HttpConnection failure could not be reproduced or attributed.
