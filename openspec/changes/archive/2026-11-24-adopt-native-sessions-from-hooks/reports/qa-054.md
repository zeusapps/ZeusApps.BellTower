## Findings

### QA-5400: A hand-set provider title setting is a dead end for the step

- Severity: suggestion
- Related task / requirement: 4.7, session-identity "Provider-owned terminal titles", standalone-setup "Opt-in provider title control"
- Location: `src/BellTower/Setup/ProviderTitleSettings.cs` lines 67 to 77 (Claude) and 125 to 136 (Codex); `src/BellTower/Setup/ProviderTitleControl.cs` line 16, at `2e7f318`
- Expected / actual: A user who already set `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` or `terminal_title = []` by hand gets window-only navigation with the reason "run setup --provider-titles". Running it only adds the note "left unowned" and changes nothing, so Bell Tower still writes no title and the stated reason cannot be satisfied. The stated design (a title only while the step is owned, never remove what the user made) is respected, but the guidance leads nowhere for this user.
- Reproduction: Disposable settings with the value already present, `setup --provider-titles --apply`, then check `nativeSessions` doctor output (source inspection of the branch; `ProviderTitleStepTests` asserts the unowned result but not the follow-up guidance).
- Evidence: Source inspection only.
- Recommended correction: Either let the step take shared ownership of an identical hand-set value (remembering it was already present, so removal leaves it), or make the reason text and note say how to proceed (remove the hand-set value first, or that it needs no action but title stays off). Decide and cover with a test.
- Relationship: new

### QA-5401: The task fallback can add up to 3 seconds to a hook

- Severity: suggestion
- Related task / requirement: 4.6, design decision 10 ("the hook never waiting")
- Location: `src/BellTower.Protocol/HookStartTask.cs` lines 16 and 62, at `2e7f318`
- Expected / actual: The hook waits for `schtasks /run` for up to 3 s when the shell start failed and a task is recorded. This is bounded and only on the failure path, but it is a wait that the surrounding text says the hook never has, and it was not measured (DEV-059 says hook latency was not re-measured).
- Reproduction: Source inspection; a stand-in `schtasks` that never exits would show the full bound.
- Evidence: Source inspection of `RunWait` and `WaitForSingleObject`; the existing fallback test uses a fast stand-in.
- Recommended correction: Measure the fallback path during the 6.1 trial and record the number, or shorten the bound or let the hook return without waiting on the exit code. At minimum state the 3 s bound in the design text.
- Relationship: new

## Assessment and limitations

Tasks 4.6 to 4.10 work as described for both providers in fixture and disposable-environment execution. No critical or warning finding. The two suggestions are open for the orchestrator to triage. The deliberate narrowing of the self-check to hook-started trays matches the assignment and the delta spec text. The shell is checked by image, user, session and by re-reading the shell window owner after opening (not by creation time as the design text lists); the re-read covers the process reuse case and I do not report it.

Not performed, and needed before release acceptance: an elevated hook (the `child-elevated` guard path has only table tests), a VS Code terminal, other Windows builds, Native AOT publish of the ingress, hook latency, real-model Codex approvals and other `approval_policy` values (a held `PermissionRequest` under a policy other than on-request is not captured, so the `user` reviewer rule is evidenced only for on-request), and other Codex or Claude versions. Evidence types: all executed checks are fixture or disposable-environment runs; nothing was run against installed native tools or a live tray. One full-suite failure was the known load-bound timeout and passed alone. No scheduled task remains. Target identity was identical before and after, and the only writes were this report and ignored build and test outputs.
