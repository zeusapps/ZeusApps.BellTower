## Findings

### QA-004: Playback can still authorize from the real source's pre-input cache

- Severity: warning
- Related task / requirement: tasks 2.4, 2.5 and 3.3; fresh idle state at playback and cancellation
- Location: `src/BellTower/Tray/WindowsUserIdleSource.cs:45-57` and `src/BellTower/Tray/TrayApplication.cs:367-374`, at target `2cabb1effe53`
- Expected / actual: A playback request must not be authorized by an idle sample taken before that request when newer input may have occurred. The tray now asks the source again, but the real wrapper returns the prior positive-idle snapshot while it is within its 500 ms validity window and before its 250 ms refresh is due. A deterministic T+100 ms recent-input case still validates playback.
- Reproduction: Obtain an idle snapshot, then at T+100 ms make the injected low-level observer report recent input and invoke the real source through the playback validity path. The wrapper returns the old idle duration, performs no fresh low-level read, and returns valid.
- Evidence: The deterministic wrapper-to-playback probe in [analysis-002 evidence](../evidence/analysis-002.md) reports `cachedIdleMinutes=20`, `lowLevelReads=1`, and `valid=True` after recent input. The mutable-source-only tests do not cover the wrapper's cache.
- Recommended correction: Provide a bounded playback-specific freshness path that cannot grant eligibility from a sample predating the playback request. A bounded fresh local-input read or a fixed-budget single-flight refresh may be used; potentially blocking WTS work must remain off the audio callback. Add real-wrapper recent-input, timeout/unknown, and single-flight mixed-batch fixtures.
- Relationship: Duplicate of canonical ANALYSIS-004; QA-004 was already recorded as its duplicate in QA-001. No new canonical finding is proposed.
