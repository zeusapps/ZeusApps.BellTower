## Answer: which rollback paths expose the loss (hooks on the candidate image while 0.1.9 is selected)

- The automatic rollback of a failed update never does. `UpdateTransaction.Apply` (`Updates/UpdateTransaction.cs:146-175`) only restores the selection to `plan.Original` and restarts that tray. The update never rewrites hook commands: `RefreshIntegrations` (`:131`, `:291-297`) runs `IntegrationRefresh.Apply` (`Setup/IntegrationRefresh.cs:16-35`), which refreshes only the shell module and the VS Code bridge. Hook commands (the ingress image hash) are written only by an explicit `setup` (`docs/installation.md`), so at the moment of an automatic rollback the hooks still name the image of the version that was selected before the update. Updates only go forward (`UpdateTransaction.Stage`, `:46`), so the restored version is never older than the version whose setup wrote the hooks.
- Exposed: a manual reselect of an older payload after the user (or setup run by the candidate) rewrote the hooks to the candidate image, that is the documented manual restore of `current.json` (`docs/installation.md`, `docs/releases.md`) and the harness stand-in; and `install-dev.ps1 -Action Rollback` after a setup ran under the dev build (`scripts/install-dev.ps1` runs no setup itself, so only a setup run by the user in between exposes it). Not exposed by any rollback: the 0.1.9 image restored by 0.1.9's own `setup --clients both --apply` (checked: delivery is whole again for every launch kind).
