## Per finding

- **ANALYSIS-180.** `CheckoutPolicy.Release(identity)` sets a `retained` source back to `launch`. It is called by `SessionCatalog.Configure` whenever a checkout argument is given (clear with `""`, as CLI `rename --checkout ""` and the tray's Clear checkout do, and attach) and by `IdentityControls.Reset` (CLI `--reset`, tray Reset pins). Both providers share the path. Test: `ClearCheckoutAndResetReleaseARetainedCheckoutForGood` (claude/codex x clear/reset, two refreshes each).
- **ANALYSIS-181.** `GitReader.TryWorktrees` returns null on failure (timeout, start failure, unreachable launch directory); `Worktrees` keeps its old shape. `IdentityResolver` never caches a null listing and treats it as an empty list for the pin, provider and unique-work tiers (unchanged behavior). `CheckoutPolicy.RetainedCheckout(checkout, listing)` keeps the retained checkout on a null listing while its directory exists, and releases it on a successful listing without it or a missing directory. Tests: `AFailedWorktreeListingKeepsTheRetainedCheckoutUntilThereIsPositiveEvidence` (both providers; the launch directory is made unreachable, then `git worktree remove` releases it) and `AFailedListingStillReleasesARetainedCheckoutWhoseDirectoryIsGone`. Note: a first attempt that hid `.git` did not fail the listing, because the disposable workspace sits inside the enclosing repository; the unreachable launch directory is the honest failure injection.
- **ANALYSIS-182.** A `retained` checkout is passed to `Choose` only while `identity.WorkSubject` is null, so any new work (mapped or not) releases it; new unmapped work shows the launch checkout again. Test `AnyNewWorkReleasesTheRetainedCheckout` (both providers).
- **QA-181.** `RetainedAsync` also offers the previously selected unique-work checkout when `Choose` found no candidate, the checkout is still listed (or the listing failed and it exists), a branch-bound `ActiveWork` with a `WorkBranch` exists, no pinned change exists, and the checkout's current branch differs from `WorkBranch`. The same pass then clears the work through `ApplyBranch` and keeps the checkout as `retained`, so retention no longer depends on the change folder surviving the switch or on the worktree being named for the ticket. A vanished change folder without a branch change still falls back to launch. Tests: `ABranchSwitchThatRemovesTheVerifyingChangeFolderStillRetainsTheCheckout` (both providers, change folder committed on the old branch, worktree `alpha`, three refreshes) and `AChangeFolderThatVanishesWithoutABranchChangeStillFallsBackToTheLaunchCheckout`.
- **ANALYSIS-184.** The trigger uses `WorkSubject` (before and after `ApplyBranch`). Test `APinnedChangeThatStillVerifiesTheCheckoutNeverFlipsTheLabelToRetained` (both providers, two refreshes stay `unique-work`).
- **ANALYSIS-185.** `CheckoutPolicy.Retained` is now the token `"retained"`, with a comment that it is a stored data contract; `RetainedLabel` holds the display text and `CheckoutPolicy.Describe` maps it; the tray (`OverviewForm.NativeStatus`) uses `Describe`. `list` prints the raw token (`checkoutSource` row field and `identity.checkoutSource`); `doctor` does not show the source. Test `TheRetainedSourceIsAStablePersistedTokenAndOnlyThePresentationIsWorded` pins the value and its JSON. The earlier long string was never released; identities that hold it (only this development tree) read as an unknown source and drop to launch on the next pass.
- **ANALYSIS-183.** `PackagedHookBenchmarkScenario.ContractGate` (public, static) requires controls valid, planned = run = accepted native hook runs, and both estimates below 300 ms; the check detail says so. Test `TheContractGateFailsWhenAnyPlannedHookRunIsMissingOrNotAccepted`.
- **QA-180.** `RunReport.Verdict` is `PASSED`, `PASSED WITH UNFINISHED ITEMS` or `FAILED`; `RunReport.ExitCode` is 0, 3 (new) or 1. Console headline and `summary.md`/evidence `Result:` line use the verdict. `scripts/field-acceptance.ps1` documents the exit codes in its header and passes 3 through with a warning (it does not throw); `docs/distribution-validation.md` documents them. Tests: `AnUnfinishedItemIsCountedAsItsOwnOutcomeAndIsNeverAPass` (updated to pin the new verdict and exit 3) and `ARunWithoutUnfinishedItemsIsAPlainPassWithExitCodeZero`. Verified end to end: `five-conversations` and `--scenario all` exit 3 through the script. Anything that gates on the exit code (the 4.x release gate) must treat 3 as open work.
- **ANALYSIS-187.** `branch-change-keeps-working-checkout` also requires each switched conversation's `list` `checkoutSource` to equal its expected token and prints it. `SessionRow` gained `CheckoutSource`. The expected token is `retained` for conversations whose work was cleared and `unique-work` for the pinned-change conversation (its pinned change still verifies the worktree; this is the ANALYSIS-184 behavior). The first rerun failed on exactly that, which showed the check was not vacuous.
