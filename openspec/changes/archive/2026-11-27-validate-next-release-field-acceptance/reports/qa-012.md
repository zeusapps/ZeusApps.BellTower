## Assessment and limitations

- All seven assigned findings verify as fixed on this target, for Claude Code, Codex and mixed sessions, with the limits stated in the table: the installed CLI and tray Clear paths were verified by unit tests only (the CLI needs a registered session, which needs the tray's capture consumer, and the user's trays are off limits). The ledger is for the orchestrator to close.
- Mistake in my execution, disclosed: my first attempt to hold the harness mutex was quoted wrongly, so `scripts/field-acceptance.ps1` ran a full five-conversations harness while the first full suite was still running. I stopped it. Four sandbox `bell-tower.exe` processes (all under `artifacts/field-acceptance/runs/<timestamp>/sandbox`) were left; I stopped them by command line. The next harness run's preflight sweep deleted two leftover `HookStart-*` scheduled tasks that the aborted run had created (the sweep reports only harness-owned leftovers). Full-suite run 1 was therefore under extra load, which is why runs 2 and 3 were added.
- Isolation false positives: two of the four five-conversations runs failed only `isolation/production-unchanged` ("a production Bell Tower process started during the run"; the PIDs were gone afterwards, and the only production processes alive at the end were the user's trays 8060 and 28388, untouched). The guard counts a production process that appears during the run as a change, and the live agent sessions on this machine start `bell-tower.exe` hook processes when they use tools. Reruns passed. This is an environment sensitivity of the guard when the run is not quiet; I did not file it as a finding because the recheck rules bar new suggestions, and the orchestrator may want to decide whether it belongs in the ledger. The two production-guard failures are not product failures: every scenario check passed in those runs.
- Build outputs after a harness run: `-RebuildCandidate` (via `scripts/package.ps1`) and the harness build changed shared Release outputs so that 91 to 94 process-spawning tests failed until `dotnet build -c Release --no-restore` ran again. I did not establish which file differed. Run the suite before the harness runs, as the assignment order does, or rebuild between them.
- `passed` in `result.json` stays `true` for a run with unfinished items; `verdict` and `exitCode` carry the distinction. This is the documented design, not a defect.
- The two unfinished items (`codex/native-title-tier`, `mixed/native-title-tier`) are the known open Codex native-title parity gap (ledger F7); this run does not change them.
- Cleanup: removed `artifacts/qa012-probe` (including the `git archive` copy of v0.1.9 sources, which stayed under `artifacts/`) and `artifacts/qa012`. Retained under `artifacts/` (ignored): `qa012-*.txt` logs and the harness run folders. No tree copies exist outside `artifacts/`. After my runs no `BellTower`, `testhost`, `vstest` or harness process of mine remains; only the user's trays 8060 and 28388 are alive. No orphaned PID I could not stop. Nothing was written to `~/.claude`, `~/.codex` or the real installation or data directory by me.
