## Findings

### QA-100: An aborted run (Ctrl+C or kill) leaves the sandbox Task Scheduler entry, trays and sessions, and nothing detects it later

- Severity: warning
- Related task / requirement: 2.1 (isolation, "removed on success and on failure/abort"); spec honest silent evidence
- Location: `tools/BellTower.FieldAcceptance/Program.cs:110-155` (cleanup only in `finally`; no `Console.CancelKeyPress`/`AppDomain.ProcessExit` hook); `Isolation/ProductionSnapshot.cs:73-86` (a task present both before and after is not a change)
- Expected / actual: Expected the task registered in the user's real Task Scheduler to be removed when the run is interrupted, or at minimum the next run to detect and report it. Actual: after the harness process was killed mid-run, `schtasks` still listed the sandbox `HookStart-<hash>` task and two sandbox `bell-tower` processes were running. A later run puts that orphan in both snapshots and computes `ownTasks` only for its own new data directory, so the orphan passes silently and accumulates.
- Reproduction: start `scripts/field-acceptance.ps1`, wait until a second `HookStart-*` task appears in `schtasks /query`, stop the `BellTower.FieldAcceptance.dll` process, list tasks and processes whose image is under `artifacts/field-acceptance/`.
- Evidence: observed once (task `HookStart-a1e9...` and two processes); I deleted exactly that task and those processes afterwards. The user's task `HookStart-274c...` was never touched.
- Recommended correction: register a `CancelKeyPress` and `ProcessExit` handler that runs the same instance disposal (tray exit, task delete, sandbox process sweep); and add a preflight that computes the task path of every leftover sandbox data directory under `artifacts/field-acceptance/**/sandbox` (and kept sandboxes) and fails or removes orphans before the run. Document the manual cleanup command in `docs/distribution-validation.md`. Note that a forced kill of the harness can never be fully covered by an in-process handler, hence the preflight.
- Relationship: new

## Assessment and limitations

Acceptance 1 (real baseline, hash verification, fixture candidate, no rebuild), 3 (56 of 56 checks, assertions meaningful and not vacuous) and 5 to 8 are met. Isolation on a normal and failing-check path is strong: allow-listed environment, a guard that fails closed and is self-tested against the real locations each run, and a before/after comparison of 87 production files, the installation tree, the scheduled tasks and the running production processes, with no change. The one out-of-sandbox effect, the per-sandbox Task Scheduler entry, is uniquely named, never touches the user's task, and is removed on normal completion, but not on an abort (QA-100, warning).

Limitations: exception and failing-scenario cleanup are verified by source inspection and unit tests only. Ctrl+C was approximated with a forced kill. The full .NET suite is not clean on this machine under concurrent load (three runs: 1, 1 and 6 different failures, all passing in isolation, and the 6-failure run excluded the FieldAcceptance tests), so a clean full-suite pass is not demonstrated by me. The failures I saw do not involve this change but the baseline suite should be rerun on an idle machine. Not exercised anywhere: VS Code bridge, Codex `/hooks` trust prompt, live installation, update-acceptance script and Smoke command. Client coverage: Claude Code, Codex and mixed are all covered by the installed-harness checks above; build, format, Node and OpenSpec checks are client-neutral. No commits, no production writes, no sound.
