## Findings

No additional QA IDs were allocated. Two independently reproduced defects share the analyzer's canonical IDs rather than duplicating ledger entries.

### ANALYSIS-001: Returning to a previously successful title skips repair after a partial failed write

- Severity: warning.
- Related tasks: 3.2–3.3; change-driven terminal presentation and last-successful receipt correctness.
- Locations at reviewed identity: `src/BellTower/Hosts/TerminalTitlePump.cs:83`, `:99`; `src/BellTower/Hosts/AttachedConsoleTitleWriter.cs:15`.
- Expected: once an attempted write may have changed the destination, a later desired A must be written unless current A is known to be applied.
- Actual: successful A leaves `Successful=A`. Failed B retains that receipt, even though the real console writer can successfully set the title to B before background output fails. Desired A then equals the retained receipt and is skipped indefinitely.
- Independent reproduction: report-local fake writer mutates its title before returning false for B. Observed `requests=A,B; desired=A; actual=B; expectedRequests=A,B,A; defect=True`.
- Evidence: [script](qa-001-partial-write.ps1), [output](qa-001-partial-write.txt). The fixture mirrors the inspected real writer's partial mutation; it does not claim an actual native background failure was induced.
- Recommended correction: invalidate certainty after an attempted failed write; add a developer-owned regression covering A success → B partial failure → A success, while preserving unchanged-tick deduplication/backoff.
- Relationship: canonical analyzer finding ANALYSIS-001; independent corroboration, not a new duplicate ID.

### ANALYSIS-002: Same-ID resume combines new process ownership with the former host destination

- Severity: warning.
- Related tasks: 2.1, 2.3–2.4; attachment generation, repair and verified navigation.
- Locations at reviewed identity: `src/BellTower/IO/AttachmentStore.cs:40`, `:44`, `:49`.
- Expected: when the supported explicit resume path replaces ownership, its host kind and destination must belong to that same replacement generation, or navigation must remain unavailable.
- Actual: replacement updates agent/shell, but window process, nonzero window handle, terminal session and known host kind retain the old values. New agent/shell can therefore be paired with an old destination.
- Independent reproduction: end previous same-ID attachment with Windows Terminal metadata; capture an explicit resume with verified new owner and VS Code/new host metadata; call `Adopt(..., resume: true)`. Observed `newAgent=True; newShell=True; newWindow=False; kind=windows-terminal; handle=111; terminal=old-terminal`, despite captured `vscode/222/new-terminal`.
- Evidence: [script](qa-001-partial-write.ps1), [output](qa-001-partial-write.txt). Window values are synthetic, identities are actual live processes, no focus was attempted, and the spawned helper was killed/joined. Ordinary fresh managed launches allocate new GUIDs and are unaffected; the defect is scoped to the explicitly supported same-ID replacement branch and its direct existing resume test contract.
- Recommended correction: replace or safely invalidate generation-bound host fields during explicit replacement while preserving extension data and refusing stale/conflicting non-resume repair. Add developer-owned same-ID cross-host replacement regression.
- Relationship: canonical analyzer finding ANALYSIS-002; independent corroboration, not a new duplicate ID.
