## Findings

### QA-200: Packaged health-aware tray refuses its own migrated state at startup

- Severity: warning; blocks the requested development-trial activation.
- Requirement/task: 4.1 current health-capable monitoring consumer must start with committed health-v1 snapshots; lifecycle restart.
- Location: `src/BellTower/Program.cs:16`, reviewed target 002; `CaptureCompatibility.EnsureTrayInvocation` optional `attachmentHealth` parameter defaults to zero.
- Expected: this payload advertises and implements health-v1, so its real tray entrypoint should pass capability 1 and start against its own migrated state. Legacy incapable consumers should still be refused.
- Actual: `Program.Main` calls `CaptureCompatibility.EnsureTrayInvocation(args, 1)`, implicitly declaring health capability zero. Real package exits 1: `Attachment health requires a health-v1 consumer; selection and sessions were preserved. Keep a compatible tray selected.` This occurs with an empty migrated snapshot, before tray startup.
- Independent reproduction: copied developer's minimal snapshot into a new isolated directory, started the exact packaged payload with `tray --silent --data-dir <isolated>`, and captured process exit/stdout/stderr. It exited within five seconds; no cleanup signal or termination was needed. Snapshot remained unchanged.
- Evidence: [qa-003-startup.json](qa-003-startup.json). No production data, settings, provider, sound or session was touched.
- Recommended correction: make the executable entrypoint declare the same health capability as its distribution probe, and add a real-executable isolated startup/restart regression. Rebuild/repackage and independently verify the corrected entrypoint before any production tray switch.
- Relationship: new finding, developer-discovered and QA-independently reproduced; existing ANALYSIS-001/002 remain previously verified.
