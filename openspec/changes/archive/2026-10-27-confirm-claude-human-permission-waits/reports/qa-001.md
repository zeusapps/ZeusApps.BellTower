## Findings

### QA-001: README.md still describes the removed 15-second debounce

- Severity: warning
- Related task / requirement: 3.4 (document supported human-signal timing); attention-notifications "Completion and permission grace"
- Location: `README.md:36` at the reviewed identity (outside the developer's write ownership, as the handoff states)
- Expected / actual: README should say permission requests are provisional until a supported signal confirms a human wait, with no timing fallback. It says "other permission paths use a 15-second debounce", which is now false for Claude and for Codex sessions without a runtime and tells users to expect alerts that no longer happen.
- Reproduction: `grep -n "15-second" README.md`
- Evidence: line 36 versus `src/BellTower/Core/SessionState.cs` (`IsActive`, `HumanWaitGrace`) and probes A, A2 (no alert after 120 s)
- Recommended correction: orchestrator to apply the replacement text proposed in `evidence/implementation-001.md`, "Proposed planning changes", item 3 (it is accurate against the probes), or an equivalent edit.
- Relationship: tracks the developer-reported outstanding item; no ledger ID

### QA-002: Doctor reports native-confirmed Codex permission waits as provisional

- Severity: suggestion
- Related task / requirement: 3.1 (honest confirmation coverage)
- Location: `src/BellTower/Diagnostics/ConfirmationCoverageReporter.cs`, `Count` (wait counts read from the persisted snapshot)
- Expected / actual: `waits.confirmed/provisional/unverified/ambiguous` is meant to distinguish confirmed human waits. Codex native confirmation is transient (`NativePermissionPending` is `JsonIgnore`), so a Codex wait that the owning runtime currently confirms (probe H: `attn=True`) is persisted with `Confirmation=Provisional`. Doctor therefore always shows `confirmed: 0` for Codex and counts such waits as provisional, understating a live human wait. No false confirmation is claimed, so this is an under-report only.
- Reproduction: probe H in the [output](../evidence/qa-001-reducer-probe-output.txt) (reason Permission, attention true, wait still `Provisional`); doctor reads the persisted `StateStore` only.
- Evidence: [probe source](../evidence/qa-001-reducer-probe-source.cs.txt)
- Recommended correction: either document in the doctor string that Codex runtime confirmation is not persisted and counts only appear as provisional, or let the Codex report use the pump's verified status. Optional.
- Relationship: none

### QA-003: Unattributed prompt handling has two unreachable-evidence edges

- Severity: suggestion
- Related task / requirement: 2.3, 2.4
- Location: `src/BellTower/Core/SessionReducer.cs` `IsStale` and `ConfirmPrompt` (30 s `StaleConfirmationWindow`)
- Expected / actual: (a) A genuine `permission_prompt` with no preceding PermissionRequest for the current tool is dropped if any question or permission wait resolved in the previous 30 s (probe K: prompt 10 s after an unrelated resolution creates no wait and no alert). (b) An unattributed late prompt from an already-resolved wait is assigned to a newer provisional request in the same turn, because the notification carries no tool fields (design Decision 2 accepts this class of ambiguity). Both are inherent to Claude's unattributed notification and the 30 s window is a documented Bell Tower constant, but neither trade-off is stated in `docs/architecture.md`, which only says late prompts are ignored.
- Reproduction: probe K (edge a); edge b by reasoning from `ConfirmPrompt` (scope-based match when unattributed), not separately executed.
- Evidence: [probe output](../evidence/qa-001-reducer-probe-output.txt), section K
- Recommended correction: add one sentence to `docs/architecture.md` naming both edges, or confirm acceptance. No code change required by the specs.
- Relationship: none

## Assessment and limitations

Acceptance covered by executed fixtures: every scenario in both delta specs for Claude and Codex and a mixed Claude/Codex pair, except those that need live providers. The 919-test suite, Release build and format check pass; independent probes reproduce the developer's key outcomes (auto approval silent beyond 15 s, Claude prompt eligible on arrival, Codex 5 s native grace and negative suppression, no resurrection, silent restart, legacy-to-unverified, unknown-field round trip, the AskUserQuestion field bug, question-plus-permission ambiguity, Codex Default-mode rejection clearing at Stop). The failing-first regression for 2A.1 was reported by the developer and not re-run against baseline code.

Developer-reported behavior change (not decided here): Codex sessions without a verified owning runtime never raise permission attention. It is reported honestly in the handoff, matrix (`unverified`, not `restricted`), doctor and docs. User impact: any Codex session started `--no-daemon`, resumed or remote, and any managed session whose runtime status read fails or times out at the moment of a human approval, gives no chip, sound, reminder or escalation for a real approval; previously a 15 s fallback alerted (with false positives on slow automatic review). Claude is unaffected. Per AGENTS.md this is open release work until a signal, restriction proof or decision exists.

Not performed or limited: live auto-versus-human acceptance (3.4, 4.1) for both clients; installed Claude Code or Codex execution; the real Codex pump and websocket path (covered only by the suite's fake runtimes); Codex `request_user_input_async`; Claude permission modes other than auto and default; probe captures in 2A.5 were not re-captured and the developer notes their PostToolUse responses are unattributed. Tasks 2A.5, 3.4, 4.1 and 4.2 remain partial as the developer reported. The identity ledger and findings file were not touched. The scratch probe project lives in the session scratchpad, outside the repository; a copy of its source is the retained evidence file.
