New tasks:

- 2.6: `SessionState.ConfirmationSignalUnavailable` (transient, set by the provider adapter), `UnverifiedGrace` (15 s), `UnverifiedSince`, `PossiblyWaiting(now)` in Core. It applies to any provider whose adapter flags the session; the Codex pump flags Codex sessions with no verified runtime, a failed or null status read, or a stale status (a verified negative status is a supported signal and is not flagged). The chip text is `AlertPolicy.UnverifiedText` ("possibly waiting for approval"); `SessionViewFactory` shows it only when nothing is actionable and the episode is not dismissed; `ChipView.Unverified` adds a tooltip; the overview row shows it. It is outside `RequiresAttention` and `EffectiveConfirmation` (stays Provisional), so no sound, reminder or escalation eligibility, and it is never labelled confirmed. It clears with the wait (correlated resolution, stop, end, dismissal) and is replaced by the ordinary chip on confirmation. Doctor `confirmationCoverage` policy/status, `DiagnosticsReporter` Codex `ApprovalResolution`, `CapabilityMatrix` rows, `docs/{architecture,compatibility,installation,follow-ups}.md` and README now describe a supported unverified fallback; the confirmed-signal gap stays recorded as unverified (not a restriction).
- 2A.6: `SessionState.HeldPrompt` (id, time, delay; additive, copied by the causal reducer, cleared with receipts at prompt/stop/interrupt/end/replacement). An ambiguous question-plus-permission prompt is held; when the question resolves, exactly one unconfirmed permission old enough to be the source is confirmed (`ConfirmedAt` = prompt time, so it is eligible at once); zero or several confirm nothing. A permission too young to be the source is excluded up front, so the prompt confirms the question and nothing is held.

## Decisions and deviations to review

1. Transient `NativePermissionPending == true` still counts as active for live presentation (a bridge until the stored confirmation lands one tick later, and because ~25 existing tests set the flag directly). Reducer decisions never read it, which is what fixes the divergence. If you want the flag strictly freshness/suppression only, those tests need the stored confirmation helper instead.
2. The 2 s racing window, the 15 s unverified grace (user decision) and gating on the 5 s floor are Bell Tower constants, not provider contracts.
3. Back-dating restored Codex waits means a restored wait shows its confirmed chip immediately after restart (silent), rather than 5 s after the first report.
4. On an outdated ingress image, question-tool approval hooks are not marked `QuestionTool`; the question still stays one question in the field sequence (the permission-shaped wait shares the question's fingerprint and resolves with it), and doctor asks for "rerun setup". A legacy PermissionRequest with no `tool_input` would be indistinguishable from a prompt (Claude always sends it).
5. Claude sessions are never flagged signal-unavailable; if a user disables `permission_prompt` hooks, a Claude request stays silent and unmarked (unverified; not detected by doctor).
6. Touched deferred areas: the `CaptureConsumer` evidence write is now exception-guarded and the signal label unchanged (adjacent to ANALYSIS-006's guard item); `ConfirmationCoverageReporter` still counts raw `Confirmation` (QA-002 unchanged). ANALYSIS-004, -005, -007 and QA-003 untouched.

## Rollback note

An older tray ignores `heldPrompt`, `adapterRevision` and `runtimeApproval`; it would treat a pump runtime-approval observation as a bare Permission with no fingerprint (a provisional wait). Setup refresh is the supported upgrade path.
