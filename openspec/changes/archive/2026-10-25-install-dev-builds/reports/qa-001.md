## Findings

### QA-001: `-Legacy` can retire a real stable payload

- Severity: warning
- Related task / requirement: 4.2; spec "Retiring dev payloads" ("Stable payloads SHALL never be retired by this procedure"); developer decision 1
- Location: `scripts/install-dev.ps1` lines 208 to 211 (reviewed identity above)
- Expected / actual: Expected a stable payload is never removed. Actual: the only guard is `Parse($Version) -le $installation.EffectiveVersion()`. A stable payload newer than the selected build's base is accepted when `-Legacy` is named. Stable and unmarked legacy payloads look the same, so the guard only holds while the stable payloads are all older than the selection.
- Reproduction: disposable installation selecting stable 0.1.8, copy the real stable 0.1.9 payload into `versions\0.1.9`, run `install-dev.ps1 -Action Retire -Version 0.1.9` (refused), then add `-Legacy` (removed, record written). This state occurs for real after a stable update is recovered or rolled back to an older selection, or when a dev build is made from a branch whose base is older than an installed stable.
- Evidence: [cycle 4](../evidence/qa-001-cycle-4-rollback-retire.txt), section "Retire stable 0.1.9 WITH -Legacy".
- Recommended correction: Judgement on decision 1: the heuristic is better than nothing but does not satisfy the requirement. Restrict `-Legacy` to an explicit allow-list (the two known trial versions 0.1.9 and 0.1.10), or additionally refuse any payload whose `release.json` and file inventory match a published release hash, or require typing the exact version plus a second confirmation. Add a test where a real stable payload above the base is refused. State the residual risk in the docs.
- Relationship: new

### QA-002: Packaging deletes the Release ingress output and breaks the next `dotnet test --no-build`

- Severity: suggestion
- Related task / requirement: 3.1, 3.2, 6.1; the developer's uncaptured full-suite failure
- Location: `scripts/package.ps1` ingress `dotnet publish src/BellTower.Ingress/BellTower.Ingress.csproj -c Release -r win-x64 ...` (the same publish exists at baseline, so this is probably pre-existing)
- Expected / actual: Expected the documented sequence "package, then test" to work. Actual: after a package build, `src/BellTower.Ingress/bin/Release/net10.0-windows/win-x64/bell-tower-ingress.exe` is gone and two `CaptureTests.ExecutableCapturesUnicodeAndFailsNeutralWithoutLeakingInput` cases (claude, codex) fail with "cannot find the file specified". A plain `dotnet build -c Release --no-restore` restores the file and the suite passes 744/744.
- Reproduction: `pwsh -NoProfile -File scripts/package.ps1 -FixtureVersion 0.1.9 -OutputDirectory artifacts/update-acceptance/qa-001-stable`, then `dotnet test -c Release --no-build --no-restore` (fails), then `dotnet build -c Release --no-restore` and test again (passes). Three runs before packaging all passed.
- Evidence: [run4](../evidence/qa-001-test-run4.txt), [run5](../evidence/qa-001-test-run5.txt), [run6](../evidence/qa-001-test-run6-after-rebuild.txt). This very likely is the developer's single unexplained failure (they built a real dev package during the same session); I did not reproduce a failure without packaging in 3 plus 1 clean runs.
- Recommended correction: Tell maintainers, in `docs/development.md` and the skill build step, to run `dotnet build -c Release` after `package.ps1`, or make the script publish the ingress to an intermediate output that does not share `bin/Release`. Optionally note in `tasks.md` evidence that the flake is explained.
- Relationship: new

## Assessment and limitations

Accepted by independent execution: dev marker on version output, `update --status` and `doctor`; stable unchanged; reserved range both directions and next-number choice; effective-version staging of stable 0.1.9 over dev 0.1.9001; Preflight with no mutation; Switch, Rollback, and refusals on selection and payload drift; Retire refusals for selected, previous and leased payloads, plus successful dev and legacy retirement; vswhere discovery in a plain shell; skill byte parity and safety content; build, format and node checks; full suite 744/744 on 4 clean runs.

Not accepted: the requirement that Retire never removes a stable payload (QA-001, warning). The orchestrator should decide between an allow-list and a hash-based stable check before tick-off.

Decisions judged: (1) `-Legacy` guard is insufficient, see QA-001. (2) Restart only a previously running tray is acceptable, with QA-004. (3) Build-input dirty flag is acceptable with QA-003. (4) `EnsureStable` is acceptable; Stage and EnsureStable refusals were exercised, the GitHub client path only by source. I also noted `UpdateDiscovery.Hint` catches only `IOException` and `JsonException`, so an `InvalidDataException` from `EnsureStable` on a hand-edited cache would propagate; the unchanged `Validate` call had the same shape, so I do not count it as a regression.

Not performed: on-screen tray tooltip and Sessions title; clean-tree dev package; live owner-drift refusal; activation of 0.1.9 over a dev selection (Stage only); live Codex skill discovery; read-only Preflight on the maintainer installation (unneeded). Unexplained parity gaps: none found; the skill is shared and identical. `tasks.md` was not edited and no ledger was touched.

Unexpected writes: the full-suite and packaging runs wrote ignored build output; the packaging run removed and then I rebuilt the Release ingress exe. No product, ledger or maintainer files were changed.
