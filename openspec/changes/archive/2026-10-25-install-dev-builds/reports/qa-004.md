## Findings

### QA-200: Cleanup hook-maintenance regression test fails during workspace teardown

- Severity: warning
- Related task / requirement: 4.3 and 6.1, generated Claude/Codex hooks during Cleanup.
- Location: `tests/BellTower.Tests/Updates/HookMaintenanceTests.cs:80`; teardown at `tests/BellTower.Tests/Testing/TestWorkspace.cs:41` at target `diff=41ba2dbe9660`.
- Expected / actual: the test should complete its generated-hook assertions, release the slow Cleanup phase, await Cleanup, and remove its fixture. Actual: the full suite and an isolated rerun both fail when recursive workspace deletion encounters a locked `0.1.9001.lock`; the teardown exception is the only isolated failure surfaced, so it may hide an earlier hook assertion and leaves the primary hook outcome unknown.
- Reproduction: `dotnet test -c Release --no-build --no-restore --filter FullyQualifiedName~HookMaintenanceTests.CleanupHashingDoesNotBlockGeneratedClaudeCodexOrMixedLegacyHooks`.
- Evidence: isolated run failed with `System.IO.IOException: The process cannot access the file '0.1.9001.lock' because it is being used by another process`, from `TestWorkspace.Dispose()` line 41 after the test at line 80. The other two full-suite failures passed on isolated rerun; their full-suite results remain recorded above.
- Recommended correction: preserve the primary generated-hook result and ensure all cleanup/lease work has completed before disposing the workspace; add evidence that no QA-created process still holds the fixture lock. This is a test reliability finding, not a claim that production cleanup failed.
- Relationship: new.

### QA-201: the final tray-start drain occurs after selection mutation

- Severity: warning
- Related task / requirement: design §7; 4.3; 6.1; QA-150/ANALYSIS-150 delayed-start correction.
- Location: `scripts/install-dev.ps1:453-467` and `:517-525` at target `diff=41ba2dbe9660`.
- Expected / actual: all matching tray starts, including children created during an expired-marker interval, must be drained before pointer/state mutation. Actual ordering reaches the `switch-before-selection` barrier and writes `current.json` at line 465 before renewing the owned markers and performing the final tray-start drain at lines 518-521. A delayed old-order child that passes its start gate during the barrier can therefore be discovered only after selection has changed.
- Reproduction: source-order evidence; the prepared delayed-child harness describes the intended disposable runtime probe, but it was not compiled or run in QA 004. Do not treat the source inspection as a functional pass.
- Evidence: initial drain is at line 431 before candidate copy/hash and the barrier at line 453; pointer mutation is at line 465; renewal and final drain occur afterward. [Design §7](../design.md) requires drain before shared-state/pointer mutation.
- Recommended correction: renew exact owned pending/restart records and drain all verified installation tray invocations immediately before the selection/state mutation boundary, then retain a final drain before reservation release.
- Relationship: new; relates to QA-150 but is a distinct delayed-start timing gap.

### QA-202: recovery accepts a restart record with mismatched ownership fields

- Severity: warning
- Related task / requirement: design §7 foreign-marker preservation and matching dead-owner recovery; 4.3.
- Location: `scripts/install-dev.ps1:389-392` and `:122-132` at target `diff=41ba2dbe9660`.
- Expected / actual: recovery must match the complete recorded operation identity before renewing either record. Actual: pending recovery checks root, data directory and original/target tuple, but restart recovery checks only `Id` and `Token`; `Set-OwnedRecordsFresh` also checks only those two fields before overwriting both records from the in-memory plan. A restart record with the same id/token but changed root/data/version/owner fields is therefore overwritten rather than refused with its bytes preserved.
- Reproduction: source inspection; the exact foreign-field runtime probe was not executed.
- Evidence: recovery branch at lines 385-391 compares the full pending tuple but only id/token in restart; renewal lines 127-131 repeats only id/token for each record.
- Recommended correction: validate the full operation tuple and prior-owner recovery conditions for both records before any renewal; preserve mismatched record bytes and refuse before mutation.
- Relationship: new.

### QA-203: stale tray presence is treated as an unverifiable live owner

- Severity: warning
- Related task / requirement: 4.1 Preflight and Rollback after a tray exits; design §7 verified-owner distinction.
- Location: `scripts/install-dev.ps1:86-98` at target `diff=41ba2dbe9660`.
- Expected / actual: absence of a live tray with a stale `tray.json` record should be distinguishable from a live but unverifiable owner. Actual: when `tray.json` exists, `Read-Owner` throws if `ProcessProbe.Identify(presence.Process.Pid)` no longer equals the recorded identity, without first establishing that the tray-instance object/process is still live. A stopped tray whose presence record remains can therefore prevent Preflight/Rollback from proceeding.
- Reproduction: source inspection; a native disposable start/exit/stale-presence runtime probe was not performed in QA 004.
- Evidence: `TrayHost` writes the presence record, and `Read-Owner` rejects stale identity at line 93 before classifying an ended process; there is no stale-record recovery path in this function.
- Recommended correction: use the live instance/process state to distinguish stale presence from an active owner that cannot be verified; retain conservative refusal for an actually live unknown owner.
- Relationship: new.

### QA-204: generated legacy hooks exceed the three-second budget under synthetic parallel load

- Severity: warning
- Related task / requirement: 4.3 and 6.3, generated launcher hooks and timeout investigation.
- Location: generated command path from the `0.1.9003` package; benchmark evidence at target `diff=41ba2dbe9660`.
- Expected / actual: generated legacy command samples should meet the stated sub-three-second hook budget. Actual: with 8-way synthetic benchmark parallelism, 24/25 Claude samples and 23/25 Codex samples exceeded three seconds; medians were 3310 ms and 3114 ms. No hook event failed, but completion exceeded the timeout threshold.
- Reproduction: `dotnet run --project tools/BellTower.Ingress.Bench -c Release --no-build -- artifacts/dev-builds/bell-tower-0.1.9003-win-x64 artifacts/qa-004-benchmark`.
- Evidence: [raw benchmark results](../evidence/qa-004-benchmark-results.json). The same benchmark recorded NativeAOT medians below 300 ms and all native samples below three seconds. Separately, the held-launch-gate control timed out all four generated legacy samples while NativeAOT completed all four.
- Recommended correction: keep the generated launcher path within the published hook budget under realistic concurrency, and make the supported provider-hook migration path to NativeAOT concrete and verifiable. This synthetic benchmark does not prove the work-machine failure's cause.
- Relationship: new.

## Assessment and limitations

The fresh package, Release build, scoped format verification, JavaScript suite, NativeAOT gate-bypass control, packaged benchmark, and read-only maintainer Preflight produced reviewable evidence. The full test suite did not pass. The benchmark confirms NativeAOT is much faster than the generated legacy chain in this environment; it does not prove the user's work-machine timeout cause. NativeAOT samples pass the stated latency gates, while legacy samples under parallel synthetic load do not.

Acceptance remains incomplete. The delayed-child fixture and complete disposable Switch/Rollback/Retire cycle were not executed. Runtime probes for expired-marker drain, foreign restart-field preservation, stale tray presence, all four blocked maintenance phases, and successful authorized restart remain for the authorized QA 005 review after the next implementation/review round. No live hooks were migrated, no provider settings were changed, no authenticated provider session was used, and the maintainer tray remained running throughout read-only Preflight.

The scoped target identity matched before and after. QA wrote only its assigned report/evidence and disposable artifacts; no product source, test source, script, docs, skill, planning or ledger file was changed.
