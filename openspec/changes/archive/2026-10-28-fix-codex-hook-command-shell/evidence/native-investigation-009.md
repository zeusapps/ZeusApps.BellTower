# Native Codex cmd fallback hook probe 009

## Scope and result

This released task 2.1 probe tested whether the unchanged Codex CLI `0.164.0` could dispatch a product-generated Codex `SessionStart` command through native cmd fallback when both PowerShell install directories were unreadable inside MXC.

**Result: native Codex cmd fallback succeeded for this isolated scenario.** A fresh protocol-1 Codex capture was written through the 0.1.9018 ingress helper under a data path containing spaces, apostrophe, Unicode, `%BELLTOWER_HOOK_PROBE_EXPANSION%`, and `! & ^ ()`. The capture's `HookShell` identity matched its sole `cmd.exe` ancestor. The helper's observed working directory matched the isolated project. No Bash fallback claim is made.

The source tree remained frozen at the previously recorded implementation identity (`aadbfb3`, tracked diff `959d86f7d758`, untracked source/test set `3/cce5a39616ce`). This phase changed only this report and ignored `artifacts/codex-hook-fallback-009/` scratch.

## Native dispatch and capture

The direct native Codex sandbox/session command exited 0 in 816 ms. Its stdout contained only the expected synthetic-session output and Codex informational messages; stderr contained the CLI's `Reading additional input from stdin...` hint. The loopback server received one `POST /v1/responses` request from `<loopback>`; no non-loopback request was recorded.

Exactly one fresh spool file appeared at the special-character data root. `BellTower.Protocol.CaptureProtocol.Decode` decoded it successfully and validated protocol version 1. The decoded observation provider was `codex` with registration source `startup`; its directory and attachment directory both matched the isolated project. `HookShell` was present, and its PID/start-time identity exactly matched the sole `cmd.exe` entry in the envelope's process ancestors. This identifies the actual shell process that launched the ingress helper rather than inferring a shell from the configured command string.

The capture SHA-256 is `13df2846296c98bcd94a69aff40856d9c80ebc2df930a5b3d344a0e4b285e651`. The raw stdout, stderr, loopback request metadata, profile, hooks configuration, generated command, and protocol capture remain in ignored scratch for independent review. All launched native Codex and endpoint processes exited; a PID/start-time/executable-verified cleanup check found neither process remaining.

## Attempt accounting and limits

The first native invocation used a private `CODEX_HOME` config where the permission-profile table had been overwritten by the session config; it exited 1 before any endpoint request or capture. Its exact stderr was not retained, so this is classified as a harness/config setup failure, not a product or MXC failure. A subsequent controller preflight also caught a missing scratch project directory before Codex started. The final attempt passed a complete preflight: all owned and executable paths existed, the helper/native hashes matched, the combined TOML profile and fake-provider configuration parsed, the loopback URL was validated, and the exact builder command matched its expected serialization.

This evidence establishes native Codex cmd fallback hook delivery for the tested MXC mode and special-character helper/data paths. It does not test native Bash fallback, Claude behavior, or external-host executor metadata. The user's previously recorded Claude/Codex live acceptance remains separate evidence; no parity exception is proposed.
