# Native Codex MXC fallback route investigation 006

## Scope and result

This is a source-only follow-up for task 2.1. It checks whether the Codex `0.164.0` MXC debug-sandbox path can deny reads to the PowerShell discovery locations around an unchanged native Codex child without changing host ACLs or installing an OS component. No CLI, sandbox, profile, or child process was run; no configuration or host state was changed.

**Result: a supported process-local policy route exists in the pinned source.** MXC translates the selected permission profile to native denied paths and explicitly disables DACL mutation. This supports a follow-up native probe, subject to the runtime's native deny-path capability. Source review alone does not establish that the installed executable contains the required helper, that the native capability is available, or that PowerShell path discovery inside the sandbox observes the denied files as absent. Those checks require the isolated invocation and a native hook capture; they are not claimed here.

## Pinned implementation trace

The source reviewed is the official [`rust-v0.164.0` tag](https://github.com/openai/codex/tree/rust-v0.164.0), matching the installed Codex CLI version recorded for this change.

1. **The debug-sandbox command routes an unchanged child through MXC.** The pinned CLI `debug_sandbox.rs` accepts the child argv and permission-profile selection. When the sandbox state specifies MXC, it preserves that backend; the Windows path transforms the supplied command through `SandboxManager` with `SandboxType::WindowsMxc`, then starts the transformed wrapper. See [`debug_sandbox.rs`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/cli/src/debug_sandbox.rs#L280-L307) and [the Windows MXC branch](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/cli/src/debug_sandbox.rs#L459-L503). The CLI help and supported invocation syntax were checked separately by the orchestrator; this investigation did not execute them.

2. **The 0.164.0 sandbox manager carries the helper path in the Codex executable.** The pinned manager calls `codex_mxc_sandbox::create_command_args`, passing the effective permission profile, child argv, working directory, and environment, and wraps the command with the Codex executable path. The MXC crate is a workspace crate and a dependency of the sandboxing layer. See [`sandboxing/src/manager.rs`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/sandboxing/src/manager.rs#L365-L411), [the workspace crate entry](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/Cargo.toml#L80-L96), and [`mxc-sandbox/Cargo.toml`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/mxc-sandbox/Cargo.toml#L1-L29). This proves the helper is part of the pinned source build path, not that this particular installed binary exposes it at runtime.

3. **Explicit deny-read entries reach the native policy.** `mxc-sandbox/src/policy.rs` resolves Windows deny-read entries into concrete paths. It removes denied identities from read and write grants before and after volume expansion/normalization, so a broader read grant such as `C:\Windows\System32` does not re-open an explicitly denied PowerShell subpath. The resulting `ContainerPolicy` carries `denied_paths`. See [`policy.rs`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/mxc-sandbox/src/policy.rs#L157-L221) and [the native request construction](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/mxc-sandbox/src/policy.rs#L266-L312).

4. **The native path does not fall back to host ACL mutation.** The generated native policy sets `FallbackPolicy { allow_dacl_mutation: false }`. Before launch, the helper checks `BaseContainerRunner::supports_native_denied_paths()` when denied paths are present and returns an error if that capability is unavailable. The MXC README also states that the backend does not edit host ACLs, create sandbox users, run setup, or request elevation; unsupported native deny-path capability fails before launch. See [policy construction](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/mxc-sandbox/src/policy.rs#L276-L305), [`native.rs`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/mxc-sandbox/src/native.rs#L15-L36), and the [pinned MXC README](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/mxc-sandbox/README.md#L0-L18).

5. **The policy can cover PowerShell's fixed fallback locations.** The resolver documented in investigation 005 checks `PATH`, then PowerShell 7 at `C:\Program Files\PowerShell\7\pwsh.exe` and Windows PowerShell at `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`. The MXC policy accepts explicit deny-read paths and gives denies precedence over ordinary read roots and platform read roots. A prospective profile can therefore keep the system directory readable for `cmd.exe` and required DLLs while denying the PowerShell locations. The exact selected executable paths and any PATH-resolved PowerShell candidates still need read-only inventory and confirmation in the probe plan before launch.

## Required validation and limits

- MXC's general availability probe checks PSEC creation/startup, not native filesystem-deny capability. The helper separately checks `supports_native_denied_paths()` when it receives a denied-path policy. A denial-policy command should fail closed if that feature is absent; do not infer deny support from the general availability bit or Windows version. See [`availability.rs`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/mxc-sandbox/src/availability.rs#L17-L51) and [`native.rs`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/mxc-sandbox/src/native.rs#L15-L29).
- A future probe must set a fresh isolated `CODEX_HOME` before the native process starts, use the directly resolved native executable, and keep its project/data/profile within the validated scratch root. It must preserve the MXC sandbox state across the nested Codex launch and capture which shell the child actually selected. The exact policy entries and paths require root review before execution.
- Source does not prove how `which::which` and filesystem metadata checks behave when PowerShell executable paths are denied by PSEC. A selected-shell value reported as PowerShell followed by a blocked launch would not prove cmd fallback. Native cmd selection and a valid durable capture remain the acceptance criteria.
- The pinned MXC README says the profile policy is applied to the child process and the native job/policy lasts through workload completion. This is the process-isolated behavior relevant here; it is not an OS-level sandbox setup or ACL change.
- No complete native hook command with the required spaces, apostrophe, Unicode, `%NAME%`, `!&^()` path controls was run. No task acceptance is claimed yet.
- Correction to investigation 005: the later root runtime audit found one WSL distribution registered and none running. Investigation 005's statement that none was registered was inaccurate; this does not change the source conclusion or establish WSL as a route.

The supported MXC policy path is a viable next probe candidate, not native fallback acceptance. No provider restriction or task exception is inferred.
