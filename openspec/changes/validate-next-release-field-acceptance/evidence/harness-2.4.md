## Notes

- faults-and-rollback, what is real and what is modeled: the 0.1.9 and candidate installations, their ingress images, trays, update transaction, spool, state and identity files are the real packaged ones under disposable roots; the provider processes are the harness's fake agents. The approval-flow tool hooks (PreToolUse, PermissionRequest, PostToolUse) are modeled payloads in the documented shapes (no native sequence capture exists for these commands), and the Codex 0.1.9 hooks run through the labeled modeled cmd fallback (the 0.1.9 Codex command only parses in the command shell). The rollback is a manual selection of the retained 0.1.9 payload (the documented manual restore of `current.json`, with the product's own capture and attachment-health compatibility check); the product has no rollback command, and the update coordinator's recovery performs the same two steps. Shuffled and duplicate delivery are injected into the capture spool while the tray is stopped (file names reordered, a capture file copied under another name); the envelopes themselves are untouched, so ordering and duplicate suppression are the product's.
- faults-and-rollback, rollback effects recorded as expected results (ANALYSIS-186, no product change): the identity data stays compatible (the `retained` checkout source and the additive `checkoutWork` field read back through 0.1.9, which keeps unknown fields), but the behavior is one-way. The first 0.1.9 pass over a retained conversation records the launch checkout (0.1.9 knows no retained input), so upgrading again does not restore the retained checkout; a conversation 0.1.9 already moved to the launch checkout before an upgrade has lost the evidence, and stays there until new work or a pin. The checks record the source before the rollback, right after it (before any 0.1.9 tray pass), after 0.1.9's passes and after the second upgrade.
- faults-and-rollback, 0.1.9 state is read only through 0.1.9's own commands (`list`, `doctor`, `statusline`) and the raw files; no in-process surface or policy of the candidate judges 0.1.9 state (ANALYSIS-162). `ConversationSurfaces` now refuses an installation that is not the candidate.
- faults-and-rollback, exposure: every hook goes through `AgentSession.Hook` (so a hook-started tray is noted by the instance's exposure guard), every tray-down phase follows the user's Exit (the recorded user stop keeps hooks from starting a tray in the real profile environment), and each group fails a check if a hook started a tray or a shared-backend Codex ran.
- Commands run through the installed launcher (sandbox-relative): `install\bell-tower.exe --version --data-dir <sandbox>\data`; `install\bell-tower.exe setup --clients both --apply --home <sandbox>\home --data-dir <sandbox>\data`; `install\bell-tower.exe start --silent --data-dir <sandbox>\data`; `install\bell-tower.exe doctor --data-dir <sandbox>\data`; `install\bell-tower.exe list --data-dir <sandbox>\data`; `install\bell-tower.exe setup --host-bridge --apply --home <sandbox>\home --data-dir <sandbox>\data`; `install\bell-tower.exe exit --data-dir <sandbox>\data`; `install\bell-tower.exe statusline --provider claude --no-color --data-dir <sandbox>\data`; `install\bell-tower.exe statusline --provider codex --no-color --data-dir <sandbox>\data`
