## Findings

### QA-240: real-environment-exposure detail states no shared-backend Codex ran, but Codex groups run one

- Severity: suggestion
- Related task / requirement: task 2.4, ANALYSIS-122 (exposure guard)
- Location: `tools/BellTower.FieldAcceptance/Scenarios/FaultGroupRun.cs:732-733` at 02d4f56 plus working tree
- Expected / actual: the check asserts `SharedBackendCodexUsed == conversations.Any(UsesSharedBackend)`, and the Codex and mixed groups include the `shared` launch kind (`app-server` fake agent), so the instance does run one modeled shared-backend Codex. The reported detail says "no shared-backend Codex ran". The assertion is right (guard sticky mark equals expectation, and no hook started a tray, so the two never combine); the text contradicts what ran and the evidence in `harness-2.4.md` repeats it.
- Reproduction: read `final/real-environment-exposure` in `artifacts/qa013/faults-1.md` for the codex group.
- Evidence: source above; runs 1 and 2 pass.
- Recommended correction: reword to "the modeled shared-backend Codex ran only with no hook-started tray in the same instance" (or state both halves of the guard).
- Relationship: none.

### QA-241: expected-failure checks pass for any loss, not for the documented cause

- Severity: suggestion
- Related task / requirement: task 2.4 user decision (plain `codex --no-daemon` documented as an expected failure), ledger F2, F4, U1
- Location: `FaultGroupRun.cs:311-315` and `:615-620`
- Expected / actual: the checks pass when the plain-kind hooks are not applied (`expectLoss ? !ok : ok`). The documented cause is an attachment id mismatch (session on `codex-session-<hash>`, event carrying `codex-<pid>-<ticks>`), which `Diagnosis(conv)` prints but does not assert. A different cause of lost delivery for that kind (a tray or spool problem) would still count as the expected failure.
- Reproduction: inspect the checks; make the hooks for that kind fail for another reason and the expected-failure check still reports "observed".
- Evidence: source inspection only; the other launch kinds in the same run do apply hooks, which bounds the risk but does not remove it.
- Recommended correction: when `expectLoss`, also require `State(conv).AttachmentId` to start with `codex-session-` and `LastEventAttachmentId` to differ from it, so the expected failure is tied to its stated reason.
- Relationship: none.

### QA-242: `--scenario all` failed once on packaged-hook-benchmark (task 2.3 scenario)

- Severity: warning
- Related task / requirement: task 2.3 gate, task 3.4 (release evidence), assignment run of `--scenario all`
- Location: `tools/BellTower.FieldAcceptance/Scenarios/PackagedHookBenchmarkScenario.cs` (event-counts-exact and durable-within-3s checks), run in `all` after `five-conversations`
- Expected / actual: DEV-010 recorded `all` at 279/281 (exit 3). In this review the single `all` run gave 275/281, exit 1: `packaged-hook-benchmark/claude/event-counts-exact`, `codex/event-counts-exact`, `mixed/event-counts-exact` and `claude/durable-within-3s`. Each detail shows every accepted hook durable and delivered but "captures whose writer could not be read before the tray consumed them: 1" (Claude one capture unmatched, 119 of 121 matched, so a gate on durability and a count mismatch). The faults-and-rollback part of the same run passed 120/120, and the benchmark alone passed 38/38 right after.
- Reproduction: `scripts/field-acceptance.ps1 -Scenario all` (not reproduced in a second `all`; only one was assigned). Output in `artifacts/qa013/all.txt`.
- Evidence: `artifacts/qa013/all.txt`; `artifacts/qa013/bench-alone.txt` (38/38). The machine was otherwise idle apart from the user's live trays.
- Recommended correction: the matching of a capture to its hook depends on reading its writer before the tray consumes it; a consumed-before-read capture should either be matched by envelope id from the tray journal or reported as inconclusive instead of failing the exact-count gate. Task 3.4 should take the `all` verdict on the release package with this flake characterized.
- Relationship: related to QA-165 and ANALYSIS-160 history (task 2.3); not a 2.4 defect.

## Assessment and limitations

- Task 2.4 behavior is exercised for Claude Code, Codex and mixed on installed packaged binaries: faults-and-rollback passed 132/132 twice with `-RebuildCandidate` and 120/120 inside `all`; the harness units (102) and the full suite (2238/2238) pass. - Check sensitivity was judged by reading each condition and, for the expected failures, the report logic. I did not mutate the product or harness (reviewers do not edit code), so "the check would fail if the behavior broke" is established by condition analysis, not by an injected regression. The earlier developer-reported pre-decision run (128/132 with real failures) shows the per-kind checks can fail.
- Not covered: Codex launched through the owned `--remote` runtime; whether a running Codex reloads rewritten hook commands mid-session (both stated as unverified in the implementation evidence); live Claude Code or Codex sessions; the manual `current.json` selection is the accepted stand-in for a rollback command that does not exist.

- QA-242 means `--scenario all` has not given a green verdict in this review; the one failing scenario belongs to task 2.3 and passes alone.
- Unexpected writes: none outside ignored `artifacts/`. Leftover processes: the unit-test tray PID 27984 created by the full-suite run was stopped; the user's trays (8060, 28388) were not touched.
