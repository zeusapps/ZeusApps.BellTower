### ANALYSIS-060: With the declarations at 0.1.9, the real-baseline upgrade and rollback harness cannot build a distinct candidate before task 4.4

- Severity: warning
- Related task / requirement: 2.1, 2.4, 3.3, 3.4, 4.4; release-readiness "baseline 0.1.9 upgrade and rollback"; regression from the ANALYSIS-040 option (a) edit to tasks 1.3/4.4 and design section 1
- Locations: `scripts/update-acceptance.ps1:6,13-14` (the candidate is `package.ps1` at the `Directory.Build.props` version, then `Smoke <baseline> bell-tower-<version>-win-x64.zip`); `tools/BellTower.Smoke/Program.cs:52` (`Assert(original != offer.Version, "Acceptance requires distinct compiled versions.")`); `src/BellTower/Updates/UpdateTransaction.cs:45-47` (offer `<=` selected effective version is refused), `:60-61` (`versions/<offer>` collision); `scripts/package.ps1:69-72,109` (`-FixtureVersion` is restricted to `artifacts/update-acceptance/` and skips the extension version agreement); [tasks.md](../tasks.md) 1.3, 2.1, 2.4, 3.3, 3.4 and 4.4; [design.md](../design.md) section 1
- Observation: tasks 2.1, 2.4 and 3.3 need an upgrade from the real published 0.1.9 to the candidate, and a rollback and coexistence with it. Task 3.4 runs `scripts/update-acceptance.ps1` and the new harness. All of these come before 4.4, which now owns the version synchronization. Until then the standard candidate package is 0.1.9. Smoke and `Stage` refuse it against a 0.1.9 baseline, and its payload would collide with `versions/0.1.9`. The default `update-acceptance.ps1` run, with a 0.1.7 fixture baseline, still passes, but it is not the real-baseline evidence the spec requires. The plan does not say which version the pre-4.4 candidate carries. It also does not say whether the upgrade, rollback and acceptance evidence must be rerun on the synchronized 0.1.11 build that 4.4 calls "one verified immutable release candidate". Evidence gathered on a build with another version or build path would not cover the published bytes. ANALYSIS-040 did not raise this.
- Proposed improvement and benefit: an orchestrator planning decision to record in tasks 2.1, 3.4 and 4.4 (and design section 1). One option: the harness builds its pre-4.4 candidate with `-FixtureVersion 0.1.11` under `artifacts/update-acceptance/`, labeled as a fixture-version candidate. Task 4.4 then reruns `update-acceptance.ps1 -BaselineArchive <real 0.1.9>` and the harness upgrade and rollback on the synchronized release-commit package before handoff. Another option: run the real-baseline parts of 2.1, 2.4 and 3.3 only after the 4.4 synchronization, so they run on the release-commit build. Either keeps dev builds for live checks at base 0.1.9, as the user decided. Either also makes clear which build each piece of evidence covers.
- Behavior-preservation risks: none to product code. `-FixtureVersion` skips the extension/application version agreement (`package.ps1:109`), so it cannot stand in for the 4.4 agreement check. Fixture-version candidates must not be written to `artifacts/releases` or reported as the release candidate.
- Evidence type: source observation
- Verification / measurement plan: a text check that 2.1, 3.4 and 4.4 name the candidate version used before and after synchronization and the rerun on the release-commit build. When the harness exists, its log shows `old 0.1.9 -> new 0.1.11` from the Smoke "PACKAGED UPDATE PASSED" line on the synchronized build.
- Relationship: regression from the ANALYSIS-040 fix (option (a))
