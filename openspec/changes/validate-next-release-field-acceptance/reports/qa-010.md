## Findings

### QA-180: The harness reports PASSED with exit 0 while a release-gate parity item is unfinished

- Severity: warning
- Related task / requirement: tasks.md 2.2; ANALYSIS-164; AGENTS.md "Treat unexplained parity gaps as incomplete release work"
- Location: `tools/BellTower.FieldAcceptance/Evidence/RunReport.cs` line 38 (`Passed`), `tools/BellTower.FieldAcceptance/Program.cs` line 320 (headline), `tests/BellTower.Tests/FieldAcceptance/SurfaceAndGateTests.cs` line 45 (`Assert.True(report.Passed)` with one unfinished item)
- Expected / actual: Unfinished items are never counted as passes, which holds in the counts (84/86). The run verdict does not distinguish them: `Passed` is true when every check passed or is unfinished, so the console prints `FIELD ACCEPTANCE PASSED: 84/86 checks passed, 2 unfinished parity items`, `result.md` starts with `Result: **PASSED**`, and `scripts/field-acceptance.ps1` exits 0. A reader or script that gates on the verdict or the exit code reads the Codex native-name parity gap as acceptance. The test pins this behavior as intended.
- Reproduction: `./scripts/field-acceptance.ps1 -Scenario five-conversations`; read the last console line and the exit code.
- Evidence: this review's `five-conversations` and `--scenario all` runs (summary lines quoted above); [harness-2.2](../evidence/harness-2.2.md) line 3 "Result: **PASSED** (84 of 86 ... 2 unfinished parity items, not passes)".
- Recommended correction: report a distinct verdict when `UnfinishedItems > 0` (for example "PASSED WITH UNFINISHED PARITY ITEMS", and a documented, non-zero or separately testable exit status or a `-AllowUnfinished` switch the release gate must set explicitly), and update the unit test and the harness-2.2 header text accordingly. The release gate (4.x) should list the unfinished items by name regardless.
- Relationship: new, related to ANALYSIS-164 and the user decision of 2026-11-25.

### QA-181: Retained checkout is not kept when the branch switch also removes the change folder that verified it, unless the worktree is named for the ticket

- Severity: warning
- Related task / requirement: tasks.md 2.8; ANALYSIS-163; delta spec "Verified checkout changes branch after its work is cleared"
- Location: `src/BellTower/Core/CheckoutPolicy.cs` `Choose` (the retained tier applies only when `Candidates` is empty and the stored source is already `Retained`); `src/BellTower/Sessions/IdentityResolver.cs` lines 31 to 45 (retention is marked only after the same refresh both chose `UniqueWork` and cleared the work)
- Expected / actual: Expected, per the spec, the conversation keeps the worktree it was verified in after a branch change in that worktree, for either provider. Actual: unique-work verification is `Directory.Exists(<worktree>/openspec/changes/<work>)` unless the worktree directory is named for the work's ticket. When the work's change folder is committed on the old branch and the worktree is switched to a branch without it, the folder disappears at the same time as the branch changes, so in that refresh `Choose` finds no candidate and returns `launch`. The conversation then shows the launch checkout's branch, and the stale `ActiveWork` is rebound to it rather than cleared (`ApplyBranch` sees a different checkout and rebinds). The retained tier is never reached because the stored source is still `unique-work`.
- Reproduction (disposable probe, outside the repository, not committed): real Git family, worktree `alpha` (not ticket-named) holding the committed change folder; verify with one refresh; `git switch -c hotfix main` inside the worktree; refresh again. Trace for both provider rows: refresh 3 `source=launch branch=main sel=D360 work=dep-7070-fix`, still the same after two more refreshes. Control run with the worktree named `DEP-7070` (the field layout): `source=retained` after the switch and kept for later refreshes.
- Evidence: probe output summarised above. The harness and unit fixtures create change folders untracked, so a branch switch never removes them and this case is not exercised by `five-conversations` or `CheckoutResolutionTests`.
- Recommended correction: either retain the stored working checkout when the previous source was `unique-work`, the checkout is still a listed worktree and its branch changed (so the retention does not depend on the evidence surviving the switch), or record explicitly in the spec, ledger F9 and the 0.1.11 notes that retention requires the verifying change folder or the ticket-named worktree to survive the switch. Add a unit test and a harness leg with the change folder committed on the old branch and a non-ticket worktree name, for both providers.
- Relationship: new, same family as ANALYSIS-163.

### QA-182: The full test suite leaves an orphaned tray process holding `src/BellTower/bin`

- Related task / requirement: tasks.md 2.1 isolation and leftovers; implementation-007 "Process note"
- Location: unit-test tray started with `tray --data-dir artifacts/unit-tests/<id>/data --silent` from `src/BellTower/bin/Release/net10.0-windows/bell-tower.exe`
- Expected / actual: A completed `dotnet test` run leaves no process. Actual: after my single full-suite run, a `bell-tower.exe` tray (PID 39148, started during the run, its parent process already gone) was still running against the disposable unit-test data directory. DEV-007 recorded the same orphan blocking a build. It is not the user's tray and not a harness sandbox tray (the harness sweep and the production-process comparison were clean), but it keeps the Release output locked and can fail the next build.
- Reproduction: run `dotnet test -c Release --no-build --no-restore` once, then list `bell-tower.exe` processes whose command line contains `artifacts/unit-tests`.
- Evidence: process list and command line after the suite; the user's two installed tray processes were unaffected. I did not stop it (the stop was refused by the permission classifier, correctly outside my allowance for an unrequested process kill); the orchestrator should stop PID 39148 or let it exit before the next build.
- Recommended correction: find which test starts a real tray and ensure its fixture stops it (the test most likely to leave it is among the tray-hosting fixtures); add a check to the suite or the verification procedure that fails on a surviving `artifacts/unit-tests` tray.
- Relationship: new; related to the process note in implementation-007.
