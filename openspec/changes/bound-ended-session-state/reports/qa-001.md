## Findings

### QA-001: Sanitization leaves path fragments after a space and misses some roots

- Severity: warning
- Related task / requirement: 2.1; design decision 4 ("The message contains no path ... only the exception type and its bounded message, with data-directory paths replaced"); spec "bounded, sanitized reason"
- Location: `src/BellTower/IO/RefreshHealth.cs`, `PathPattern()` (the `[^\s'"<>|]*` tail) and `Describe`
- Expected / actual: A path other than the data directory should be removed from the log and `refresh-health.json`. Actual: the pattern ends at whitespace, so a path with a space keeps its tail, and roots other than `/home`, `/Users`, `/tmp`, `/var` are not matched. Observed with a scratch probe: `Access to '<drive>:\<profile dir with a space>\x.json' denied` becomes `Access to '<path> space\x.json' denied` (this leaks the part of a profile folder name after the space), and `/root/secret/a` and `/mnt/c/<dir>/b` are left intact or partly intact. The data directory itself is correctly replaced even with spaces, because it is replaced first by exact text.
- Reproduction: call `RefreshHealth.Describe(new IOException("Access to '<drive>:\\<profile dir with a space>\\x.json' denied"), "D:\\data")`.
- Evidence: scratch probe in a copy (removed); the existing test `ReasonAndRecordNeverContainTheDataDirectoryOrOtherPathsAndAreBounded` uses only space-free paths.
- Recommended correction: Treat a quoted segment as a unit (replace `'...'` and `"..."` contents that look like a path) and extend the pattern to continue over spaces up to the next quote, or reduce the message to a fixed set of known exception kinds when a path-like token is detected. Add a test with a space-containing user path.
- Relationship: new

### QA-002: "Transitions only" write is not proven for the repeated-failure log

- Severity: suggestion
- Related task / requirement: 2.1; design decision 4 ("never per tick")
- Location: `tests/BellTower.Tests/IO/RefreshHealthTests.cs`, `FirstSuccessAfterFailureLogsRecovery...` and `RefreshHealth.Failed`
- Expected / actual: Writing the record on every logged failure (mutant: `if (changed)` made always true) should fail a test. Actual: the mutant survives, because the transitions-only test repeats the failure at +2 minutes, which is inside the 10-minute log interval and returns before reaching the write. The production code is correct (persist only when `changed`); the test just does not exercise a repeat after 10 minutes.
- Reproduction: In a scratch copy change the guard to always persist and run the three new classes; 24 of 24 pass.
- Evidence: mutation table above.
- Recommended correction: In the test, advance the clock beyond 10 minutes, repeat the same failure, and assert the record's last-write time is unchanged while the log gains a second entry.
- Relationship: new

### QA-003: The fallback's pass bound and the fallback's use in recovery are not proven

- Severity: suggestion
- Related task / requirement: 1.4, 1.5; design decision 3 ("bounded number of passes")
- Location: `src/BellTower/IO/StateSnapshotStore.cs` (`pass >= FallbackPasses`), `tests/BellTower.Tests/IO/BoundedStateTests.cs`
- Expected / actual: A test should fail if the last-pass remove-all is lost. Actual: the mutant survives (the loop still ends in about the same count for the fixture, whose estimate is close). The bound is true by construction in the current code (read), and `InRange(encodes, 2, 5)` covers the normal fixture only. Also, the recovery fixture (1.5) recovers through compaction alone, so no test drains a state that needs both compaction and the fallback with queued captures.
- Reproduction: replace `if (pass >= FallbackPasses)` with a never-true condition in a scratch copy and run the three classes; all pass.
- Evidence: mutation table above.
- Recommended correction: Add a fixture in which the weight estimate is too low (for example sessions with deeply nested content) or use a budget so small that only removing every ended session fits, and assert at most `FallbackPasses + 1` encodes. Add a drain-level test with both ended sessions inside the settle interval and a reduced budget, with queued captures for both providers.
- Relationship: new

## Assessment and limitations

- Every one of the seven spec scenarios and tasks 1.1-1.5 and 2.1-2.3 has fixture evidence for Claude Code and Codex (mixed where relevant) plus my reading of the code. The two compaction guards, the cap, the 30-day rule, the fallback, live-session protection, floor ordering, resume revival, queued-capture recovery, size bound, the doctor section and the refresh log all behave as specified. Compaction keeps the displayed fields (the fixture comparison excludes only the journal, checkpoint, floor and operations).
- Compatibility holds by reading `IsValid` and by a read-back of the compacted file; no new `state.json` field exists.
- One real defect to correct before acceptance: QA-001 (sanitization leaks fragments of paths with spaces and some root shapes). Three suggestions (QA-002 to QA-004) are test-strength gaps with no behavior defect found. QA-005 is a full-suite failure caused by the other change.
- Residual: a delayed registration that falls between a post-end ignored event and the compaction floor is ignored after compaction, but would have revived the session before it. The design accepts this (floor at the latest journal observation) and it is only reachable after more than 10 minutes; recorded for the orchestrator, not as a defect.
- Not performed: the installed and live check (3.3), the real tray, real data directory, and any `TrayApplication` execution. `openspec validate --strict` was not part of this assignment.
- Unexpected writes: none to the repository. Scratch copies and the detached worktree were removed or are in the session scratch area. The report is the only file written under the change root.
- Decisions needed: whether QA-005 is fixed by the other change or accepted as a known failure for 3.1, and whether QA-001 is fixed now or deferred.
