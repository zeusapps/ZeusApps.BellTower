# Implementation 002 (fix round 1): fix-vscode-window-activation

Target: Implementation 001 plus these fixes, baseline `9b26088`, uncommitted. All fixes await independent verification. Shared host policy only; no provider transport changed.

## Per finding

- **ANALYSIS-001 (warning, focus bounce): fixed.** `service.js`: a focus generation counter is advanced by every `onDidChangeWindowState` event (focus and blur, now both forwarded by `extension.js` through `noteWindowState`). A sample whose generation changed, or taken while the window is no longer focused, is discarded and repeated instead of the second focus gain being dropped. Self-heal: the request carries the handle the tray activated (`FocusRequest.WindowHandle`, set only when the activation was confirmed). A protocol 2 reveal that fails while the bridge window is unfocused and the handle equals its own record clears the record. Legacy requests, a different or absent handle, a focused window and a missing terminal never clear. Node tests: probe A sequence (A to B to A, sampler first sees B, ends with `1111`, never `2222`), blur then refocus, self-heal and its non-clearing cases.
- **ANALYSIS-003 (warning, auxiliary windows): probe done, fail-safe (a) implemented.** Isolated fixture (`aux-out.txt` in scratchpad, VS Code 1.143.1): after `workbench.action.moveEditorToNewWindow` the fixture main process owns two visible `Chrome_WidgetWin_1` windows (2362630 and 9506132), and the extension window state went `focused:false` right after the move. The premise that a floating editor is a second same-class window is confirmed. Whether `window.state.focused` is true while an auxiliary window holds the foreground could not be observed unattended (the user application held the foreground; nothing was foregrounded). Status of the hypothesis: premise confirmed, consequence unverified, left to live task 4.2. Option (a): the bridge keeps the set of distinct handles sampled per instance; once more than one has been seen it publishes no window evidence (`terminal only`), with a log message and a Node test. Compatibility matrix and install docs updated, marked unverified.
- **QA-001 (warning): fixed.** `VsCodeWindowNavigationTests` now has native disposable-window tests with windows the test process creates (transparent, non-activating WinForms windows on their own thread): handle to owner and class mapping and a destroyed handle through `NativeWindowInspector`; ownership accepts a real window, refuses the shell window of another process, a wrong class and a destroyed window; a really minimized window is restored once; visible maximized (`IsZoomed`) and borderless fullscreen (bounds) windows get no restore and keep their show state; denied foreground gives a failure receipt while the terminal reveal request still goes out. Honest label: `SetForegroundWindow` is not called on test windows (a recorded denial substitutes it, so the tests never take the foreground from the person running them); `IsForeground`, restore and show state are real Win32. A real foreground grant is environment dependent and stays with live task 4.2.
- **QA-002 (warning): fixed.** Minimal refactor: `Tray/NavigationOutcome.ApplyViewed` holds the decision `TrayApplication.Navigate` used inline; `Navigate` calls it. Tests (`NavigationOutcomeTests`): failed, denied, partial and lost-foreground results leave `ViewedEpisode`, episode, since and attention unchanged; success marks only for chip clicks with an episode; a late success for an older episode cannot hide a newer timer.
- **QA-004 (warning): fixed.** `doctor` `vsCode` is now an object from `Diagnostics/VsCodeBridgeReporter`: every fresh registration as `verified`, `partial` (older bridge) or `unverified` with the reason, and every live VS Code session of either provider with `navigation` and `reason` from the same `VsCodeNavigator.Explain`. Test `DoctorReportsWindowVerificationEquallyForClaudeAndCodex` covers matched claude and codex sessions on verified, partial and unverified destinations.
- **ANALYSIS-002 (suggestion, requested): fixed (a) and (b), not (c).** The sampler returns `{unavailable:true}` for spawn failure, timeout, exit not 0 or bad output: the earlier record is kept, sampling is retried (bounded), a distinct message is logged. Real contradictions still clear the record. Request processing no longer waits on sampling (the tick publishes and serves requests first, then starts sampling, which republishes itself). Option (c) was not adopted.
- **ANALYSIS-004 (suggestion, requested): fixed with a measured correction.** `VsCodeNavigator.Precision` uses a snapshot reused for 200 ms and re-filtered against the 15 second freshness on every use; `FocusAsync` and diagnostics always read fresh. The scoped reader `VsCodeNavigator.ReadRegistration` opens with `FileShare.ReadWrite | FileShare.Delete`; `AtomicFile.Read` is unchanged. Measured: Node 24 `renameSync` over a file that another process holds open fails with EPERM even when that reader shares delete (modes Read, ReadWrite+Delete and Delete+Read all failed; no open handle succeeded). So the share mode lets the reader coexist with a writer (tested) but does not stop rename collisions; the snapshot, by shrinking the number and length of opens, is the real mitigation. A short bounded rename retry in the bridge would address residual collisions directly; not implemented (outside the requested set).
- **ANALYSIS-005 (suggestion, requested): fixed.** The tray removes both request and receipt on read (also for an unreadable receipt) and on timeout, with a short retry because the bridge may be reading the file, and sweeps `Requests/*.result` older than one minute (`ReceiptSweepAge`, asserted above the 5 s expiry) before each request. Tests: cleanup on read, on timeout, old receipt swept and recent kept.
- **QA-003 (suggestion, requested): fixed.** A window that was already focused at load samples on its first `onDidChangeWindowState` event that reports `focused` and `active` becoming true while it has no record and has seen no handle (an input event delivered after load). Why this does not reintroduce the prototype-001 mismatch: that failure came from trusting the initial `focused` value with no event; this path never samples from the initial value, requires an input event, still needs the stable double sample, owner equal to the extension host parent, editor class, an unchanged generation and focus after the sample, the multiple-handle guard, and the tray re-verification at click time. A foreign foreground is rejected (test). Residual: an interaction event with the foreground on another window of the same editor process is covered by the same bounce, multiple-handle and self-heal protections, not eliminated.
