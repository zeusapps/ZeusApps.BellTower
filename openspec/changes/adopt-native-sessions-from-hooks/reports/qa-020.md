## Findings

### QA-2000: Runtime-confirmed active work is forgotten when runtime facts pause

- Severity: warning
- Related task / requirement: 2.3, design decision 2 (work side from exact-conversation runtime status; freshness rules)
- Location: `src/BellTower/Core/ConversationLifecycle.cs` lines 94-98 (`evidenceAt` computation)
- Expected / actual: fresh active runtime status at T extends the conversation's visibility to T plus grace. Actual: it is persisted only in `UnverifiedSince`, but the next evaluation recomputes `evidenceAt` from `Latest(ConversationObservedAt ?? UnverifiedSince ?? RegisteredAt, activeEvidenceAt)`. Whenever `ConversationObservedAt` is set (every hooked conversation) it takes precedence, so a prior runtime-active extension is dropped as soon as no fresh runtime fact is supplied (transport gap, poll backoff, Bell Tower restart, runtime freshness of 2 minutes versus a larger grace). `UnverifiedSince` moves backward and the record becomes `unavailable` even though active work was confirmed within the grace.
- Reproduction (scratch copy, not in the repo): shared record with `ConversationObservedAt = now-30m`, grace 10 min. Evaluate with runtime Active at now-10s (health `unverified`). Evaluate the result again at now+3m with no runtime facts. Expected `unverified`, actual `unavailable`.
- Evidence: reproduced in my scratch copy under the scratchpad (`ScratchQa.RuntimeActiveEvidenceDoesNotRegressWhenFactsStop` failed). No current test covers it because the evidence source in every test supplies facts at every evaluation.
- Recommended correction: include the stored `UnverifiedSince` as a lower bound in `Latest(...)` (or persist the last active-evidence time in `evidence`), and add a test where facts stop after an active observation. This matters before the transport task 3.x produces facts intermittently.
- Relationship: new

### QA-2001: Reconcile overwrites future-revision shared evidence

- Severity: suggestion
- Related task / requirement: 2.1 fail-closed encoding; 2.4 data preservation
- Location: `src/BellTower/Core/ConversationLifecycle.cs` line 98 (`Evidence = evidence with { Terminal = terminal }`) with `AttachmentEvidence.Of`
- Expected / actual: a stored evidence record with an unknown revision should be treated as absent for decisions but not destroyed. Actual: `Of` returns a freshly derived revision-1 record and `Evaluate` persists it, so a shared record carrying `revision: 2` and a future facet is rewritten at revision 1 on the next drain (reproduced). The existing hook path (`AttachmentEvidence.Merge`) already behaves the same, so this is not a new class of loss, only a second writer.
- Reproduction (scratch copy): save a shared-runtime attachment whose `evidence` has `revision: 2` and a `futureFacet`, publish a hook, `new StateStore(...).Drain()`, read the attachment: `Evidence.Revision == 1`.
- Evidence: scratch test `ScratchQa.FutureRevisionEvidenceIsPreserved` failed (expected 2, actual 1).
- Recommended correction: do not persist the derived evidence when the stored revision is not current (leave the stored object and write only legacy fields), or document that downgrade is out of scope. Low priority.
- Relationship: new

### QA-2002: Tests do not pin three stated behaviors

- Severity: warning
- Related task / requirement: 2.3 verification list (shared owner killed; delayed events), design decision 2 freshness rules
- Location: `tests/BellTower.Tests/Providers/ConversationLifecycleTests.cs`
- Expected / actual: each stated rule has a test that fails when it is broken. Surviving mutations:
  - M12: `unavailable` made sticky again (the evidence calls the non-sticky change out as a new behavior: "fresh evidence reinstates `unverified`"). No test starts from `Health = "unavailable"` and expects recovery after a new hook or runtime fact.
  - M7: ignoring `shell-exited` (a shared record whose recorded `Host.Shell` ended is a disconnect, not an end; this is the guard for the task 4.2 constraint). No test covers it.
  - M9: a tie between runtime and hook observation favoring the hook instead of the runtime. No test covers it.
- Reproduction: mutate the matching expression in a copy of `ConversationLifecycle.cs` and run `ConversationLifecycleTests`; all 20 pass.
- Evidence: scratch runs listed in the checks table.
- Recommended correction: add one test each. The shell-exited test is the most valuable because it protects the rule that makes the 4.2 constraint safe for the current tray.
- Relationship: new

## Assessment and limitations

- Task 2.4: the conclusion that no new consumer gate is needed holds for the shapes 2.3 writes. No path writes `EndedAt`, `Process`, `Host.Shell` or a new `Health` value for a shared conversation; an older tray can at most show a shared conversation as `unverified` and then `unavailable` (never `verified-live` or ended), which is today's behavior. The recorded constraint for task 4.2 is correct and should be added to the task text and design Risks as proposed.
- Task 2.3: the rule matches decision 2 in the reducer. `runtimeStatus` is never read, never-bound stays terminal-unverified, demotion and disconnect are never completion, PID plus creation time is used, late facts are ignored, and direct processes are routed unchanged through `AttachmentHealth`. Claude and embedded Codex are covered by direct-process rows; shared mode exists only for Codex, so no parity gap is created. The main correctness gap is QA-2000, and the main test gap is QA-2002.
- Not performed: any real provider, binder, runtime transport, live tray, VS Code or Windows Terminal check (none exist yet); attention behavior on a real shared session is untested.
- Evidence type: all executed checks are simulated fixtures. Source inspection is labelled as such.
- Unexpected writes: none to the repository. Scratch copies and mutation runs were confined to the session scratchpad. Existing `bell-tower` processes seen during the run belong to the user's installation (started before this review) and were not touched; no test host remained.
