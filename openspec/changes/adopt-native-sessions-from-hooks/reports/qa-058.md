## Findings

### QA-5800: Permanent-limit classification depends on exact message text

- Severity: suggestion
- Related task / requirement: 4.11; "Viewed wait timer"
- Location: src/BellTower/Hosts/NavigationReasons.cs:42-43 (`IsPermanentLimit`), src/BellTower/Hosts/Navigator.cs:20-24
- Expected / actual: the permanent limit is identified by comparing `FocusResult.Message` to the `SharedBackend` string. Today `Navigator` produces exactly that string and tests cover it, so behavior is correct. A future edit of the message at one of the two sites, or a second producer, would silently turn the rule into "keep the timer" with only the Navigator-based test noticing.
- Reproduction: inspection; no defect observed.
- Evidence: the constant is shared, so the comparison is by constant, not a copy of the text; tests build the result through the real Navigator.
- Recommended correction: optional; a typed marker on the result would be sturdier. Not required for 4.11.
- Relationship: none

### QA-5801: Timer is hidden before the reason is shown

- Severity: suggestion
- Related task / requirement: 4.11; spec "once the reason has been shown"
- Location: src/BellTower/Tray/TrayApplication.cs:431-450
- Expected / actual: the spec says the timer hides "once the reason has been shown". `ApplyViewed` and `Tick()` run before `notice.ShowNotice`. If the notice were to throw, the timer would be hidden with no reason shown. Normal flow shows both in the same handler pass, so the spec scenario holds. Also, if the viewed-state save fails for a permanent limit, the status reads "Session focused; the timer preference could not be saved.", which is inaccurate for a limit result.
- Reproduction: inspection of the handler; not executed.
- Evidence: source only.
- Recommended correction: optional; neutral wording for the save-failure status and, if desired, apply after the notice call.
- Relationship: none

## Notification and toast click paths (question from the assignment)

Source search found no toast or balloon click handler that navigates: the only callers of `Navigate` are the strip (`hideTimer: true`) and the Overview (`hideTimer: false`), and there is no `BalloonTipClicked` or toast activation handler in `src`. A shared-backend click that leaves the timer visible therefore cannot come from a notification click today; the Overview click leaves it visible as the spec requires ("Overview and CLI navigation SHALL NOT hide chip timers"), and the CLI `focus` command does the same. The spec requires only chip clicks to hide the timer, and the implementation matches it. If a notification click navigation is added later, the spec leaves its behavior undefined, so it should be decided then. Both providers share one classifier and one hide path (Claude Code and Codex attachments tested through the real Navigator).
