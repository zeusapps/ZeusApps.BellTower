### Flake investigation (bounded)

Method: a clean linked worktree of 1c80a7d (baseline) and a second one holding the target's 32 files, each built in Release and tested with `dotnet test -c Release --no-build`. The analyzer was probably running its own builds at the same time, so absolute load was not controlled.

- Baseline 1c80a7d, 4 full runs (1551 tests): no `CodexShared*`, `CodexTransport*` or other transport failures. Once, `AudioQueueTests.NormalAndReminderLikeMixedProviderAggregatesUseSharedPolicy(reminderLike: True)` failed (3 `Done` items instead of 1).
- Target, 3 full runs (1593 tests): run 1 failed `CodexSharedRuntimeServiceTests.DisposingAnObserverConnectionLeavesBothBackendsServingTheNextOne` (time-budget transport exception). Run 2, executed at the same moment as a baseline run that had no such failure, failed `CodexSharedAccessTests.FailuresAfterTheHandshakeCarryAReason(DropAfterInitialize, Refused)`, `CodexSharedAccessTests.ARootThreadWhoseIdentifiersAgreeIsMappedAndReadWithoutTurnsOrResume`, `CodexSharedRuntimeServiceTests.ObserverReadsDiscardPreviewsTurnsAndTokens(owned: True)`, `CodexSharedRuntimeServiceTests.AStalledSharedBackendBacksOffThePermissionPumpForTheWholeHome` and `AudioQueueTests.NativeProbeExceptionReturnsUnknownInsteadOfEscapingDoctor`.
- Target, filtered run without `NativePresentationTests` and `MixedLaunchAndNativeTests`: failed `CodexSharedAccessTests.AThreadThatIsNotTheRequestedRootIsRefusedOnASharedBackendWithTheRightKind(...ThreadUnverified)`, `CodexTransportTests.RefusedConnectionIsReportedAndBacksOff`, `CodexTransportTests.ASupersedingListenerIsSeenByTheNextOpenAndTheVerifiedConnectionKeepsItsBackend`, `CodexSharedAccessTests.FailuresAfterTheHandshakeCarryAReason(DropAfterInitialize, Refused)`, plus the `AudioQueueTests` probe test.
- Target, filtered run also excluding `TerminalTabSelectionTests`, `NavigationOutcomeTests` and `CapabilityMatrixTests`: failed `CodexTransportTests.BackoffRecoversAfterTheBackendAppears` and the `AudioQueueTests` probe test.
- The 73 tests matching `CodexShared|CodexTransport` passed twice at the target and twice at baseline when run alone (5 s each).
- `CodexSharedAccessTests.AFailureThatStartedBeforeASuccessDoesNotUndoTheSuccess` (the QA-3800 test) did not fail in any run I made.
- In every run at both revisions, four `CodexNameTests` fail (`NativeRenamePausesWritesUntilExplicitResume`, `NativeNamesFollowIdentityAndDuplicateWritesAreSuppressed`, `ResumedThreadRetainsNativeOwnershipAcrossRuntimeRestart`, `ParallelRuntimesAndThreadIdsStayIsolated`). The message is a title carrying `| worktree: <folder>` appended: it is an artifact of running in a linked git worktree and is not a product or target defect. They are not counted below.

Conclusion: the load-sensitive tests are the `CodexShared*` and `CodexTransport*` tests (time budgets over loopback), and `AudioQueueTests` shows unrelated flakes at both revisions. The shared and transport failures were seen only at the target (3 of 3 full or filtered-full runs plus the two filtered runs) and not at baseline (0 of 4), including one pair run simultaneously under the same machine load. Excluding every changed or added test class did not remove them, so the changed tests are not the trigger. I did not isolate the cause (candidates: different xUnit class scheduling with 42 more tests, or machine load from the concurrent analyzer that the pair run could not control). This is reported, not fixed.

## Findings

### QA-4000: Delta spec, design and tasks do not record the color-reset decision that the code and docs implement

- Severity: warning
- Related task / requirement: 4.3, `specs/session-identity/spec.md` (native presentation requirement and scenario "No safe restoration mechanism is available"), decision 5 and 8 in `design.md`, evidence 045 Follow-up
- Location: `openspec/changes/adopt-native-sessions-from-hooks/specs/session-identity/spec.md` lines 21 and 39-41 at the reviewed identity; `tasks.md` line 29; implementation in `src/BellTower/Core/NativePresentation.cs` (grants title and background together) and `src/BellTower/Hosts/TerminalColors.cs` (`Reset`)
- Expected / actual: The spec says Bell Tower SHALL change colors only when "restoration behavior [is] verified" and, when a prior presentation or safe restoration cannot be established, SHALL leave that surface unchanged. The 2026-11-13 follow-up (user decision, in evidence 045 only) writes the palette background, never reads the prior color, and resets with `OSC 110/111`, whose effect in Windows Terminal and the VS Code terminal is explicitly assumed. Neither `design.md`, `tasks.md` nor the spec records that decision, so the artifacts contradict the shipped behavior and a verifier reading only the spec would call the color write a violation. The code, matrix, doctor and docs agree with each other and honestly mark the reset as assumed.
- Reproduction: compare `specs/session-identity/spec.md` lines 21 and 39-41 with `evidence/implementation-045.md` "Follow-up" and `Core/NativePresentation.cs` `Effective`.
- Evidence: source inspection of the files named above; no code defect.
- Recommended correction: the orchestrator should record the color decision (title and color together, reset to terminal default instead of prior-color restore, reset assumed until trial 6.1) in `design.md`, the spec scenarios and task 4.3 through the OpenSpec update workflow, and keep trial 6.1 as the acceptance evidence for the reset.
- Relationship: new

### QA-4001: Full-suite run at the target shows load-sensitive `CodexShared*` and `CodexTransport*` failures that did not appear at baseline in four runs; cause not isolated

- Severity: warning
- Related task / requirement: 6.4 (final verification), QA-3800, QA-3900, ANALYSIS-3200 (earlier deferred suggestions)
- Location: `tests/BellTower.Tests/Providers/CodexSharedAccessTests.cs`, `tests/BellTower.Tests/Providers/CodexTransportTests.cs`, `tests/BellTower.Tests/Sessions/CodexSharedRuntimeServiceTests.cs` (names in the investigation section)
- Expected / actual: Expected a green full suite at the final target (apart from the linked-worktree `CodexNameTests` artifact). Actual: each target full-suite run failed 1 to 5 of these loopback tests with "The Codex runtime did not answer within its time budget" or a canceled task. They pass in isolation at both revisions and did not fail at baseline in four full runs.
- Reproduction: in a linked worktree of the target, `dotnet test -c Release --no-build`; compare with a baseline worktree of 1c80a7d run at the same time.
- Evidence: counts and test names in "Flake investigation" above. `AFailureThatStartedBeforeASuccessDoesNotUndoTheSuccess` did not fail in any run. Excluding the changed test classes did not remove the failures, so the cause may be class scheduling or machine load rather than the new tests.
- Recommended correction: run the target full suite on an otherwise idle machine (and in the main tree) before declaring 6.4 closed. If the failures persist, the developer should make these classes independent of parallel load (a shared `[Collection]` for the loopback tests, or larger injected time budgets) as the deferred QA-3900 and ANALYSIS-3200 suggest. I did not fix anything.
- Relationship: related to QA-3800 (fixed), QA-3900 and ANALYSIS-3200 (deferred)
