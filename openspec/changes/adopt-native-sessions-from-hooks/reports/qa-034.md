## Findings

### QA-3400: The real runtime-host row never exercises the backend-stop branch

- Severity: warning
- Related task / requirement: 3.3 ("only Bell Tower owned helpers are stopped")
- Location: `tests/BellTower.Tests/Hosts/ManagementOwnershipProcessTests.cs` `RealRuntimeHostStopsOnlyTheBackendItStarted`; `src/BellTower/Sessions/CodexRuntimeHost.cs` finally block (`server.Kill(entireProcessTree: true)`)
- Expected / actual: The test and evidence-039 say the stand-in backend "never becomes ready" and that the host "stops only the backend it started". Actual: the stand-in (a renamed `cmd.exe` launched through the PowerShell wrapper) has already exited when the host reaches its finally block (probe printed `exited=True`), so the `if (!server.HasExited)` kill never runs. The test's own fallback (`backend = []`) tolerates this silently. A mutant that also kills other `codex` images in the test workspace survived. The only termination site that signals a backend is therefore guarded by the source scan (which counts it) but not by any behavioral test.
- Reproduction: insert a write of `server.HasExited` at the start of the finally block, run `--filter RealRuntimeHostStopsOnly`; or apply mutant M2.
- Evidence: this report, Mutants 2 and 4.
- Recommended correction: use a stand-in backend that stays alive (for example a `ping -n` loop image started through the same wrapper, or a stand-in that listens but never speaks the protocol), assert the backend was found and ended, and fail instead of falling back to an empty list. Correct the evidence wording ("never becomes ready" versus "exits immediately") and keep the limitation listed.
- Relationship: new

### QA-3401: Loopback owned-runtime transport honors proxy environment variables

- Severity: warning (pre-existing, outside the 3.3 diff; found while tracing the denied requests)
- Related task / requirement: design.md decision 4 (authenticated loopback runtime); not a 3.3 defect
- Location: `src/BellTower/Providers/CodexLoopbackTransport.cs` line 8 (`new ClientWebSocket()` with the bearer header at line 17); contrast `CodexSharedTransport.cs` line 49, which sets `UseProxy = false`
- Expected / actual: A connection to the runtime Bell Tower started on a loopback endpoint should never be routed through a proxy. Actual: with `HTTP_PROXY` or `HTTPS_PROXY` set and no bypass entry, the runtime-host readiness probe sent a CONNECT for the loopback endpoint to the proxy (observed in the proxy log). The runtime then never becomes ready behind a proxy, and the bearer token is sent in clear through the proxy if it permits the tunnel.
- Reproduction: set `HTTP_PROXY` to a logging proxy and run the `RealRuntimeHostStopsOnlyTheBackendItStarted` test; the proxy sees `CONNECT 127.0.0.1:<port>`.
- Evidence: native harness log (this report).
- Recommended correction: set `socket.Options.Proxy = null` for the loopback transport and add a regression test with a proxy environment variable and a local listener. Parity: the shared transport already does this; Claude has no equivalent transport.
- Relationship: new

### QA-3402: Process tests start trays that contact the real update service

- Severity: suggestion
- Related task / requirement: project safety rules (isolated, no production traffic)
- Location: `tests/BellTower.Tests/Hosts/ManagementOwnershipProcessTests.cs` `StartTray` and the update rows; `src/BellTower/Updates/ReleaseClient.cs`
- Expected / actual: Tests should not depend on public network access. Actual: the trays these rows start make a release check to `api.github.com` (observed through the proxy log). Existing tray tests follow the same pattern, so this is not new, but the update rows lengthen exposure.
- Reproduction: run `--filter UpdateReplacesOnlyTheTray` behind a logging proxy.
- Evidence: this report.
- Recommended correction: a test-only way to disable or redirect the update check for the isolated tray (an existing seam if there is one), or note it as a known hermeticity gap.
- Relationship: new

### QA-3403: Source scan counts lines, not terminating calls

- Severity: suggestion
- Related task / requirement: 3.3 stop-site guard
- Location: `tests/BellTower.Tests/Core/ProcessStopAuthorityTests.cs` (`Count(line => ... Terminating.IsMatch(line))`)
- Expected / actual: A second kill added on a line that already has one (as in mutant M2, where a `foreach ... Kill()` was prepended to the existing kill line) leaves the per-file count unchanged, so the guard passes. Primitives such as job objects with kill-on-close or `NtTerminateProcess` also match nothing.
- Reproduction: apply mutant M2; `ProcessStopAuthorityTests` still passes.
- Evidence: this report.
- Recommended correction: count matches rather than lines (`Regex.Matches`) and add `JobObject`/`NtTerminateProcess`/`SetInformationJobObject` to the pattern.
- Relationship: new

## Assessment and limitations

Acceptance for 3.3 is largely supported. The audit confirms the developer's conclusion: every termination in `src` targets a handle Bell Tower created in the same operation, and owned-runtime shutdown is a marker consumed by the manager Bell Tower started. Detach, setup removal, tray exit and update/rollback send no signal to anything but the tray for their own data directory (isolated by data-dir derived mutex names; the user's tray was untouched). The 19 process tests and the source scan are meaningful for detach, stop, stale and hostile records, setup removal, tray exit and the update coordinator, are isolated (workspace roots, scrubbed `BELLTOWER_*` environment, no leaked processes observed), and killed two of three independent mutants. The native row passed against a real Codex 0.166.0 backend that survived every action with unchanged identity.

Gaps: (1) QA-3400, the only backend-signalling termination in the host is not covered behaviorally; (2) post-switch rollback is not process-tested (developer limitation, confirmed; the code path reuses `RequestExit` and `StartTray`); (3) the detach rows use an attachment registry, not a live provider hook; (4) the native row covers Codex only, Claude native not performed; (5) full-suite load-sensitive failures are unrelated and pass alone. No files other than this report were written; no unexpected mutation of the review target. Decision for the orchestrator: whether QA-3400 blocks closing 3.3 or is accepted with the limitation recorded.
