## Assessment and limitations

- Stated limits: an npm-style shim or any intermediate process between the shell and the hooked `codex.exe`, and a profile launch that never calls `prepare-session` (no VS Code or Windows Terminal, or background coloring disabled), both fail closed only when the mode is unknown. The Codex profile adds `--no-daemon` and a shim forwards arguments to the native process, so a readable command line classifies as embedded and takes the direct branch without relying on the shell proof. A user whose mode is known is therefore not weakened. Users with an unreadable or unrecognized command line lose the binding, which was the accepted fail-closed trade-off. Claude is unaffected. I did not execute an installed shim, only reasoned from the classifier and the module flow.
- Full suite is not clean: `CliTests.GeneratedPowerShellHookCommandPreservesUnicodeAndFinishesWithinItsTimeout` and `HookMaintenanceTests.CleanupHashingDoesNotBlockGeneratedClaudeCodexOrMixedLegacyHooks` failed in two consecutive full runs with a three-second hook budget exceeded (exit -1), while passing alone. The target does not change those areas. I attribute them to load in a 4.5 minute run on a shared machine, but I did not prove it against a clean baseline, so they remain an unresolved environmental risk for the orchestrator to rerun on an idle machine. They are not reported as a defect.
- No target files or findings.md were edited. No testhost remained. MSBuild reusable build-node `dotnet.exe` workers started by my build and format steps are still idle; my attempt to stop them was denied by the permission system, and they exit on their own timeout.
