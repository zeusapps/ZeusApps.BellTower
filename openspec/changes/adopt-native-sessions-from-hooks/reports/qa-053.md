## Findings

### QA-5300: Delivery, log codes and notice window behavior have no automated check

- Severity: warning
- Related task / requirement: task 4.1, design decision 8; assignment delivery claims
- Location: `src/BellTower/Tray/TrayApplication.cs:431-441`, `src/BellTower/Tray/NoticeForm.cs`, `tests/BellTower.Tests/Hosts/ClickReasonTests.cs`
- Expected / actual: The claims that every click writes `navigation-ok-<precision>` or `navigation-refused-<precision>` with no paths or prompts, and that the notice never activates and closes, should each have a check. Only the pure `Decide` mapping and the `Place` function are tested. The log string composition lives inline in the async-void `Navigate` handler, and the non-activating style, click-to-hide and timer-hide are not tested.
- Reproduction: `grep -rn "navigation-ok\|navigation-refused\|ShowWithoutActivation\|NoticeForm" tests` finds only `NoticeForm.Place`.
- Evidence: Source inspection supports the claims; no executed check does.
- Recommended correction: Extract the log code into a small pure function (for example in `NavigationNotice` or `NavigationOutcome`) and add a theory asserting the code for each precision and success, including that the output matches `^navigation-(ok|refused)-[a-z-]+$`. Add a test that `NoticeForm` created without a handle reports `ShowWithoutActivation` and the `WS_EX_NOACTIVATE` style bit, and that `Hide` happens on the timer tick if it can be driven without a message loop. Otherwise record these as live-only checks in the trial.
- Relationship: new

### QA-5301: No executed check of the `focus` command or `SessionCatalog.FocusAsync` for a shared conversation

- Severity: suggestion
- Related task / requirement: T-4 ("in both hosts, the Sessions window and the `focus` command")
- Location: `src/BellTower/Cli/FocusCommand.cs:14`, `src/BellTower/Sessions/SessionCatalog.cs:60`
- Expected / actual: The `focus` command should be shown to print the shared-backend message and exit 1. It passes through the same `Navigator`, so it is very likely correct, but only the `Navigator` is tested.
- Reproduction: no test references `FocusCommand` or `SessionCatalog.FocusAsync` with a shared attachment.
- Evidence: source inspection of the call chain.
- Recommended correction: Add one test through `SessionCatalog` (or the command with a disposable `--data-dir`) using a stored shared Codex conversation and assert message and exit code.
- Relationship: new

### QA-5302: An ended shared conversation still gets the generic process message

- Severity: suggestion
- Related task / requirement: T-4 ("generic message limited to a direct session whose process is gone")
- Location: `src/BellTower/Hosts/NavigationReasons.cs:32-35`
- Expected / actual: `ForSharedConversation` requires `EndedAt is null`, so a shared conversation that has ended falls to `ProcessUnverified` ("The session process cannot be verified.") although it never had a process. The spec statement is narrower than the behavior. Impact is low since an ended session is normally not offered for clicking.
- Reproduction: build a shared conversation attachment with `EndedAt` set and call `Navigator.FocusAsync`.
- Evidence: source inspection; not executed.
- Recommended correction: Either state this edge in a test and doc, or answer the shared reason for an ended shared conversation as well (its own "session ended" wording is also acceptable).
- Relationship: new

### QA-5303: The setting-off reason is lost when the Windows Terminal helper falls back

- Severity: suggestion
- Related task / requirement: T-6
- Location: `src/BellTower/Hosts/WindowsTerminalNavigator.cs:50-70` and `:97-103` (`FocusWindow`), reached from `WindowsTerminalFocusService`'s caller
- Expected / actual: With the setting off the explanation appears only when the `focus-terminal` helper returns normally. When the helper cannot start, times out (4 s) or returns unparsable output, `FocusWindow` returns the old "Windows Terminal focused; select the session's tab or pane." and the T-6 reason is not shown. The click still states a message, so task 4.1 holds, but the user's trial case can differ from the tested path in these fallbacks.
- Reproduction: not executed; source inspection.
- Evidence: the fallbacks are not covered by `ClickReasonTests`.
- Recommended correction: Decide whether the fallbacks should reuse the same setting-off wording for an adopted direct session, or document that they do not.
- Relationship: new

### QA-5304: Precision text from a VS Code receipt flows into the log code

- Severity: suggestion
- Related task / requirement: log hygiene (no paths or prompts)
- Location: `src/BellTower/Tray/TrayApplication.cs:431`, `src/BellTower/Hosts/VsCodeNavigator.cs:122-124`
- Expected / actual: The precision comes from `FocusResult` values; for VS Code the whole object is deserialized from a bridge receipt file, so its precision is free text, and a missing field would be null (`Replace` would throw inside an async-void handler; `NeedsNotice` already has the same null exposure, so this is not a new class of failure). `LocalLog` strips separators and caps at 120 characters, which keeps paths out, but arbitrary words could still be logged.
- Reproduction: source inspection; not executed.
- Evidence: `LocalLog.Write` filtering at `src/BellTower/IO/LocalLog.cs`.
- Recommended correction: Log only a precision from the known set (`exact tab`, `exact terminal`, `terminal only`, `window only`, `unavailable`) and `other` otherwise; consider a null-safe precision in the receipt reader.
- Relationship: new
