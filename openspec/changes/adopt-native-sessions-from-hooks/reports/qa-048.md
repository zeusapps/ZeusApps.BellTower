## Findings

### QA-4800: The two user-stop producers have no test

- Severity: warning
- Related task / requirement: task 4.5; spec scenario "User stopped the tray"
- Location: `src/BellTower/Tray/TrayApplication.cs:175-180` (Exit menu handler), `src/BellTower/Cli/ExitCommand.cs:10` (wiring to `RequestUserExit`), reviewed at 5e95554 plus working tree
- Expected / actual: the acceptance case "user Exit then hook starts nothing" depends on exactly two call sites recording the stop. Tests exercise `RecordUserStop` and `TrayController.RequestUserExit` directly but neither call site. Reverting either call site passes the whole HookTrayStart, Cli and Tray test selection (229 tests).
- Reproduction: in a copy of the tree, change `ExitCommand` to `RequestExit()` and delete the `RecordUserStop(paths.Root)` line from the Exit menu handler; build; `dotnet test --filter "FullyQualifiedName~HookTrayStartTests|FullyQualifiedName~Cli|FullyQualifiedName~Tray"` -> 229 passed.
- Evidence: mutants C and D above. Separately, my end-to-end probe shows the unmutated `bell-tower exit` does record the stop and suppress both providers' hooks, so this is a coverage gap, not a behavior defect. The menu click itself was not executed by anyone (not performed).
- Recommended correction: add a test that runs the `exit` command through `CliApplication` against a held tray mutex and asserts the stop record, and extract the Exit handler body into a method the test can call (or otherwise exercise it), asserting the record. Keep real tray start out of the test, as the task requires.
- Relationship: none

### QA-4801: The no-breakaway fallback is untested and can make a visible tray flap if a provider job kills on close

- Severity: suggestion
- Related task / requirement: task 4.5 (outside the provider's job); design decision 9 process creation; risk line
- Location: `src/BellTower.Protocol/TrayProcess.cs:146-163`
- Expected / actual: the fallback is reachable and safe for the hook (my probe: `{}`, exit 0, outcome `StartedWithoutBreakaway` recorded). It is not covered by any automated test, and the Codex 0.167.2 hook job was not probed by anyone. If a provider's hook job refuses breakaway and kills its processes on close, the tray started inside it ends with the hook, so the next hook after the 30 s interval starts it again and the user sees a tray that appears and disappears roughly every 30 s while a session is busy; only `doctor` explains it.
- Reproduction: a child process that assigns itself to a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and no breakaway flag, then runs `bell-tower-ingress.exe --provider claude --data-dir <disposable>` with a valid stand-in launcher record. Output: `StartedWithoutBreakaway`, and the stand-in ended when the job closed.
- Evidence: probe row above (JIT and AOT builds). Claude Code 2.1.325's job allows breakaway by the developer's probe; Codex unknown.
- Recommended correction: add an automated test using that job-object harness (so the outcome string and the unchanged hook output are pinned), and record the Codex hook job as an explicit item of the user trial 6.1 (or a probe with a fake endpoint) before the Codex claim in `docs/compatibility.md` is treated as verified. Decide whether a fallback start inside a kill-on-close job should be skipped rather than retried (a user decision on behavior, not a defect against the current text).
- Relationship: none

## Assessment and limitations

Assessment of the developer's defaults against the design:

- (a) Start only after a durable write or a benign no-envelope event: consistent with the spec ("after persisting a capture") and with the safety goal; verified by tests. Not a breach.
- (b) Unreadable LUID fails open: practically unreachable (the call reads the process's own token). A readable LUID with an unreadable logon time degrades to a LUID-only match, which could in theory collide across boots. Acceptable; documented in the evidence. See QA-4802 for the elevated-token concern.
- (c) Fixed 30 s window with a previous-window yield: the only gap is a sub-millisecond race at a boundary where hook A has chosen window b but not yet created its file while hook B in b+1 reads no previous record; that yields two attempts, and the tray mutex still permits one tray. It does not break "at most one attempt per interval" in any observed run (12 concurrent hooks and 32 concurrent claims gave one winner). Acceptable.
- (d) Update pending equals `restart.json` younger than 10 minutes without an owner check: stricter than the tray's own gate (`UpdateTransaction.RestartPending` also requires a live owner). After a crashed update the marker blocks hook starts for up to 10 minutes although the tray would be allowed to start. This errs on the safe side of "nothing starts while an update is pending", is documented, and is acceptable.
- (e) No `--silent`: `--silent` selects a silent audio sink, so omitting it is correct for a user's tray. Acceptable.
- (f) Only real attempts recorded: refusals are visible through the live `doctor` fields (user stop, pending update, availability) instead of the last-attempt line. Acceptable.

Docs: `docs/hook-ingress.md`, `docs/installation.md` and `docs/compatibility.md` match the executed behavior (names, 30 s interval, 10 minute marker, `doctor` fields in camel case as printed, stop and clear rules, the unprobed Codex job stated openly). I found no contradiction.

Remaining gaps: Codex hook job not probed (not performed, reason above); tray Exit menu click not executed; real Windows Terminal and VS Code restart trial not performed (task 6.1); no before/after latency comparison by me; the suite exercises the JIT ingress while production is NativeAOT (AOT was covered by my probes only); elevated agents unverified (QA-4802). The pinned SDK is not installed, so `scripts/format.ps1 -Verify` and an in-repository build could not be run; results come from an equivalent scratch copy, and the working tree identity is unchanged.

Return to the orchestrator: QA-4800 should be resolved or consciously deferred before task 4.5 is considered verified; QA-4801 and QA-4802 are deferrable suggestions. No ledger edits were made.
