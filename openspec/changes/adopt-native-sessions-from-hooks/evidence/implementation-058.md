# DEV-058: trial 6.1 investigation round (T-12, T-5, T-8, T-9, T-10) and fixes (T-4, T-6, T-7)

Baseline `7a9d1be`. Trial environment: Bell Tower 0.1.9028 dev, Claude Code 2.1.330, Codex 0.171.0, Windows 11 (build 10.0.26300, 26H2), Windows Terminal, not elevated. Phase 1 reports and recommends; it changes no design. Phase 2 fixes what needs no design choice. Nothing here touched the real data directory, the real tray, provider settings in the user profile or any user process.

## Probe material (all under the ignored `artifacts/t12-probe/`)

- `jobprobe/` is a small diagnostic executable (not part of the solution). Modes: `report` (job chain, limit flags, members, ancestors, and the job seen by children created with `CREATE_BREAKAWAY_FROM_JOB`, with a plain create, with `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` = the shell and with `PROC_THREAD_ATTRIBUTE_JOB_LIST`), `nest` (builds nested jobs of given flags to learn the kernel's breakaway rule), `scan` (job membership of every process), `log` (a hook that records its event and payload), `pty` (runs a command in a ConPTY, answers cursor queries, scripts key presses and records the raw terminal stream) and `winject` (a replica of Bell Tower's console write).
- Isolated provider homes (`claude-home*`, `codex-home`), loopback stand-in model endpoints (`fakeresp*.py`, `fakeanth.py`) and a disposable data directory (`data-t8`). Claude Code and Codex ran with `CLAUDE_CONFIG_DIR` / `CODEX_HOME` pointing there and a dead or loopback endpoint, so no real account was used.
- `harness/` loads the built `bell-tower.dll` and drives the real consumer, resolver and console writer over `data-t8`.

## Phase 1: T-12, the hook's tray start refused by a job

### What the hook process sees

| Launch | Immediate job of the hook | Limit flags | Owner |
| --- | --- | --- | --- |
| Claude Code 2.1.330 hook (`claude -p`, isolated config, started from a Windows Terminal shell) | one job with about 110 members: Windows Terminal, the shell, Claude Code, the Bell Tower trays, and unrelated vendor and shell helpers | `0x1800` BREAKAWAY_OK, SILENT_BREAKAWAY_OK, no KILL_ON_JOB_CLOSE | not the provider: it is the same job the plain shell, the explorer-launched probe and every other process of the session is in |
| Codex 0.171.0 hook (`codex exec`, isolated home) | a Codex-owned job with 3 members (the hook shell and its children) | `0x2800` BREAKAWAY_OK, KILL_ON_JOB_CLOSE | the provider (Codex), nested inside the same session job above |
| Hook inside a plain Windows Terminal shell with no provider | the session job above | `0x1800` | none of the provider, the terminal host or the shell |

- Reading the job member lists and the job-handle table (a read-only duplicate of each accessible holder's job handles) shows no process of the provider, Windows Terminal, the shell or `explorer` holds a handle to the session job. The holders found are system and service processes that this non-elevated probe cannot open (most of them one DCOM-launch service host, plus other service hosts, `System` and Defender components). The session job is therefore not owned by the provider, the terminal host or the shell.
- `scan` shows all 155 processes of the machine, including `explorer`, `sihost` and system processes from the first process of the sign-in onward, are in a job. On this build no process is outside every job, so "outside every job" cannot be satisfied by any launch route.
- Not probed: VS Code. It was not running, and starting a window with an automatic task was judged too intrusive for a read-only probe. libuv-based hosts are known to put children in a kill-on-close job by default, so the VS Code case remains unverified. The Windows Terminal case is the shell running this session; a second `wt -w new` window could not be started from the probe's process (no new terminal process appeared), so it was not repeated there.

### Why the breakaway attempt leaves the child in a job

1. `CreateProcessW(..., CREATE_BREAKAWAY_FROM_JOB | CREATE_SUSPENDED)` succeeds in both providers, and the Codex-owned job is left: a child created from the Codex hook sees only the session job. DEV-054's finding (breakaway allowed) is therefore still true.
2. `TrayProcess.Start` then calls `IsProcessInJob(child, NULL)`, which is true for membership in any job. With the session job above it is always true on this build, so the DEV-056 check reports `provider-job-breakaway-incomplete` and terminates the suspended child. The check rejected the child for the harmless session job, not for a provider job.
3. The nested-job rule observed with synthetic jobs matches the documentation (Microsoft Learn, "Nested Jobs"): a breakaway child leaves the immediate job and each job above it that permits breakaway, and joins the first job that does not. A synthetic chain of one kill-on-close job without breakaway under a breakaway-capable job leaves the child inside the kill-on-close job (the DEV-056 fixture). The session job is the exception: it permits breakaway by its flags, yet the child stays in it after 8 consecutive breakaways, after `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` = the shell and after `PROC_THREAD_ATTRIBUTE_JOB_LIST`. Its owner and mechanism are not identified (an OS or vendor session-level job; a silo-like container was considered and not confirmed).
4. The same applies to the known `HookTrayStartTests` failures: the test host is in the same session job, so the ordinary-start tests fail for this reason, not only because of a VSTest job.
5. Every other route tested lands in a job too: a process started by Task Scheduler sits in a Task Scheduler job (`0x0`, no breakaway), an explorer-launched process sits in a small explorer job (`0x800`) inside the session job.

### Options to start the tray outside the provider's job

All options keep the existing hook-side rules unchanged: capture first, never wait, user-stop suppression, one attempt per interval, update-pending gate, recorded stable launcher validated by the hook, no inherited handles, bounded diagnostics.

| Option | How | Trade-offs | Keeps the safety rules |
| --- | --- | --- | --- |
| A. Keep breakaway, replace the check | Drop `IsProcessInJob(child, NULL)`. Make the tray's own startup read its immediate job (`QueryInformationJobObject(NULL)`) and exit with a recorded reason when it has `KILL_ON_JOB_CLOSE`. | Smallest change; fixes this machine. It cannot see an outer kill-on-close job above the immediate one, so the DEV-056 nested synthetic case would pass the hook and be detected only if the immediate job is the kill job. The hook cannot inspect the child's chain before resume. Latency unchanged. | Token and handle rules unchanged. The kill-on-close guarantee weakens from "verified by the hook" to "verified by the child where visible". |
| B. Shell as parent (`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`) | Locate the interactive shell (`GetShellWindow` then its process), verify image, owner, session and creation identity, open it for `PROCESS_CREATE_PROCESS`, create the launcher as its child. Documented to inherit the specified process's job, token and handles ([UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)). | The child never joins the provider's job: probed from the Codex hook, children created this way see only the session job. The invariant becomes "no worse than the shell", provable without introspecting jobs. The user's non-elevated token comes from the shell, which would make `CreateProcessWithTokenW` and the linked-token step unnecessary (not verified here: no elevated session was available, so the elevated case is unverified). One P/Invoke change in `TrayProcess`; roughly the same latency (about 15 ms). Needs a running shell (none during the first seconds of sign-in, or with a custom shell: fail closed and queue). Parent-process spoofing is a known detection pattern for security products (MITRE T1134.004), a possible false positive. Tests need an injectable shell process. | Environment from the shell's token via `CreateEnvironmentBlock`, no inherited handles, same attempt and suppression logic. |
| C. Ask the shell to launch (`IShellDispatch2.ShellExecute` from the desktop's shell view, or `explorer.exe <shortcut>`) | The user's shell process creates the process. | Documented, unelevated by construction, environment and token are the shell's, nothing inherited. Needs COM (STA, interop under NativeAOT) or a recorded shortcut file; 400 to 700 ms measured for the explorer route; depends on a responsive shell; arguments only through a shortcut. The child lands in the explorer job inside the session job. | Handles and environment satisfied. The one-attempt interval and user stop stay in the hook. |
| D. Per-user scheduled task started on demand | Setup registers one task (current user, interactive token, limited, no trigger, single instance, no time limit, runs when on battery) whose action is the stable launcher; the hook only triggers it (`schtasks /run` or `ITaskService`). | Token, environment and handles come from the Task Scheduler service, never from the hook; works from an elevated hook with the limited principal; Task Scheduler also gives one-instance enforcement. Costs: a persistent system registration with its own setup, doctor, update and removal rules (close in spirit to the sign-in entry the user rejected on 2026-11-15, though it has no trigger and starts nothing by itself); defaults must be overridden (72-hour limit, battery conditions); 380 ms to first output measured; the tray inherits the Task Scheduler job (no kill-on-close flag, but the service may terminate it when the task is stopped). | All hook rules stay; the launcher record is replaced by the task definition, which a user with write access can also change. |
| E. WMI `Win32_Process.Create` | Documented as not associated with the caller's job. | Creates the process in session 0, so a tray with UI would not show; rejected. | Not applicable. |
| F. COM local-server activation or a sign-in entry | Per-user COM class, or Run entry. | The Run entry was rejected by the user. COM needs registry registration and the activating identity follows the caller's token (elevated stays elevated). | Not recommended. |

Recommendation: B for both providers (one shared start path), with A's child-side self-check kept as a cheap second line, and the DEV-056 strict check removed in the same change. D is the fallback if B proves unreliable, or if the user wants the tray owned by Task Scheduler. B and the removal of the check are a design change (decision 9 says "outside a provider job object", which this machine shows is not a checkable property); this round does not implement them.

Unverified in this environment: VS Code integrated terminals, an elevated hook (token inheritance with B, linked-token path), Windows builds other than 10.0.26300, and any non-session-job kill-on-close job above the Codex job.

## Phase 1: T-5, native title never shows

Evidence from the real Codex 0.171.0 TUI (`--no-daemon`) run in a pseudo-console and the real Bell Tower console writer applied to it:

- Codex writes the terminal title itself, as `OSC 0`, at start (`<project>`), at about 20 frames per second while a turn works (a spinner prefix and the project and thread name), and once more at completion (`<thread name> | <project>`). It also emits `OSC 7501` state changes (`working`, `done`, `idle`). The real `AttachedConsoleTitleWriter` wrote Bell Tower's title during the working phase; the next spinner frame replaced it within about 70 ms. A title written while Codex is idle persists until the next turn.
- The background (`OSC 11` and `OSC 10`) written the same way reached the stream during the working phase and nothing in Codex reset it (no `OSC 111`), so color is not affected by the provider title.
- Documented controls: Codex `[tui] terminal_title = [...]` (an ordered list of item identifiers; the documented default is activity, thread name and project name; an empty list is expected to stop it but was not verified), and per-session `/title`. Claude Code sets the tab title from the conversation (or the session name) and offers `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` (an environment variable that can be set through the settings `env` block; it also stops the generated-title request and status reports to the terminal) and `terminalTitleFromRename` (only chooses between the generated title and the session name). Sources: Claude Code settings reference and environment variables; Codex configuration types.
- Windows Terminal tab selection matches the managed title, so a provider rewriting the title also weakens tab navigation after a turn, which matches T-5's VS Code and Windows Terminal observations.

Options: (1) write after the provider on each hook, which needs a write on every Stop and prompt event and still loses during a turn for Codex; (2) have setup offer, as an explicit and removable step, the provider setting that stops the provider's own title (`CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` in Claude settings `env`, `terminal_title = []` in Codex config) for sessions Bell Tower presents; this edits user provider settings, so it needs consent and the existing ownership and backup rules; (3) accept color and badge only, drop the title from native sessions and stop depending on it for tab selection, finding the tab another way; (4) return a session title from the hooks (Claude documents a `sessionTitle` hook output; Bell Tower's hooks return `{}` by design). Recommendation: (2) offered as an opt-in setup step with honest diagnostics, and (3) as the stated fallback in the capability matrix while it is off. This is a provider-settings and product decision; nothing was implemented.

## Phase 1: T-8, palette only at prompt completion for `codex --no-daemon`

Not an adoption defect. Probed with the real ingress, consumer, resolver and writer on a real Codex 0.171.0 TUI in a pseudo-console, with isolated state:

- Codex fires `SessionStart` lazily at the first prompt submit, then `UserPromptSubmit` about 0.3 to 1.5 s later, then `Stop`. There is no hook at launch (unlike Claude Code).
- The real ingress classified all three hooks as `embedded-runtime`, direct, observed, with the Windows Terminal host and shell recorded, from the first. The only child of the Codex image at those moments is the hook shell, so the cross-check never contradicts.
- Draining the first capture produced a resolved presentation (background and title) on the first tick; applying it with the real writer put the `OSC 11` background into the stream during the working phase.
- One probe-only effect found on the way: `--dangerously-bypass-hook-trust` is not in the classifier's known option list, so an invocation carrying it classifies `unknown` and fails closed. That is expected and was not the trial's command line.

So the data path from the first accepted hook to the write is immediate in isolation. The delay in the trial is not reproduced. Remaining candidates, none provable without a real tray run: the isolated writer process failing and entering its 2, 5 and 15 second retry backoff while Codex repaints, the 2-second tray tick, or Windows Terminal rendering. The doctor log lines `title-unavailable` and `title-recovered` around the trial time would separate these. No code change is justified yet; this is not a confirmed defect.

## Phase 1: T-9, no confirmed wait for `codex --no-daemon`

Cause, from the source and the compatibility document: a Codex `PermissionRequest` is provisional (its hook runs before guardian or user review), and only the owning runtime's or a verified shared backend's `waitingOnApproval` status confirms a human wait. `--no-daemon` runs an embedded runtime with no endpoint, so Bell Tower has no confirmer; the request stays provisional and after the 15-second unverified grace shows the silent "possibly waiting for approval" chip. The docs record this as an open parity gap ("not a proven restriction") and state "there is no timing-based confirmation". The Codex hook payloads recorded here (`SessionStart`, `UserPromptSubmit`, `Stop`) carry only `session_id`, `turn_id`, `cwd`, `model`, `permission_mode` (`default`), the transcript path and event fields; no reviewer field. An approval scenario could not be reproduced with the stand-in endpoint (the stand-in's tool call was not run by Codex), so the `PermissionRequest` payload itself was not captured.

Fixing it in the shared policy needs a new signal or a rule the spec forbids: (a) a timing rule (rejected by the spec; it would alert on slow automatic review), (b) the session's effective `approvals_reviewer` and approval policy read from the Codex configuration and command line, so `PermissionRequest` under reviewer `user` counts as a human wait, (c) an approval record read from the provider transcript, (d) keep the chip. This is a behavior decision, so it is reported, not implemented. Recommendation: (b) or (c) after a probe that captures the real `PermissionRequest` payload and the transcript at approval time.

## Phase 1: T-10, declining a Claude Code prompt

Probe: Claude Code 2.1.330 TUI in a pseudo-console, isolated settings, a stand-in endpoint returning one Bash tool use, hooks for every permission-related event logging their payloads. After the prompt appeared the probe pressed Esc ("Interrupted - What should Claude do instead?"):

- Hooks seen: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, then `Notification` (`permission_prompt`) 6 s later. After the decline no hook fired in the next 90 s: not `PermissionDenied` (auto mode only), not `PostToolUseFailure` (documented not to run for permission denials), not `PostToolBatch`, not `Stop`, not an `idle_prompt` notification.
- The transcript records the decline immediately: a `tool_result` rejection for the tool use and a `[Request interrupted by user for tool use]` entry.
- Codex has an `Interrupt` hook, which the adapter already maps to the interrupt kind; the trial found Codex clears the provisional state at a decline.

Result: no hook signals a Claude manual decline; the next prompt clears the wait, as observed. The only observation found is the transcript tail, a new evidence source for the reducer, so it is a design decision, not applied. Options: (a) bounded read of the transcript tail named by the hook payload, matched by tool use identifier, when a permission wait is outstanding; (b) accept the documented gap and say so in the chip; (c) a timeout rule (against the spec). Recommendation: (a), shared reducer rule with a thin Claude transcript adapter (Codex already has `Interrupt`).

## Phase 2: fixes

All changes keep one shared policy and thin provider adapters; no provider-specific click logic was added.

- T-4 (shared backend click). `Navigator.FocusAsync` now answers a shared conversation before the process check, with `NavigationReasons.SharedBackend` for a verified shared backend (names the limitation and the two routes, the Codex profile and `codex --no-daemon`) and `NavigationReasons.TerminalUnverified` for a shared conversation whose mode is not recognized. It never reaches a host navigator, so the same text appears in Windows Terminal and VS Code, in the tray, the Sessions window and the `focus` command. The misleading "The session process cannot be verified." now applies only to a direct session whose process is gone.
- T-6 and delivery (T-4, T-6). `WindowsTerminalFocusService` states `NavigationReasons.WindowOnlyPresentationOff` when an adopted direct session is focused at the window only because the setting is off, and keeps the generic message otherwise (including a managed launch that opted out). Delivery: `NavigationNotice.Decide` sends a click's reason to a balloon when Windows will show one and to the new `NoticeForm` (an always-on-top, non-activating message next to the chip strip) when `SHQueryUserNotificationState` says Windows suppresses balloons (full-screen app, presentation, quiet time, locked). Each click is written to the local log as `navigation-ok-<precision>` or `navigation-refused-<precision>`. The suppression hypothesis (a full-screen or focus-mode Windows Terminal hides the balloon) is a likely explanation for the trial's missing message, but it was not confirmed; the balloon text itself was already produced before this change.
- T-7 (Sessions window behind the terminal). `WindowActivator.Raise` asks for the foreground, and when Windows declines it lifts the window above others with a topmost pulse and asks once more. `OverviewForm.Raise` uses it for the tray menu item, the tray double click and every place that previously called `Show` alone.
- T-9 and T-10: not changed; see the phase 1 sections and the documentation note added to `docs/compatibility.md`.

Documentation: `docs/installation.md` (click navigation), `docs/compatibility.md` (matrix row, adopted-direct row, two new open-evidence items), `CapabilityMatrix` rows (same text, printed by `doctor`).
