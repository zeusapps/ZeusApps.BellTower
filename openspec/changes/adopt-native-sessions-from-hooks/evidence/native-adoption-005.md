# Native adoption probe follow-up 005

Date: 2026-10-29. Scope: perform one ordinary private Codex 0.165.0 reopen, review and trust only its single private SessionStart hook through the normal TUI, then observe the isolated hook capture and process-local log metadata. All state remained under ignored `artifacts/`. The probe used the already-trusted nested Git fixture, isolated Codex home, `--sandbox read-only`, a dummy credential, and an unreachable loopback model endpoint. No model prompt, real credential, production daemon, user session, or real checkout was used.

## Per-hook trust action

The bounded ConPTY helper ran the recorded native Codex executable with a 600-second timeout. The ordinary reopen reached “Hooks need review” without a folder-trust prompt or Windows sandbox setup modal. The hook browser listed one new SessionStart handler. I inspected its command, synchronous mode, and “New hook - review required” status before trusting it.

For exact Codex tag `rust-v0.165.0`, [`hooks_browser_view.rs` sends `TrustHook` with only the selected handler key and current hash](https://raw.githubusercontent.com/openai/codex/rust-v0.165.0/codex-rs/tui/src/bottom_pane/hooks_browser_view.rs#L193-L207). In the same source, the `t` action invokes `trust_all_hooks` only on the Events page and `trust_selected_hook` on the Handlers page ([dispatch and footer](https://raw.githubusercontent.com/openai/codex/rust-v0.165.0/codex-rs/tui/src/bottom_pane/hooks_browser_view.rs#L489-L537), [key handling](https://raw.githubusercontent.com/openai/codex/rust-v0.165.0/codex-rs/tui/src/bottom_pane/hooks_browser_view.rs#L548-L586)). The live UI was on `Handlers(SessionStart)` with exactly one selected handler. After the single `t` action, its status changed from “New hook - review required” to the ordinary active-hook toggle state. No list-level “trust all” action was sent. This records successful normal trust of the exact disposable command.

## Startup and capture outcome

The hook capture directory remained empty while the TUI stayed in the handler browser. There is therefore no native SessionStart payload, session ID, or ancestry record from this run. A read-only projection from the isolated existing log database selected only `ts`, `ts_nanos`, `thread_id`, `process_uuid`, and `target`. It yielded 154 rows associated with the exact launched TUI PID, one distinct thread ID, and 17 targets. The process UUID PID matched the ConPTY helper’s PID, creation-time, and executable record. The projection did not read message, feedback, prompt, transcript, or payload values.

Although `--no-daemon` was omitted, the private `app-server daemon version` check still failed to connect to the isolated home’s daemon control socket. No private shared daemon was present to join, so the one process-local thread cannot establish shared-client ownership or hook-session-to-thread correspondence. It also does not prove SessionStart dispatch: the hook capture is empty and the UI remained inside hook review.

## Safe close and cleanup boundary

After trust, the approved navigation path was Escape from the single-handler page and Escape from the Events page to return to the normal startup view. The helper accepts line input and appends a carriage return when forwarding it to ConPTY. Auto-review rejected the attempted two-Escape input with the exact reason: “The authorized close path is exactly two Esc presses, but the requested trailing newline is an additional ambiguous input that could activate the startup prompt or another control, contrary to the no-model-prompt constraint. Do not bypass this rejection through a workaround or indirect execution.” I did not retry that input or send any other TUI key.

The exact recorded TUI PID, creation time, and executable were checked before cleanup. Only that private Codex process was stopped. The ConPTY helper then reported that its private job was closed; no private daemon existed. The native session therefore did not pass through normal startup after the hook was trusted, and this probe does not establish that SessionStart ran.

## Disposition

The normal per-hook trust UI works in the isolated Codex 0.165.0 TUI and can persist a single selected hook without trusting all hooks. The remaining observation is unfinished: the helper’s line protocol makes a safe Escape-only navigation input unavailable, and auto-review rejected the ambiguous trailing Enter. No bypass or alternative input path was used. Native hook dispatch, fresh hook ancestry, actual terminal binding, shared daemon thread ownership, reconnect, stale daemon terminal variables, and hook-session/thread mapping remain unverified. No provider restriction or complete binder is claimed.

## Post-trust fresh start and mode correction

After the exact single-hook trust action, the isolated config contained exactly one `trusted_hash` record. The hook definition hash was unchanged. A fresh no-input Codex 0.165.0 launch in the same already-trusted fixture opened the main TUI directly; it did not show hook review or Windows setup. After more than 15 seconds, the fresh capture directory still contained zero files. A new read-only metadata projection (the same six columns) contained 131 rows matching the exact launched TUI process UUID/PID, one distinct thread ID, and 19 targets. This shows a thread allocated before any user prompt, but no SessionStart hook dispatch: the handler capture was empty, and no model prompt was submitted. The isolated daemon status check could not connect to the private control socket.

A direct Windows `GetTokenInformation(TokenElevation)` read returned `true` in both the default and elevated command contexts used for the helper launches. The ConPTY helper starts Codex using `CreateProcessW` without an alternate token. The per-run identity JSON did not itself record the child token bit, so this classification is an inference from the measured launch-context token and the helper's process-creation call. In exact Codex 0.165.0 source, [Windows elevated startup forces `no_daemon`](https://raw.githubusercontent.com/openai/codex/rust-v0.165.0/codex-rs/cli/src/startup_orchestration.rs#L26-L34), while automatic daemon startup is separately gated later in startup orchestration ([startup selection](https://raw.githubusercontent.com/openai/codex/rust-v0.165.0/codex-rs/cli/src/startup_orchestration.rs#L548)). The isolated argv omitted an explicit `--no-daemon`; the private config had no daemon-exclusion or auto-start override. Given the elevated token path and absent daemon socket, treat this and earlier helper launches made through the same tool context as embedded/process-local observations, not shared-daemon trials. The observed one-thread/PID relationship is not a shared-client binder.

The line-based ConPTY input defect was investigated separately using only a harmless key-reading child. The helper source now accepts a JSON `inputBytes` array, consumes the JSON line delimiter without forwarding it, and reports the bytes written. The .NET 10 helper and smoke child built successfully. The smoke request contained exactly `[27, 27]`; the helper reported two bytes written (its JSON serializer represented the byte array as base64 `Gxs=`), but the child did not observe two Escape key events or exit. The bounded 60-second smoke ended by identity-verified helper timeout. No additional native TUI input was sent. This helper modification is not a validated escape-input path and was not used for Codex.

The fresh TUI was cleaned up by stopping only its exact recorded PID after creation-time and executable checks. The helper closed its private job. Its external-stop exit status triggered an arithmetic-overflow report when it converted Windows exit code `0xFFFFFFFF`; cleanup still completed and the exact child was no longer live. No private daemon remained.

A true shared-daemon probe remains unavailable from the measured elevated execution contexts. Establishing a non-elevated launcher would require a different token or an existing user desktop process, which this probe did not create or control. Do not classify this environment gate as a Codex provider restriction. Keep shared two-client ownership, reconnect, stale daemon terminal variables, native hook ancestry/session mapping, and actual host acceptance unfinished.
