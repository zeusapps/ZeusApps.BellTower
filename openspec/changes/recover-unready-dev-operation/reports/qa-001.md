## Findings

### QA-001: Finalize retry cannot finish when the interrupted removal left only one record

- Severity: warning
- Related task / requirement: 2.3, design decision 3 (interrupted-finalize retry)
- Location: `scripts/install-dev.ps1` `Remove-OwnedCoordinationRecords` (lines 597-601) and `Invoke-Finalize` (retry gate near line 683 and `if (!$pendingExists -or !$restartExists)` refusal near line 700), at identity `43216f4f40a3`
- Expected / actual: design decision 3 and task 2.3 promise that an interrupted finalize is repaired by running Finalize again. `Remove-OwnedCoordinationRecords` deletes `pending.json` and then `restart.json`. An interruption between the two deletes leaves one record and a manifest in `finalized-without-tray`. The retry path then sees exactly one record, skips the `already-finalized` shortcut, and refuses with "an operation coordination record is missing; preserving any remaining record", pointing to `docs/releases.md`. Meanwhile `EnsureNoCoordinator` still blocks every new Preflight and Switch because of the leftover record. The maintainer is back in a manual-recovery state, which is the exact deadlock this change removes. The existing Switch and Rollback code has the same two-step removal, but the new Finalize retry promises to handle it.
- Reproduction: not executed (no fixture crosses the two deletes). From source, with a manifest in `finalized-without-tray`, one owned record deleted and the other left unchanged, run `-Action Finalize -OperationManifest <path>`.
- Evidence: source reading only. The retry test restores both records, or has none, but never one.
- Recommended correction: in the retry path (`state = finalized-without-tray`), accept one or two present records and remove each one that is present only after verifying its own bytes against the stored hash and its plan against the manifest. Add a fixture test that leaves one record (each of the two) and checks the retry removes it and that a following Preflight and Switch succeed. The same change may also apply to Rollback's end-of-operation removal if the orchestrator wants it, which is out of scope here.
- Relationship: none

### QA-002: The end-to-end acceptance for "Switch whose candidate never confirms, then Rollback whose original never confirms" is simulated, not executed through the script

- Severity: suggestion
- Related task / requirement: 2.4, spec scenarios "Restarted tray never confirms readiness" and "Switch whose candidate never became ready"
- Location: `tests/BellTower.Tests/Scripts/InstallDevScriptTests.Finalize.cs` `StuckRollback` (lines 309-319), `InstallDevFunctionHarness.ps1` scenarios `not-ready-*`
- Expected / actual: task 2.4 describes a Switch whose candidate never confirms, then a Rollback whose original never confirms, then Finalize. The test performs a successful Switch and interrupts the Rollback after the pointer phase. The readiness-deadline failure and its stored `trayNotReady` (message, manifest store) run only in the function harness with stubbed launcher and owner read. The real script's chain `Start-SelectedTray` deadline, then `New-NotReadyFailure` writing the manifest, then Finalize reading `trayNotReady` for the reason, is never executed as one flow. The `trayNotReady` reason path in Finalize is tested only by injecting JSON into the manifest. DEV-001 documents this limitation honestly, and I confirmed from source that the real rollback leaves `restored-monitoring-snapshot` (line 1343) with both records kept, so the fixture state is faithful.
- Reproduction: n/a (coverage observation).
- Evidence: the Finalize tests and the harness scenarios as listed above. No test combines a real readiness timeout with Finalize.
- Recommended correction: optional. The `$script:trayReadySeconds` seam already exists, so a disposable run with a stand-in tray command line could drive a real not-ready failure (the stand-in launcher is the stable launcher of the fixture). Otherwise record this as a documented evidence gap and rely on task 4.3 for the live path.
- Relationship: none
