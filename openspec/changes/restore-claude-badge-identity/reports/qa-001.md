## Findings

### QA-001: A generated Claude title is stored as a user title, wins precedence and pauses sync

- Severity: critical
- Related task / requirement: 2.1, 6.3; session-identity "App-owned names and optional change association" ("Generated or Bell Tower-managed native names SHALL NOT be mistaken for user overrides"); design decision 1
- Location: `integrations/claude-native/helper.mjs:~79` (`info.customTitle ?? null`), `src/BellTower/Sessions/ClaudeNameService.cs:~39-44`, `src/BellTower/Core/NativeNamePolicy.cs` (`Conflict`, `Pause`), `src/BellTower/Core/SessionIdentity.cs` (`Name => ManualName ?? NativeTitle ?? ...`); reviewed at `d307c34` working tree
- Expected / actual: Expected: a Claude-generated `ai-title` is not treated as an explicit native title and does not change precedence or pause synchronization. Actual: the SDK returns the generated title as `customTitle` (probe), `ClaudeNameService.Sync` on first read sees a non-blank name with no `NativeLastName`, calls `NativeNamePolicy.Pause`, which sets `NativeSyncEnabled=false`, `NativeTitle=<generated title>`, `NativeTitleSource="verified-user-name"`. `Name` then resolves to the generated title instead of `Role: change`. This hits exactly the sessions the change targets (conversations first seen after the first model turn, first-install and resume, or whenever the helper was unavailable at the first tick). The history path does not have the problem (it reads only `custom-title` records), so the two Claude paths disagree. The developer reported this as a "decision"; it is a direct breach of the quoted SHALL.
- Reproduction: (1) `$req | artifacts/qa-001-stage/node.exe artifacts/qa-001-stage/helper.mjs` with a transcript holding only `{"type":"ai-title","aiTitle":"Generated summary title"}` returns `current = "Generated summary title"`. (2) Probe `TakeOwnershipAfterGeneratedTitlePause` applies `Conflict` then `Pause` to that value and prints `name='Generated summary title' status=paused...`.
- Evidence: [qa-001-helper-aititle.txt](../evidence/qa-001-helper-aititle.txt), [qa-001-probe-results.txt](../evidence/qa-001-probe-results.txt) (`OWN after pause`), [qa-001-probes.cs.txt](../evidence/qa-001-probes.cs.txt)
- Recommended correction: Claude only: gate the user-title decision on a real `custom-title` record. Either extend the helper to report whether the title came from a custom-title entry (for example compare against the transcript's `custom-title` records, or call the SDK session listing field that separates custom from generated title if one exists), or have `ClaudeNameService` treat `current` as a user title only when the history reader has seen a non-ours `custom-title` record (`NativeTitleOffset >= 0` / `NativeTitleSource == claude-custom-title`). Add a test with a fake client returning a generated title and an `ai-title`-only transcript asserting `NativeSyncEnabled` stays true and `Name` stays role+subject. Re-evaluate Codex after a probe of whether 0.164.0 ever generates `thread.name`.
- Relationship: new (orchestrator flagged item (4) in the ledger)

### QA-002: The SDK fork "(fork)" title is read as an explicit user title

- Severity: warning
- Related task / requirement: 2.5, 6.3; same SHALL as QA-001; Implementation 004 open decision (5)
- Location: `src/BellTower/Sessions/IdentityHistoryReader.cs:~185-196` (`Merge`), `tests/BellTower.Tests/Sessions/IdentityHistoryTests.cs:~441`
- Expected / actual: Expected: a title that Bell Tower wrote for the parent (with SDK-added suffix " (fork)") is Bell Tower-managed text, not a user override. Actual: the fork's `custom-title` "Parent title (fork)" is not equal to the fork's `NativeLastName` (null), so `NativeTitle="Parent title (fork)"` is stored with source `claude-custom-title`, wins over role+change, and a forked conversation loses its automatic identity; the existing test asserts this outcome. `NativeNamePolicy.Ours` only matches exact `NativeLastName`/`NativePendingName`.
- Reproduction: the SDK `forkSession` fixture `claude-sdk-0.3.309-fork.jsonl` through `IdentityHistoryReader.Refresh` (the existing test does this).
- Evidence: source reading plus the existing test's own assertion; not independently re-executed.
- Recommended correction: decide fork identity policy (inherit parent's Bell Tower identity, or ignore a title that equals the parent's last managed name plus " (fork)" when `forkedFrom` is present) and encode it in a test. Needs an orchestrator/user decision before implementation.
- Relationship: new

### QA-003: Taking ownership or resetting cannot clear a paused native title

- Severity: warning
- Related task / requirement: 4.1, 4.4, 6.3; docs/session-identity.md "Ownership"
- Location: `src/BellTower/Sessions/NativeNameControl.cs`, `src/BellTower/Core/NativeNamePolicy.cs` (`Pause`, `Confirm`), `src/BellTower/Core/IdentityControls.cs` (`Reset`)
- Expected / actual: Expected: "pauses ... until you choose Use name in native chat" (docs) means Bell Tower's name replaces the native one. Actual: `SetEnabled(true)` only flips flags; `NativeTitle` stays set, so `identity.Name` (the desired name) still equals the old native title and the next sync writes it back unchanged. `Reset` deliberately keeps native titles. There is no path back to the automatic name except setting a manual name (the existing Codex test passes only because the fixture has a `ManualName`). Combined with QA-001 a generated title is permanent.
- Reproduction: probe `TakeOwnershipAfterGeneratedTitlePause`: after `Pause`, `NativeNameControl.SetEnabled(..., true)` and `SetColor(reset: true)` both leave `name='Generated summary title'`.
- Evidence: [qa-001-probe-results.txt](../evidence/qa-001-probe-results.txt) (`OWN after take ownership`, `OWN after reset`)
- Recommended correction: when the user takes ownership, clear `NativeTitle`/`NativeTitleSource` (and the history title offset) so the automatic or manual name is written; keep `Reset` as designed but document how a native title is released. Test for Claude and Codex without a manual name.
- Relationship: new; applies to both clients

### QA-004: A branch change re-selects older history work that is bound to the prior branch

- Severity: warning
- Related task / requirement: 3.3, 2.5; "Branch switches" scenario (branch-derived and touched-work evidence of the prior branch is invalidated)
- Location: `src/BellTower/Core/CheckoutPolicy.cs` `ApplyBranch` (resets `HistoryWorkOffset=-1` and `SelectionAt=null` but keeps the backward cursor), `src/BellTower/Sessions/IdentityHistoryReader.cs` `Satisfied` / `Merge`, `src/BellTower/Core/WorkPolicy.cs` (`SelectionAt is null` makes any history work "newer")
- Expected / actual: Expected: after the same checkout changes branch, work evidence recorded before the switch stays invalid. Actual: invalidation clears the active work and marks the backward walk unsatisfied; the walk resumes older chunks and applies the oldest work it finds as the new active work, bound to the new branch.
- Reproduction: probe `BranchSwitchThenOlderHistory`: transcript with work `old-z`, 700 KB chatter, work `new-a`. After the first tick `active=new-a`; after `ApplyBranch(..., "other-branch")` `active=` empty; after six more ticks `active=old-z source=history:edit`.
- Evidence: [qa-001-probe-results.txt](../evidence/qa-001-probe-results.txt) (`BRANCH ...` lines)
- Recommended correction: when invalidating branch-bound evidence, record a history floor (offset or timestamp) so history work at or before the invalidation point is never re-applied, or stop the backward walk. Add a regression test spanning at least two chunks.
- Relationship: new; shared policy, both clients (probe exercised Claude; Codex shares `Merge`/`WorkPolicy`)
