## Findings

### QA-250: A Codex fork applies copied pre-switch work when a read window sees the copied prefix before the fork's own boundary event, and never retracts it

- Severity: warning (narrow race window; Codex only; the work is bound to the new branch and only a later work action replaces it)
- Related task / requirement: ANALYSIS-150; tasks 2.5, 3.3; "Git branch and worktree context" (branch-bound evidence is invalidated)
- Location: `src/BellTower/Sessions/IdentityHistoryReader.cs:234-240` (boundary filter in `Merge`) and `:264` (`WorkPolicy.Apply` for resolved calls); `src/BellTower/Core/IdentityInheritance.cs:10-12` (floor copy does not help Codex because copied items are restamped)
- Expected / actual:
  - Expected: a fork child never shows pre-switch parent work, even transiently, or at least recovers once the boundary is seen.
  - Actual: the filter works only when the boundary offset is already known in the same or an earlier pass. If one read window contains the copied prefix with its work and result lines and the child's own `thread_settings_applied` has not been written yet (file growth between ticks, or a prefix larger than one window), `Merge` applies the work (`ActiveWork=change-a`, `Subject=change-a`, `WorkBranch=feature`). When the boundary arrives in a later tick, `ForkBoundaryOffset` is set, but the already applied `ActiveWork` (with `HistoryWorkOffset` below the boundary) is not cleared and persists until a newer work action. The result is the QA-004 misname class reached through a fork.
  - Not affected: the whole file already present, including a large prefix and a boundary beyond the newest window (the probes `large` and `tailwin`); Claude in every shape (floor via inherited timestamps).
- Reproduction: `pwsh -NoProfile -File artifacts/qa-004-probe/probe-fork-boundary.ps1 -Provider codex -Case growth -Bin src/BellTower/bin/Release/net10.0-windows` (source saved in [qa-004-probe-fork-boundary.ps1.txt](../evidence/qa-004-probe-fork-boundary.ps1.txt); copy it under `artifacts/` first). `growth-large` shows the same with a 400 KB prefix, where the third tick applies the work.
- Evidence: [qa-004-probe-results.txt](../evidence/qa-004-probe-results.txt), blocks `provider=codex case=growth` and `case=growth-large`: after `prefix only tick1` / `large prefix, no own boundary yet tick3`, `ActiveWork=change-a WorkSource=history:edit Boundary=-1`; after `boundary appended`, `Boundary=3172` (or `401172`) but `ActiveWork=change-a` is unchanged.
- Practicality: the fork's copied items and the settings snapshot are persisted in one batch (per the handoff's primary-source reading), so the window is the interval in which a tick reads a partially flushed batch. That is plausible but unproven; I could not observe a real `codex fork`. A rollout from a version without the event (documented fallback) has the same visible outcome permanently.
- Recommended correction (no edit by me):
  - When a proven Codex fork (`ForkParent` set) has no boundary yet, do not apply history work from records whose offset could still be before it. Hold the calls in `HistoryCalls` until the boundary is known, or until a post-copy marker or the file has settled; this keeps one shared rule.
  - Alternatively, when `ForkBoundaryOffset` becomes known, clear `ActiveWork` if `WorkSource` is `history:*` and `HistoryWorkOffset < ForkBoundaryOffset` (via `WorkPolicy.Clear`).
  - Add a growth test for both providers (prefix tick, then boundary tick) alongside `IdentityRecoveryPolicyTests`.
- Relationship: residual of ANALYSIS-150 (the Codex part), not a new category. The orchestrator decides whether to treat it as part of ANALYSIS-150 or a recorded limitation.
