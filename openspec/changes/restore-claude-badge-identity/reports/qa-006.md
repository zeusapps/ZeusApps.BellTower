## Assessment and limitations

Residual confirmed. Parent live change-b (strong, t=30) older than the fork time (t=40) and newer than Claude's original copy stamps (t=10), with a parent transcript that holds only change-a: Claude fork resolves change-b (`fork:Write`), Codex fork resolves change-a (`history:edit`), because Codex copies are restamped at fork time. When the parent's live work is newer than the fork time, both keep change-b.

Reachability and user impact: low. The shape needs parent live evidence that is not in the transcript the fork copied. When the parent transcript contains the change-b work (the normal case, since live evidence comes from the same tool calls), both clients resolve change-b (probe shape `real`). Remaining ways in are a hook-observed work record that the history reader does not parse, or a fork taken from an earlier point than the live work. In those cases the Codex badge shows the older copied change until the fork's first own work, which then gives change-b on both clients. No data is lost and it cannot be pinned wrongly. I rate it acceptable as a documented difference; the docs state the difference but not its condition (QA-350, suggestion). The Codex fork-from-an-earlier-point case was not tested, because no fork-point model exists in the fixtures.

Observation, not a finding: with a live-different parent (livedif) on Codex, large and growth-large histories show change-b (`fork:Write`) for the first one to two refresh ticks of the same walk, then change-a once the history catches up; this converges within one backward walk and the final value does not depend on timing. The late-parent shape (a contrived parent appearing after the child) still differs between clients (Claude keeps change-a, Codex retracts); it is unchanged from analysis-005 and out of this round's scope.
