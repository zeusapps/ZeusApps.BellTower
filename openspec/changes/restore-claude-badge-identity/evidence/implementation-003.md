## Intake items and decisions

- I-8 fixed (4.2 above).
- I-9 fixed. `StatusLineReader` uses the tray snapshot when it is fresh and matches the current title and palette; otherwise it renders Git context from `IO/GitHeadReader`, a process-free read of this conversation's own checkout (identity pin, resolver's saved checkout or launch directory) straight from `.git/HEAD` (directory or `gitdir:` file, linked-worktree detection via the `worktrees/<name>` git dir, detached = 7-character prefix). It starts no process, reads one small file, and consults no other conversation's data. Tests: no snapshot, stale snapshot rejected, outdated title rejected, fresh snapshot used, two conversations never borrow each other's snapshot or checkout, a fake `.git` that only a process-free reader understands, and agreement with `git` for main, linked worktree, subdirectory and detached HEAD. Decision (documented in `IdentityPresentationStore`): tray refresh runs about every 2 s, unchanged content is rewritten on a 15 s heartbeat, readers reject snapshots older than 30 s (`Staleness`, now public and asserted >= 2 x heartbeat). One missed heartbeat never causes a fallback; a stopped or wedged tray is noticed within 30 s, and the fallback is cheap and accurate anyway.
- I-10 implemented a real source (did not remove the branch). Hook `cwd` (documented required field in both providers' hook inputs) is recorded as `ProviderCwd` for main-thread events only (`CheckoutEvidence.Observe`, wired in `HookIngestor` and `CaptureConsumer`, idempotent; subagent events excluded). The tray resolver verifies it before use: it must be absolute, existing, in a different Git toplevel than the launch checkout, and be one of the launch repository's listed worktrees. A cwd inside the launch checkout (the D360 case where the agent never `cd`s) or in an unrelated repository is not evidence. Tests for both clients, including hook ingestion with and without `agent_id`.
- I-11 fixed: see 4.1. Catalog/list output now reports `NativeNameSynchronization`, `NativePresentationName`, `Checkout` and `CheckoutSource` for both clients (Claude's native presentation is the plain title; Codex keeps its worktree suffix). `CodexNamePump` was renamed `NativeNamePump` and drives both providers.
- I-12 fixed. New provider-neutral `Core/NativeNameSchedule` (due when the desired name changed, the verification interval elapsed, the user requested ownership, or the backoff expired; backoff 2, 5, 15, 30, 60 s as in `TerminalTitlePump`). The pump owns long-lived `ClaudeNameService` (verify every 5 minutes, since a helper spawn is expensive) and `CodexNameService` (every 10 s) with their schedules; `IClaudeNameClient` was extracted so tests use a fake. Tests: 25 idle ticks cause one Node read for Claude (and one connection for Codex), backoff and recovery for both, pump with mixed sessions. Services without a schedule (CLI and existing Codex tests) behave as before.
- D-1 fixed for both clients. `SessionIdentity.NativePendingName` is recorded before the provider write (`NativeNamePolicy.RecordIntent`), confirmed after (`Confirm` moves it to `NativeLastName`); `NativeNamePolicy.Ours` (last or pending) is used by the conflict check and by `IdentityHistoryReader`, so a history pass between the SDK write and the bookkeeping, or a crash after the write, never reads Bell Tower's own title as a user override. Codex had the same window (the next read would pause synchronization on its own name) and got the same ordering. Tests: history pass inside the write sees the pending name (Claude), pending visible during the Codex write, write-landed-then-failure recognized as ours on retry, real user rename still pauses both. Backward compatible: the field is optional JSON; older readers keep it as extension data.

## Open questions and risks for the orchestrator

1. A provider cwd in an unrelated repository is deliberately not used. The spec scenario "A session reports a different checkout" could be read to include it; confirm or relax (the display would then describe a repository unrelated to the launch).
2. When the agent never leaves the launch directory the checkout comes only from the work mapping; if the change folder exists in every worktree and the ticket is not in the change name, the result is "ambiguous" and the user attaches a checkout (by design, per spec).
3. `Reset` keeps live `ActiveWork` (an observed evidence, not a pin) and the role. If the intent is that reset also drops active work, say so; history recovery would re-derive the history-sourced part anyway.
4. `Configure` stores the Git toplevel of an attached path (a subdirectory is normalized to the worktree root) and rejects non-Git directories.
5. Claude `VerifyEvery` (5 min) and Codex (10 s) are interpretation choices for "change-driven"; a user rename in Claude's native UI is also seen through the history reader without a helper call.
6. `TestWorkspace.Dispose` now clears read-only attributes so repositories created by tests can be deleted (Git object files are read-only on Windows). `LegacyImportTests` redirects `Console.Out` briefly to prove nothing is emitted; it is the only test doing so.
7. Planning-artifact proposals (not edited): none required; Implementation 002 note about the "selects a change" scenario wording still stands.
