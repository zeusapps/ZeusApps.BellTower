## 1. Helper packaging

Change:
- `integrations/claude-native/helper.mjs` reworked: stdin capped at 64 KiB by bytes (previously it threw outside the `try`), strict request validation before any SDK work (UUID session, absolute directory and config directory, no NUL), title 1..100 characters without control characters, `expected` mandatory (string or null) when renaming, `CLAUDE_CONFIG_DIR` pinned before the SDK loads, stable stderr codes (`input-limit`, `invalid-request`, `invalid-target`, `invalid-title`, `sdk-unavailable`, `session-unavailable`, `native-name-conflict`, `claude-native-unavailable`), no write when the title already matches. Only `getSessionInfo` and `renameSession` are used; ctx7 `/websites/code_claude_en_agent-sdk` confirms both signatures (`options.dir`), that `renameSession` appends a `custom-title` entry and rejects empty titles, and that `SDKSessionInfo.customTitle` falls back to the generated title.
- `package.json` (exact pin), committed `package-lock.json` (SDK plus its eight optional native packages with integrity values), `.npmrc` (`legacy-peer-deps`, `omit=optional`, `ignore-scripts`), `runtime.json` (Node 24.13.0 win-x64 archive SHA-256 `ca274269...cb88`, `node.exe` SHA-256 `d14ba95c...ba11`, SDK integrity). I fetched the live `https://nodejs.org/dist/v24.13.0/SHASUMS256.txt`: it is byte-identical to the probe copy in `artifacts/identity-contract-probe/node-shasums.txt`, and the downloaded zip and its extracted `node.exe` match both pinned values. The SHASUMS signature file was not verified.
- Repository pattern: third-party payloads are restored or downloaded at build time with pins (NuGet `--locked-mode`), never committed. I followed that: no binaries are committed. `scripts/stage-claude-native.ps1` verifies lockfile vs `runtime.json`, uses a cached archive in `artifacts/native-cache` or downloads once from nodejs.org over HTTPS (SHA-256 checked before and after extraction; `-Offline` forbids downloading), runs `npm ci --ignore-scripts --omit=optional --legacy-peer-deps` in a scratch directory (integrity-checked by npm), and stages only `node.exe`, `NODE-LICENSE.txt`, the SDK package directory (includes `LICENSE.md`), `helper.mjs`, `package.json`, `package-lock.json`, `runtime.json`. Peer packages are not needed: with `--legacy-peer-deps` the SDK loads and renames (7,616 files and 46 MB shrink to 27 files).
- `scripts/package.ps1` stages into `versions/VERSION/claude-native/` and adds every file to `release.json`, so `Installation.VerifyFiles`, update extraction (which rejects uninventoried files) and rollback verify them. Size: `node.exe` is 90 MB (about 36 MB zipped); previous release ZIP was 106 MB, limits are 350 MB archive and 900 MB expanded, entry count stays well under 512.
- Missing helper: `ClaudeNameClient.Unavailable()` (node.exe, helper.mjs, SDK package version) feeds `ClaudeNameService` (status `unavailable: Claude native helper is not installed (node.exe missing)` etc., with the shared backoff, no exception) and `doctor` (`claude.nativeHelper`). A helper-reported `native-name-conflict` now retries on the backed-off schedule instead of marking the provider unavailable.
- `.gitignore` gained `integrations/claude-native/node_modules/` (defensive; staging uses a scratch directory).

Tests: `integrations/claude-native/helper.test.mjs` (8, run against the staged payload with an isolated fake profile): read writes nothing; rename appends exactly the SDK `custom-title` record, preserves existing bytes, is idempotent; conflict never writes; exact session/directory/config targeting (other session, wrong directory, empty config, nothing created in the process profile); 13 invalid-request shapes; input bound; missing SDK; and the documented limit that an `ai-title` is returned as `customTitle`. `ClaudeNameClientTests` (4): unavailable reasons per missing piece and version mismatch, service reports unavailable and leaves identity/transcript untouched, conflict retries without `unavailable`, and the client/helper process protocol against a stub helper using the PATH `node.exe` (the test fails with a clear message if `node.exe` is not on PATH). `NativeNameTests` gained the mixed case: a missing Claude helper is explicit and the Codex session stays synchronized.

## 2. Unverified history gaps (primary sources only)

All Codex facts come from `openai/codex` at tag `rust-v0.164.0` (the installed version) fetched with `gh api`, plus ctx7 `/openai/codex`; no real transcript was read.

- Codex `apply_patch` result text: VERIFIED and enabled. `core/tests/suite/apply_patch_cli.rs` asserts the freeform result `Exit code: 0\nWall time: N seconds\nOutput:\nSuccess. Updated the following files:\nA path...`; `core/src/tools/mod.rs` shows the optional `Total output lines: N` line; `protocol/src/models.rs` serializes `custom_tool_call_output.output` as a string or content-item array; `rollout/src/policy.rs` persists custom tool call items regardless of history mode. `IdentityHistoryReader` now reads `custom_tool_call(apply_patch)` plus its result; success requires the anchored exact header (`PatchApplied` regex), everything else discards the call. Relative patch paths still resolve against the launch directory (the rollout has no turn cwd). Tests: exact-success matrix (verification failure, `Exit code: 1`, marker without header, bare marker all rejected), content-array and CRLF/`Total output lines` forms. Fixture shape in `IdentityFixtures.Codex.PatchResult`; provenance updated. No live capture of the installed binary.
- Codex history native title: VERIFIED ABSENT from rollouts at 0.164.0 (no persisted `EventMsg` for a name; names go to `session_index.jsonl`, an internal append-only file). Kept disabled in history; managed runtimes read through the thread name service. Unmanaged sessions: unverified. Closing evidence: a documented or supported read for unmanaged sessions (reading the internal index would be unsupported).
- Non-`exec_command` Codex shell tools: at 0.164.0 `tools/handlers/mod.rs` registers only `unified_exec` (`exec_command`, `write_stdin`); `shell`, `shell_command` and `local_shell` handlers do not exist at that tag. So nothing to enable for this version; other versions stay unverified and disabled. A yielded `exec_command` (session id, no exit header) simply never produces a result and cannot select.
- Codex failed-patch PostToolUse: VERIFIED it does not fire. `core/src/tools/registry.rs` computes the PostToolUse payload only when `success` is true, and `tools/events.rs` returns `Err(RespondToModel)` for any non-zero exit, verification failure, rejection or denial. This matches the existing successful-post-only ingestion; the capability string says so.
- Claude fork `sessionId` rewriting: VERIFIED for the SDK operation only. Docs ("forkSession is not a byte copy ... rewrites every sessionId") and a reproducible probe of SDK 0.3.309 `forkSession` on a disposable transcript: every record gets the fork's `sessionId`, uuids are remapped, `forkedFrom` is added and a `custom-title` "<title> (fork)" is appended. Fixture `claude-sdk-0.3.309-fork.jsonl` (real output, redacted) and a test show the fork recovers inherited work and the "(fork)" native title while a session bound to the parent's id does not read the fork's records. Interactive `claude --fork-session` and `/branch` are NOT verified (needs an authenticated model turn); if they do not rewrite ids, a fork loses inherited evidence (conservative). Note the "(fork)" title will be read as a user native title for the fork's identity (first-ownership pause); decision for the orchestrator whether a fork should inherit the parent's Bell Tower identity instead.
