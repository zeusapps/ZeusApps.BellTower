# Native Codex fallback investigation 005

## Scope and result

This is an evidence-only follow-up for task 2.1. It traces the version-pinned Codex CLI `0.164.0` shell override and app-server environment API to determine whether an isolated process can select `cmd.exe` or Git Bash for native hook dispatch. No product, test, provider, global shell, PATH, system, or user configuration was changed. No native fallback probe was run because the available public local-CLI/app-server paths did not provide a supported way to select either shell.

**Result: partial; native cmd/Bash hook coverage remains unverified.** The source confirms that Codex can carry an internal shell override and can use an executor-reported environment shell. It does not expose either mechanism as a supported local CLI or app-server request setting in the inspected `rust-v0.164.0` paths. This is not evidence of a universal provider restriction and does not waive task 2.1.

## Version-pinned source trace

The inspected source is the official [`rust-v0.164.0` tag](https://github.com/openai/codex/tree/rust-v0.164.0), matching the installed Codex CLI version recorded by the change.

1. **The internal override is not a normal thread option.** `ThreadSpawnRequest` owns a private `user_shell_override` field. Its normal constructor sets it to `None`. The only assignments in `core/thread_manager.rs` are in `start_thread_with_user_shell_override_for_tests` and `resume_legacy_thread_from_rollout_with_user_shell_override_for_tests`; both APIs are explicitly test-only. Normal thread creation and resume construct requests with the default. See [`thread_manager.rs`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/thread_manager.rs#L339-L373) and [the test-only override methods](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/thread_manager.rs#L1308-L1348).

2. **The shell override is consumed at session initialization.** `SessionSpawnArgs` forwards the internal value into `SessionConfiguration`. Session startup chooses `user_shell_override` when present, otherwise `default_user_shell()`, then initializes `ThreadEnvironments` with that shell as its default. Hooks receive the selected turn environment's shell program and arguments, as described by native investigation 003. This is an internal Rust caller path, not a CLI argument or a mutable thread setting. See [`session/mod.rs`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/session/mod.rs) and [`session/session.rs`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/session/session.rs).

3. **The public app-server parameters do not set this override.** The pinned [`ThreadStartParams`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L59-L139) exposes model, cwd, workspace roots, policies, ordinary config overrides, and related thread metadata; it has no shell or `userShell` input. The pinned [`TurnEnvironmentParams`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L90-L96) contains only `environmentId`, `cwd`, and `runtimeWorkspaceRoots`. The locally retained protocol schema likewise lists `userShell` only in response/notification shapes, not request parameters.

4. **Executor metadata is a distinct, host-supplied route.** When an environment is resolved, core converts the environment's reported `ShellInfo` into a `Shell` (`environment_selection.rs`, [`pinned source`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/environment_selection.rs#L907-L943); [`Shell::from_environment_shell_info`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/shell.rs#L57-L71)). The app-server request can select a registered environment by ID, but the inspected request does not register an executor or set its shell metadata. An external executor that reports `cmd` or `bash` would be a different host mode; no such executor is available in this isolated local CLI setup.

5. **A PATH-only failure cannot safely prove the cmd fallback.** On Windows, `default_user_shell_from_path` calls PowerShell discovery and falls back to `ultimate_fallback_shell()` only when discovery returns `None`. PowerShell discovery searches `PATH` and then fixed PowerShell 7 and Windows PowerShell locations. The resolver chooses `ShellType::PowerShell` based on discovery; it does not launch a candidate to validate its actual shell language first. See [`shell_detect.rs`](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/shell-command/src/shell_detect.rs#L189-L211), [PowerShell discovery](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/shell-command/src/shell_detect.rs#L245-L272), and [Windows default/fallback selection](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/shell-command/src/shell_detect.rs#L295-L353). Therefore making a PATH candidate fail or wrapping/renaming `cmd.exe` as a PowerShell candidate would not establish native cmd dispatch and could mislabel the runner.

## Probe decision and limits

- No native cmd or Bash hook dispatch was attempted. A supported process-local selection route was not found in the CLI or public app-server inputs, while the internal override setters are test-only.
- The existing installed PowerShell locations were not altered, masked, or removed. No provider hook registration or user data was touched.
- The host runtime audit found no isolated Windows sandbox executable, no available Docker engine, and no registered WSL distribution. No alternate OS runtime was started or installed.
- The Context7 library lookup for Codex CLI documentation returned no output before its process was interrupted. The version-pinned official source above supplies the relevant implementation evidence; current unversioned documentation was not used to infer `0.164.0` behavior.
- A separate executor/session host that can safely register a `cmd` or `bash` environment may provide a test route, but its protocol, shell identity, path mappings, and native hook dispatch must first be proven. Direct shell recorder runs remain adapter controls, not Codex native coverage.

No acceptance, provider restriction, or task exception is inferred. Existing native PowerShell evidence and user live acceptance remain valid for their recorded modes only; native cmd/Bash coverage remains open.
