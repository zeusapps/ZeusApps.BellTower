## Findings

### QA-050: An unrelated foreground operation clears an attributed approval wait

- Severity: warning
- Related task / requirement: 4.2; [causal ordering delta](../specs/session-tracking/spec.md), especially correlated approval resolution
- Location: `src/BellTower/Core/SessionReducer.cs:314-328`; reproducer `tests/BellTower.Tests/Core/ReducerTests.cs:141-148`
- Expected / actual: a permission wait tied to one operation stays pending when a different, uncorrelated ToolStart arrives. The current `IsPermissionResumption` treats any different operation ID as resumption for an identified wait, and treats an operation outside a candidate set the same way. In the identified-wait fixture, the unrelated operation has the same fingerprint and the wait is removed before its result arrives.
- Reproduction: run the bounded filter recorded in the checks above. The existing identified-wait fixture creates a confirmed wait for operation `blocked` with fingerprint `same`, then applies a later ToolStart for `other` with the same fingerprint. Actual reason is null instead of Permission. The backdated-restore fixture also fails because its wait is removed by the first unrelated start before replay-window compaction.
- Evidence: full suite 991/1000; bounded reducer filter 0/2 passed; source branches at lines 320-328. The independent eight-variant reproduction and causal-window sequence are documented in [analysis recheck 002](analysis-002.md) and [its reproduction evidence](../evidence/analysis-002-reproductions.md).
- Recommended correction: preserve identified and candidate waits on unrelated operation starts, including same-fingerprint starts with conflicting IDs. Retain same-operation late-start protection and the existing no-ID/no-fingerprint foreground activity fallback; resolve through correlated results or other independently established resolution evidence. Update the new different-operation assertions and old same/candidate-start expectations to keep the wait until correlated completion.
- Relationship: same issue as canonical `ANALYSIS-050`. The backdated-restore failure is a manifestation of this broad-clear branch, not a separate replay-window finding.

## Assessment and limitations

The three original analyzer corrections are verified: unrelated subagent starts preserve foreground waits, Codex accepts the serializer-generated special-character TOML probe configuration, and malformed receipt shapes no longer crash reporting. The native pass/failure settings snapshot fixture passed for both providers. The Release build and scoped formatting checks passed.

The target is not ready for acceptance. QA-050 is a genuine correlation defect: a wholly different main-thread operation can clear an identified approval wait. The full suite failed 9 of 1000 tests after the native executable prerequisite was supplied. Seven failures represent stale assertions that treat a late same/candidate ToolStart as resolution; preserve those scenarios but change the expectations to keep the wait until correlated results arrive. The unrelated-ID and backdated-restore failures are real manifestations of QA-050; the latter is removed by the first unrelated start, before causal-window compaction.

The required latency budget still fails, and Codex argv support, Claude Code's own hook runner, and user-operated post-migration mixed-session acceptance remain pending. No production settings, user installation, user data or live agent processes were changed. The only additional build artifact was under ignored `src/BellTower.Ingress/bin/` output. Implementation identity matched before and after this review.
