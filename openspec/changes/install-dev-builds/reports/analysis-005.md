## Findings

### ANALYSIS-200 (recheck): Normal Rollback still changes monitoring before its owned-record boundary, and relative tray roots can bypass draining

- Severity: warning; blocking agreed safe startup/refusal behavior in tasks 4.1/4.3.
- Locations at the reviewed identity: `scripts/install-dev.ps1:625–675`, especially `:640–661`, `:663–674`; `src/BellTower/IO/TrayInvocationCommand.cs:77–79`, `:105–110`; `scripts/install-dev.ps1:226–227`; `src/BellTower/IO/DataPaths.cs:16–20`.
- Observation, state boundary: the `rollback-state-restore` call at `:627` occurs only when the original pointer is already selected. A normal Rollback of the candidate enters `:637` onward, stops the tray, performs a bare drain at `:643`, waits for setup/state/presentation locks, then rewrites `state.json` and its backup at `:655–658`. It does not validate/renew the owned record pair through `Assert-OperationBoundary` before these writes. If a marker changes during stopping, draining or a data-lock wait, the next exact marker check is `:664`, after monitoring has changed. The corrected plan explicitly requires refusal before monitoring mutation for that case.
- Observation, recovery state: monitoring restoration is not recorded before the `rollback-before-selection` barrier or its subsequent refusal. The manifest remains `running-candidate` (or another pre-restoration state) until both pointer restoration and `:674` succeed. On drift/unknown-child failure at `:664`, selection is still candidate while monitoring has been restored, but the record does not report that intermediate state. The drain failure text at `:251` also unconditionally says monitoring was left intact, which is false on this path. This is a recovery-state defect, not an editorial wording suggestion.
- Observation, classification: `Classify` accepts relative or drive-relative `--data-dir` and compares `Path.GetFullPath` results using the installer process's current directory. The actual tray uses `DataPaths` in its own process. For example, a delayed tray started with working directory `D:/trial/install` and `--data-dir ../data` resolves to `D:/trial/data`; an installer running from the repository resolves the same argument elsewhere, returns `OtherDataDirectory`, and omits that child from the drain. Neither the target working directory nor proof of another data root is available to this classifier. Unknown roots must not become a harmless exclusion.
- Proposed correction and benefit: put the complete owned-record renewal/drain boundary on the normal monitoring-restoration path outside its data locks, then preserve the actual restored-state phase before a later pointer refusal. Reject non-fully-qualified tray data roots unless the exact target-process resolution context is independently verified; do not resolve them against the installer's directory. Retain corrected rooted argv handling and short lock windows.
- Behavior-preservation risks: keep normal event/session helpers excluded, known other data roots untouched, old-order children fenced, and state/pointer preservation distinct at each failure point. Do not hold process waits under data/launch locks or widen hook budgets.
- Evidence type: concrete source/control-flow and primary documented path semantics; no analyzer-executed native reproduction claimed.
- Verification: hold the disposable state lock during normal Rollback, change either owned marker before releasing it, and assert both monitoring/pointer bytes remain unchanged. Separately change a marker after restoration at the existing barrier and assert candidate pointer plus an honest restored-monitoring phase. Exercise delayed children using relative/drive-relative roots with different process working directories; safely refuse ambiguity rather than skip them.
- Relationship: incomplete correction of canonical ANALYSIS-200, overlapping QA-201 and earlier ANALYSIS-150/QA-150. Switch's final pointer boundary, rooted Unicode argv and normal restart receipts are corrected portions of the original finding.

### ANALYSIS-201 (recheck): A second recovery failure uses a stale phase, and interrupted candidate restart ownership cannot find its recorded launcher

- Severity: warning; blocking supported same-manifest recovery in task 4.1 and design decision 7.
- Locations at the reviewed identity: `scripts/install-dev.ps1:477–499`, `:541–553`, `:273–274`, `:295–302`, `:523–526`, `:691–695`.
- Observation, phase: while recovering an interrupted Switch, `:548` persists the old `coordinationPhase='Switch'` and `:549` its old target. The next plan at `:551–553` changes the target/contract/owner to the Rollback original version. There is no later update of the manifest's phase to Rollback. If this recovery restores the original pointer but its original restart fails, the next Rollback derives candidate from the stale Switch phase at `:477–479` and rejects its own original-target records at `:499`. The new idempotent already-original branch is unreachable in this case. The developer smoke tests Switch failure followed by successful recovery, and a separate fresh Rollback failure followed by retry; it does not cover failure of the first recovery itself.
- Observation, interrupted restart: `Start-SelectedTray` records `restartLauncher` at `:273`, then verifies the running candidate before its caller persists `candidateTray` at `:694`. A failure/interruption during that interval leaves an operation-owned live candidate plus recorded `restartLauncher`, but no `candidateTray`. At Rollback entry, `Assert-OwnedCandidate` falls back to `candidateLauncher` at `:299–302`. No assignment to `candidateLauncher` exists anywhere in this installer, so the matching operation-owned candidate is refused as unrecorded. The existing failure injection stops before launch and therefore cannot expose this interval.
- Proposed correction and benefit: publish the current phase/target coherently with its expected record transition, so a failed recovery can itself resume from its validated current phase. Use the actually persisted restart receipt for the interrupted-candidate fallback, requiring its expected version/activation, exact live launcher identity, tray PID/start/data/image and ancestry. Do not adopt or stop a foreign tray to force recovery through.
- Behavior-preservation risks: retain full pair semantic/byte checks before renewal/deletion and proven-ended coordinator takeover; never accept arbitrary candidate/original targets or remove drifted records. Preserve the original-state idempotency already added.
- Evidence type: deterministic field/control-flow mismatches in source, not measured native failures.
- Verification: inject candidate restart failure; inject original restart failure during the resulting recovery Rollback; then retry the same manifest after its owner ends. It must complete from the original-pointer phase with no repeated snapshot restore. Separately interrupt/fail after the candidate has published valid presence but before `candidateTray` persistence, and verify same-manifest Rollback recognizes only its exact recorded launcher descendant. Retain negative activation/lineage tests and marker drift preservation.
- Relationship: incomplete recovery correction/regression under canonical ANALYSIS-201 and overlapping QA-202. Ordinary full tuple/hash drift rejection and a fresh Rollback's original-target retry are corrected portions of the original finding.
