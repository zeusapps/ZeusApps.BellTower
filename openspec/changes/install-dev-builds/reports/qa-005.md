## Findings

### QA-250: normal Rollback restores monitoring state before validating changed operation records

- Severity: warning; blocks the agreed pre-mutation recovery safety requirement.
- Related task / requirement: tasks 4.1 and 4.3; design §7; ANALYSIS-200.
- Location: `scripts/install-dev.ps1:640–661` at reviewed identity, especially the normal Rollback path before `:664`.
- Expected / actual: if a restart marker changes while Rollback is stopping/draining the tray or waiting for data locks, Rollback should validate its owned record pair before changing monitoring state. Actual: after detecting the changed bytes at the later boundary, it had already restored the monitoring snapshot. Selection stayed on the candidate, the manifest still reported `running-candidate`, and the changed marker remained. The refusal prevented pointer mutation but did not prevent the earlier monitoring-state write.
- Reproduction: on a disposable native install, Switch to candidate; hold the setup data lock; start Rollback and wait until it blocks after tray stop; append bytes to its restart marker; release the lock. Rollback exits nonzero after state restoration. See [QA drift probe](../evidence/qa-005-rollback-drift.ps1) and disposable state `artifacts/qa-005/rollback-drift-46d6256a90fd43a081c7d0c1e22b7923`.
- Evidence: marker drift caused refusal; candidate pointer hash did not change; monitoring backup was restored; operation manifest phase was stale at `running-candidate`; drifted marker and pending record remained.
- Recommended correction: assert/renew the complete owned record pair at a boundary before monitoring restoration, outside data locks; record the actual restored-monitoring phase before any later barrier/refusal. Keep refusal before pointer mutation.
- Relationship: independent runtime confirmation and refinement of canonical ANALYSIS-200; related to the normal-Rollback boundary defect, not QA-201's delayed Switch child ordering.

### QA-251: failed original restart during Switch recovery leaves retry bound to the wrong phase target

- Severity: warning; blocks idempotent recovery after a second restart failure.
- Related task / requirement: task 4.1; design §7; ANALYSIS-201.
- Location: `scripts/install-dev.ps1:548–553` at reviewed identity.
- Expected / actual: after a failed Switch is recovered by Rollback, if restarting the original payload also fails, a later retry using the same manifest should recognize the recorded original target and finish safely. Actual: recovery wrote original-target restart/pending records and restored the original pointer, but retained `coordinationPhase=Switch` and the candidate `coordinationPhaseTarget`. The retry derived the candidate target and refused its own original-target records; the records remained stranded.
- Reproduction: run native Switch with candidate restart failure; invoke recovery Rollback for that manifest while original restart is also configured to fail; remove failure injection and retry the same manifest. The second recovery attempt exits 1 with an owned-record target/contract mismatch. See [QA nested recovery probe](../evidence/qa-005-nested-switch-recovery.ps1).
- Evidence: after the injected original-restart failure, pointer selected original `0.1.9003`, manifest phase was `restored-monitoring-snapshot`, coordination phase remained `Switch`, target remained candidate `0.1.9001`, and both owned records described original target `0.1.9003`; same-manifest retry refused and left them present.
- Recommended correction: persist the recovery phase and target as Rollback/original before publishing original-target records; make retries resume the already-restored phase idempotently without repeating monitoring restoration.
- Relationship: independent native runtime reproduction of canonical ANALYSIS-201's nested failed-Switch recovery case.
