## Findings

### QA-001: Temporary eligibility loss resets the same episode's reminder history

- Severity: warning
- Related task / requirement: tasks 2.1–2.3; Persistent bounded reminder receipts
- Location: `src/BellTower/Core/ReminderPolicy.cs:66-70` at reviewed identity `dd04597165e1`
- Expected / actual: A per-episode ordinal and stable receipt ID should survive a temporary tick where a still-unresolved episode is not currently eligible. The policy deletes receipts whenever the episode is absent from the current actionable set. A transient unverified attachment or temporarily unconfirmed Codex permission can therefore reset the count and later permit more than the configured three reminders for the same episode; the next receipt also has a new escalation ID.
- Reproduction: Advance an episode to ordinal one, advance one tick with the same episode absent/ineligible, then advance again after it becomes eligible. The second eligible period creates a fresh receipt at ordinal zero.
- Evidence: `ReminderPolicy.Advance` removes every receipt for which `active.TryGetValue` fails. `StateStore.AdvanceReminders` intentionally filters to currently `verified-live`/actionable sessions before passing them to that policy.
- Recommended correction: Retain receipts for unresolved same-episode records through temporary ineligibility; prune only on proven episode resolution/change, acknowledgment, confirmed end, or a documented retention bound. Add a recovery fixture that proves ordinal and receipt ID are stable.
- Relationship: Duplicate of analyzer finding ANALYSIS-001; orchestrator owns canonical triage.

### QA-002: Escalation lookup can return a candidate after current permission confirmation is lost

- Severity: warning
- Related task / requirement: task 3.1; Escalation eligibility interface
- Location: `src/BellTower/IO/StateStore.cs:47-56` at reviewed identity `dd04597165e1`
- Expected / actual: The candidate should be returned only while its episode remains currently actionable and confirmed. `Escalations()` checks the persisted session's ended/health/episode/acknowledgment fields, but does not check `RequiresAttention` or current owning-runtime approval. `NativePermissionPending` is transient and excluded from serialized snapshots, so a Codex request that now reports no pending human approval may still produce a candidate from the older persisted confirmed wait until another scheduler tick retires it.
- Reproduction: Persist a confirmed Codex permission episode and eligible escalation; make the fresh current runtime projection report `NativePermissionPending=false`; call `Escalations()` before a subsequent reminder advance. The query reloads the stored session and can return its stale candidate.
- Evidence: Source inspection of the candidate filter and `[JsonIgnore]` transient `NativePermissionPending` field in `SessionState`; existing tests cover acknowledgment, not loss of current confirmation.
- Recommended correction: Bind candidate enumeration to fresh current actionable projections (including the current Codex confirmation and enabled policy), or otherwise synchronously invalidate the candidate when that evidence changes. Add a stale-current-confirmation fixture.
- Relationship: Duplicate of analyzer finding ANALYSIS-002; orchestrator owns canonical triage.

### QA-003: Future native input ticks can be treated as long idle after uptime wraps

- Severity: warning
- Related task / requirement: task 1.3; Idle-gated reminder eligibility
- Location: `src/BellTower/Tray/WindowsUserIdleSource.cs:51-54` at reviewed identity `dd04597165e1`
- Expected / actual: An inconsistent last-input tick should yield unknown. The current code accepts unsigned elapsed whenever the result is less than full system uptime. Once uptime exceeds the 32-bit tick range, a future tick can wrap to a value less than uptime and appear as approximately 49.7 days of inactivity.
- Reproduction: Evaluate `Elapsed(5_000_000_000, 705_042_704)`. The low 32 bits of uptime are `705_032_704`; the last-input tick is 10 seconds in the future, but subtraction yields `4_294_957_296` ms, which passes the current uptime comparison.
- Evidence: Deterministic arithmetic reproduction from the reviewed function. The tests cover one legitimate wrap and a future tick only while uptime is short (`Elapsed(10_000, 11_000)`), so they miss this case.
- Recommended correction: Add an explicit disambiguation/bound for non-monotonic or future native ticks after uptime wraps, and a regression test using uptime greater than `uint.MaxValue`.
- Relationship: Duplicate of analyzer finding ANALYSIS-003; orchestrator owns canonical triage.

### QA-004: Playback revalidation can reuse an idle sample taken before recent input

- Severity: warning
- Related task / requirement: tasks 1.3, 2.4 and 2.5; Recent input and playback revalidation scenarios
- Location: `src/BellTower/Tray/TrayApplication.cs:367-379` at reviewed identity `dd04597165e1`
- Expected / actual: The playback guard should use a current idle observation. `CurrentIdle` calls the source again only when the cached snapshot is over 500 ms old, so an input event just after an inactive observation can leave that stale value usable by `IsCurrentAlert` while its timestamp is still under the 500 ms limit. The scheduled reminder can then proceed despite recent input.
- Reproduction: Let the idle source return a value above threshold, queue a due reminder, then change the source to recent input within 500 ms and invoke the validity callback. The callback returns true using the old `idleSnapshot` without querying the source.
- Evidence: The tray caches `idleSnapshot` at tick time and `CurrentIdle` explicitly reuses it for up to 500 ms; there is no test changing input between enqueue and sink playback.
- Recommended correction: Revalidate idle state at playback using a fresh or sufficiently synchronized source observation and add an injected queue fixture where recent input invalidates a queued reminder.
- Relationship: Duplicate of analyzer finding ANALYSIS-004; orchestrator owns canonical triage.

### QA-005: Saving the settings dialog drops unknown reminder fields

- Severity: warning
- Related task / requirement: tasks 1.2 and 3.2; configuration unknown-field preservation
- Location: `src/BellTower/Tray/ReminderSettingsForm.cs:89-99` at reviewed identity `dd04597165e1`
- Expected / actual: Saving known reminder settings should preserve unknown fields for forward-compatible config round-trips. `Save()` replaces `value.Reminders` with a new `ReminderSettings`, dropping its `AdditionalData`; the store-level test updates a known property and therefore does not exercise this UI path.
- Reproduction: Read a config whose `reminders` object contains `futureReminder`, open and save the reminder settings form, then read the config. The form's replacement object contains no `AdditionalData`, so `futureReminder` is lost.
- Evidence: Source inspection; `ReminderSettings` has `JsonExtensionData`, and the storage test preserves it only when mutating a field on the existing object.
- Recommended correction: Update fields on the existing `ReminderSettings` object or copy its extension data, then add a settings-save round-trip test with an unknown nested property.
- Relationship: Duplicate of analyzer finding ANALYSIS-005; orchestrator owns canonical triage.

### QA-006: Disconnected-session behavior has no deterministic test

- Severity: warning
- Related task / requirement: task 1.3; idle state recent/idle/unknown/disconnected verification
- Location: `src/BellTower/Tray/WindowsUserIdleSource.cs:70-85` and `tests/BellTower.Tests/Core/ReminderPolicyTests.cs:156-163` at reviewed identity `dd04597165e1`
- Expected / actual: Current session active/disconnected status, WTS query failure, and unknown handling should be testable using an injected native boundary. The fixture only checks tick arithmetic and that an injected generic exception gives unknown. The WTS call is embedded in the native method, so no fixture proves that a disconnected status or invalid WTS result fails closed.
- Reproduction: Review the reminder tests for WTS/disconnected cases; none exercise `WTSQuerySessionInformationW` result mapping. The policy request explicitly requires a disconnected-session fixture.
- Evidence: `ReminderPolicyTests` contains a single input-source test which asserts unsigned wrap, a short-uptime future tick, and a thrown observer. There are no `WindowsUserIdleSource` tests for active/disconnected/query failure/stale observation mapping.
- Recommended correction: Extract and test a deterministic WTS/native-result mapping seam or inject the WTS and input calls; cover active, disconnected, malformed/missing buffer, query error, stale result, and unknown input for shared policy.
- Relationship: No duplicate known; coverage gap only, not proof that the native WTS implementation fails.

### QA-007: Persisted restart/replay behavior is covered only by an in-memory policy fixture

- Severity: warning
- Related task / requirement: tasks 2.2 and 2.3; Persistent bounded reminder receipts
- Location: `tests/BellTower.Tests/Core/ReminderPolicyTests.cs:66-85` at reviewed identity `dd04597165e1`
- Expected / actual: Restart acceptance should serialize the receipt, construct a fresh store/run, and prove that crash/replay neither duplicates an ordinal nor emits overdue reminders. `RestartAndReenableMoveExpiredDeadlinesIntoFutureWithoutCatchUp` calls the policy twice on the same `AppState`, so it does not cross the persistence/reload boundary. Other receipt tests serialize snapshots but do not combine that with run-ID restart/no-catch-up behavior.
- Reproduction: Inspect the restart test: it retains the same object and changes `run-1` to `run-2`; it never saves/reloads between calls.
- Evidence: Existing state-store tests prove individual receipt persistence and unknown-field reload; they do not demonstrate restart replay as an integrated scenario.
- Recommended correction: Add a disposable-state integration fixture that saves a due receipt, reloads through a new `StateStore` with a new run ID after a long absence, asserts no immediate scheduled item, then advances to the new deadline and checks a single next ordinal/stable ID.
- Relationship: No duplicate known; acceptance evidence gap.

### QA-008: Receipt pruning bound is not covered by a test

- Severity: warning
- Related task / requirement: task 3.2; bounded persisted receipt state
- Location: `src/BellTower/Core/ReminderPolicy.cs:116-121` and `tests/BellTower.Tests/Core/ReminderPolicyTests.cs` at reviewed identity `dd04597165e1`
- Expected / actual: The 10,000-record limit should preserve current episode state predictably while pruning old receipts. The implementation takes the first lexicographic keys when over the limit, but no test verifies the bound or ensures that active receipts are not pruned in favor of unrelated records.
- Reproduction: No test constructs more than 10,000 reminder receipts or calls `ReminderPolicy.Advance` to exercise its pruning branch.
- Evidence: `ReminderPolicy.Advance` has an explicit count-bound removal loop; the assigned test files contain no bound/pruning case.
- Recommended correction: Add a deterministic over-limit fixture that verifies the count remains bounded and documents/preserves active episodes while pruning the intended oldest/inactive receipts.
- Relationship: No duplicate known; acceptance evidence gap.
