# Architecture

Bell Tower uses a .NET 10 Windows application, a small stable launcher, a shared distribution-contract library, and separate xUnit/packaged acceptance projects. WorkLog is an organizational reference and has no project/runtime dependency.

| Area | Responsibility |
| --- | --- |
| Core | Provider-neutral observations, session activity/attention reduction, palettes, grace and episode/audio policy |
| IO | Separate snapshot/attachment/identity/config stores, atomic local files, serialized state transactions, process identity/liveness, bounded logs, read-only Git queries |
| Providers | Sanitize Claude/Codex hook JSON; render the ANSI Claude status line |
| Sessions | Agent launching and lifecycle; session listing, naming and focus actions |
| Hosts | Capture attachments; route through ITerminalNavigator; separate VS Code request protocol and Windows Terminal activation; scoped title helper |
| Tray | Nonactivating strip, session overview, position/refitting, serialized chime/SAPI voice, silent audio sink |
| Setup | Plan/review/apply hooks, badge, PowerShell module/imports, terminal profiles and VS Code bridge; preserve unrelated settings; legacy metadata import |
| Cli | System.CommandLine command classes, typed options/validation, generated help, neutral hook errors, literal agent argument forwarding |
| Diagnostics | Report setup observations and capability limits without modifying configuration |
| vscode | Dependency-free local registration/focus bridge, separately tested with Node's built-in runner |

Hook invocations extract only needed fields and publish unique normalized records to the inbox. Tool/prompt bodies and transcript contents are not retained. Tool input is hashed in a canonical order for correlation when permission events omit tool-use IDs. Event-specific success output is an empty JSON object and does not approve, deny, or continue work.

The tray holds a per-data-directory instance mutex and reduces inbox records under a state lock. It commits an atomic snapshot before removing accepted records; replay is idempotent. Previous snapshots provide corruption recovery. An attachment's process ID is paired with process creation time. Inactive processes are never inferred dead solely from elapsed time, and no agent/terminal is terminated by Bell Tower.

Attachment health and title refresh share one policy across Claude Code and Codex. Launch-shell ownership survives palette consumption. The tray's asynchronous checkout cache supplies overview and change-driven desired title values; a bounded isolated writer receives only the desired title/palette and verified destination. The writer revalidates ownership under the detach presentation lock, and failed destinations use bounded backoff. Timeout cleanup terminates and joins only the owned writer. See [health, controls and compatibility](attachment-health.md).

Foreground activity, known background tasks, and outstanding attention are independent. Acknowledgment belongs to an episode; metadata updates never reset it. Completed operation IDs/fingerprints prevent delayed permission observations from reviving known completed calls. Provider-native turn IDs protect turn boundaries where available. Synchronous bounded hooks reduce delivery races when a provider lacks turn IDs.

Identity is stored independently under a hash of provider plus session ID. Manual name overrides the session-selected change, which overrides the directory default. A bounded selection reader recognizes literal OpenSpec invocations from main-session Bash hooks. Pre-tool operation receipts establish the latest pending selection; a matching post-tool completion requires structured OpenSpec success or a verified local scaffold and success marker. A bounded history of operation hashes suppresses replay. Atomic identity read/merge/write preserves concurrent manual edits. Raw command text and output are not retained. Initial launch metadata is optional. Color is generated once and persists. The planning root/store is separate provenance; Git inspection continues to use the verified session checkout and a bounded cache.

Codex footer configuration uses Tomlyn 2.10.1 to replace only the native `tui.status_line` value while preserving unrelated TOML text. Prior/installed expressions are owned in the integration manifest and restored only while unchanged. Updated local launchers create one capability-authenticated loopback app-server per attachment. A hidden runtime host starts without inherited handles, joins the verified shell console, and drains provider output without retaining it. This avoids leaking launch-pipeline handles while preserving backend/shell console membership. The native TUI remains a direct shell child. The wrapper requests owned-runtime cleanup only after the TUI exits; ordinary detach/tray management never stops the server. The runtime also monitors shell liveness and removes its token/record on exit.

The native-name pump targets the exact thread in its verified runtime. It reads metadata without transcripts, suppresses duplicate writes, bounds requests, and records the last applied name. A differing existing/native name pauses writes until explicit takeover/resume. Derived names reserve room for a linked-worktree suffix while branch uses its native field. No native database/JSONL writes or production terminal-input injection are used. Explicit standalone/remote sessions without an owned runtime report unavailable native sync while retaining tracking.

Audio runs on one STA worker. Alerts carry their reason to the sink, which selects the bundled event tone unless a custom WAV or the classic 880 Hz, 400 ms chime is selected. PCM normalization bounds both source and converted size. Aggregated alerts use the highest-priority reason's tone. SAPI prefers an installed Zira voice and falls back to tone-only; no invariant-globalization switch is set. Tests never invoke the physical sink.

Distinct blockers at the visible attention priority renew the episode; exact duplicate waits retain it. The persisted episode start determines new-notification eligibility independently of the oldest outstanding wait. This prevents a stale unmatched wait or an earlier viewed/dismissed chip from silencing the next permission request, while preserving silent restoration and duplicate suppression. Provider command fingerprints use Bash/apply_patch command content across hook stages; other tools retain canonical complete inputs.

For managed Codex sessions, a separate bounded metadata poll reads the owning runtime's thread status without loading turns or responding to approvals: `waitingOnApproval` is the human-approval signal, and `waitingOnUserInput` (probe-verified at 0.164.0 for question dialogs in Plan mode and in Default mode with `default_mode_request_user_input`) is read as confirmation evidence for a pending question and never gates or delays it. Fresh non-waiting approval status suppresses permission attention during automatic review and command execution. A confirmed human wait receives a five-second grace from its confirmation. Verification is bound to the exact runtime, thread, attachment, and attention episode; cached status expires after five seconds and is never persisted as authoritative across restarts.

Human-wait confirmation is one shared policy (`WaitState.Confirmation`, `SessionState`) with thin provider adapters. `PermissionRequest` only starts an approval flow, so a permission wait is created **provisional** and is never a chip, sound, reminder or escalation by itself, however long an automatic review lasts. A permission wait becomes attention when a supported signal confirms a human wait: Claude's `Notification` `permission_prompt` (the hook adapter marks it `HumanPrompt` and credits the provider's own notification delay, a 5-second floor below Claude's documented notification delay of about 6 s and the 6.1 to 6.3 s observed at 2.1.310), or Codex's fresh owning-runtime `waitingOnApproval` status. The shared 5-second grace counts delay already elapsed, so a Claude prompt is eligible on arrival with no extra debounce, while Codex's immediately observed status keeps the 5 seconds from its first report. Waits that have no supported signal are **unverified**: after 15 seconds a session without a supported signal (Codex without a verified owning runtime or with a failed status read, or Claude where no `permission_prompt` has been observed in the session, which the provider's `CLAUDE_CODE_DISABLE_PERMISSION_PROMPT_NOTIFY_HOOKS` setting can cause; the Claude adapter supplies that fact through `ClaudeConfirmationSignal` from `SessionState.PromptObserved` and Core applies the same policy) shows a visibly unverified \"possibly waiting for approval\" chip (`SessionState.PossiblyWaiting`, `UnverifiedGrace`), which is silent, outside `RequiresAttention` and `EffectiveConfirmation` (so no sound, reminder or escalation), never labelled confirmed, dismissible, and cleared by the correlated resolution, stop or end (this includes snapshots written before this policy, which are migrated as unverified and never newly announced); `bell-tower doctor` reports per provider what is configured, observed and unavailable (`confirmationCoverage`). Resolved waits leave bounded receipts (cleared at the next prompt, stop, interrupt, end or replacement attachment) so a late `permission_prompt` cannot recreate them: an unattributed prompt within 30 s of a resolution, or after the turn stopped, is ignored when no pending request could be its source (30 s is a Bell Tower heuristic, not a provider contract); shuffled or duplicated delivery is replayed by time; and several same-fingerprint requests without IDs are confirmed only as a set and never resolved or assigned arbitrarily. A prompt can only confirm requests whose start is at or before the prompt minus Claude's documented notification delay (about 6 seconds, floor 5), so a request that began moments earlier is never confirmed by it; an unattributed prompt arriving within 2 seconds of a resolution while other requests remain marks them ambiguous instead of confirming. An unattributed prompt that arrives while a question and a permission are pending is never credited to the permission, including by elimination after the question resolves (an isolated capture showed the question's own dialog emits that prompt, and Claude presents a following permission dialog sequentially); the permission is confirmed only by its own later prompt. Codex runtime confirmation takes the same stored transition: the pump publishes a runtime-approval observation that the shared reducer applies (identical episode and receipt handling on the causal and unordered paths, the observation keeps its own journal time and carries `RestoredSince` so waits restored from before the tray run are confirmed back-dated and restore silently; while a confirmed permission wait is outstanding a continuing positive status is that wait's evidence and is credited to no newer request), and the transient runtime flags remain only for freshness and negative-status suppression. Producers older than these fields (a cached ingress image) are recognized by a missing `adapterRevision`; their legacy `permission_prompt` shape (a permission observation with neither a tool ID nor a fingerprint) is re-derived as a prompt, and `bell-tower doctor` reports the outdated image (rerun setup). A confirmed Claude wait persists its confirmation time so a tray restart restores it silently. Each distinct episode has its own audio deadline; duplicates do not extend it. A provisional request takes the episode only when nothing else is actionable, so a newer unconfirmed or auto-approved request never re-announces or un-dismisses an older wait, and resolving a newer request restores an older outstanding wait's original deadline without replaying its sound. Confirming a request that was only provisional starts a fresh attention episode, so a dismissed unverified chip never hides the later confirmed wait. Elapsed time remains anchored to the original wait. Questions/errors remain immediate, completion retains its twenty-second grace, and restored already-due waits remain silent even after fresh native verification. `SessionState.EffectiveConfirmation` and `RequiresAttention` are the confirmed-eligibility contract that reminders, escalation and webhooks consume.

Codex runtime queries capture the opaque identities and revision of all permission waits present when each status read starts. A wait's scope combines its stable episode identity with a hash of its current unresolved candidate membership, so partial resumption invalidates evidence even when the wait episode remains. The pump accepts a cached positive status only while its attachment, episode, inspected wait set and revision still match. It includes the wait scopes and revision in the persisted runtime observation; Core confirms only when the complete unresolved permission set matches that captured set and revision. The revision increments only when the permission-wait scope set changes, so an A→A+B→A transition cannot revive old transient or persisted evidence, while unrelated events do not make a valid result stale. A fresh query receives a new observation ID, so an earlier rejected event cannot dedupe later valid evidence. Older queued runtime observations without scope or revision are ignored. Legacy waits without episodes receive a stable hash of their normalized wait identity; candidate membership is canonicalized and hashed without exposing operation metadata.

Question tools (`AskUserQuestion`, `request_user_input`, `request_user_input_async`) stay question waits. Claude runs the question dialog through its approval flow (`PermissionRequest` without `tool_use_id` but with the same tool name and input, then a `permission_prompt` about 6 s later, in auto and default modes); the adapter marks these `QuestionTool`/`HumanPrompt` and shared policy treats them as confirming evidence for the one pending question (by tool name plus input fingerprint, or the turn scope), never as a new permission wait, announcement or dismissal. When a question and an uncorrelated permission request are both pending, an unattributed prompt is recorded as ambiguous and assigned to neither and not reassigned later. Codex emits no approval hook for `request_user_input`; a Default-mode call rejected without a dialog (`PreToolUse` then `Stop`, no `PostToolUse`) clears at `Stop` with nothing restored, reminded or escalated.

The VS Code bridge registers its extension-host process creation time, current terminal shell PIDs, a protocol version and, once its window has gained focus, window evidence (handle, owner identity and class of the foreground window sampled by `bell-tower foreground-window` while the bridge's window reported focus before and after). It accepts only its window instance's unexpired requests, verifies shell creation time, and acknowledges only the exact terminal reveal. `VsCodeWindowOwnership` accepts evidence only when the owner identity matches, the handle is a live visible editor-class window of that owner, the owner is in the bridge's process lineage and no other fresh bridge claims the handle; otherwise nothing is activated. `VsCodeNavigator` activates that window first (`WindowActivator` restores only a minimized window and confirms the actual foreground window), then requests the reveal (naming the activated handle so a bridge whose own window is unfocused can discard a wrong record), then re-confirms the foreground. Samples are discarded and repeated when any focus or blur event occurs during sampling. Tray precision uses a registration snapshot reused for about one tick and never past the 15 second freshness; the tray removes request and receipt files on read and on timeout and sweeps receipts older than a minute. Bridge writes use unique temporary files that are removed on failure; a registration write failure is retried on later ticks without starving focus requests, and expired ownership is never used. Windows Terminal activation validates its window owner and restores only minimized windows. A bounded disposable helper marks the verified session console's title, selects a unique matching live UI Automation tab, and restores the prior title under the presentation lock. Ambiguity falls back to the verified window. No saved tab index or friendly name identifies a session. Split-pane focus remains separate.

Desktop ownership stores optional project directories and selected providers. Setup generates named project profiles additively and supplies explicit Windows Terminal starting directories. The PowerShell session functions accept a directory, invoke the native agent there, and restore the invoking shell's location afterward. Scoped console presentation applies the stored identity palette only when the launch opted into background ownership; the wrapper resets configured profile colors on exit.

The packaged application uses immutable versions beneath a stable launcher and atomically selected current.json. Shared launch/lifetime leases protect old runtime processes against cleanup. Background release discovery is independent of monitoring; explicit update activation restarts only the selected data-directory tray, validates readiness, and restores the prior version on failure. Hook ingestion remains available during restart. Contract 1 retains existing shared state/runtime/integration formats. Owned integration refreshes occur only during explicit setup/update, preserving user edits and selected providers. See [release operations](releases.md) for migration, rollback, and bootstrap maintenance.

The desktop workflow is terminal profile -> PowerShell role function -> native agent. The executable launcher is optional. The bundled shell module sets attachment metadata, resolves the native command, starts the tray separately, and restores shell environment/title on exit. Hook observations bind the provider session ID to that attachment. Local Codex role functions use its dedicated mode so the backend does not inherit another session's terminal metadata.

Title synchronization runs in a separate short-lived helper. It validates both the shell and agent creation times, checks both processes belong to the attached console, and sets only the title. It never injects text/keystrokes, changes foreground focus, or modifies global themes. Detachment and title writes share a presentation lock so the module restores the old title after pending writes finish. Plain/native sessions without managed-title metadata remain untouched.
