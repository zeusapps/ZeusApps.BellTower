# Architecture

Bell Tower uses a .NET 10 Windows application, a small stable launcher, a shared distribution-contract library, and separate xUnit/packaged acceptance projects. WorkLog is an organizational reference and has no project/runtime dependency.

| Area | Responsibility |
| --- | --- |
| Core | Provider-neutral observations, session activity/attention reduction, palettes, grace and episode/audio policy |
| IO | Separate snapshot/attachment/identity/config stores, atomic local files, serialized state transactions, process identity/liveness, bounded logs, read-only Git queries |
| Providers | Sanitize Claude/Codex hook JSON; render the ANSI Claude status line |
| Sessions | Agent launching and lifecycle; session listing, naming and focus actions |
| Hosts | Capture attachments; route through ITerminalNavigator; separate VS Code request protocol and Windows Terminal activation; scoped title helper |
| Tray | Nonactivating strip, session overview, position/refitting, serialized chime/SAPI voice, silent audio sink |
| Setup | Plan/review/apply hooks, badge, PowerShell module/imports, terminal profiles and VS Code bridge; preserve unrelated settings; legacy metadata import |
| Cli | System.CommandLine command classes, typed options/validation, generated help, neutral hook errors, literal agent argument forwarding |
| Diagnostics | Report setup observations and capability limits without modifying configuration |
| vscode | Dependency-free local registration/focus bridge, separately tested with Node's built-in runner |

Hook invocations extract only needed fields and publish unique normalized records to the inbox. Tool/prompt bodies and transcript contents are not retained. Tool input is hashed in a canonical order for correlation when permission events omit tool-use IDs. Event-specific success output is an empty JSON object and does not approve, deny, or continue work.

The tray holds a per-data-directory instance mutex and reduces inbox records under a state lock. It commits an atomic snapshot before removing accepted records; replay is idempotent. Previous snapshots provide corruption recovery. An attachment's process ID is paired with process creation time. Inactive processes are never inferred dead solely from elapsed time, and no agent/terminal is terminated by Bell Tower.

**Bounded monitoring state.**

`state.json` stays under its 16 MiB snapshot budget for Claude Code and Codex alike, because retention lives in the shared store and reducer with no provider branch. Each drain, before it saves:

- An ended session untouched for 10 minutes (`StateStore.SettleInterval`) is compacted: the journal observations at or before its last applied observation are folded away, its checkpoint and completed-operation memory and open operations are dropped, and its ordering floor moves to the latest folded observation (never backward). Later observations that the ended session ignored, such as a resumed client's prompt delivered before its resume registration, stay in the journal (bounded by the 256 window) against a checkpoint copied from the compacted session, so a late resume registration still sorts ahead of them and revives the session with them replayed. Compaction is skipped in a drain while a capture or inbox backlog remains (a full capture batch or pending files), so events queued behind the first batch are applied first, unless the save would exceed the budget: then settled sessions are compacted before any session is removed. Displayed fields do not change. A delayed earlier event stays at or before the floor and is ignored, so the session stays ended with no attention. The `state.json` schema is unchanged (an empty or short journal and a null or copied checkpoint are valid for older builds).
- At most 200 ended sessions are retained (`StateStore.MaxEndedSessions`), oldest `LastObserved` first, in addition to the 30-day age limit. Live sessions are never removed.
- A save that would still exceed the budget removes the oldest ended sessions in at most four extra re-encodes and then fits. Only when live sessions alone exceed the budget is the save refused with `InvalidDataException`; captures then stay queued.
- State written by an earlier version at the budget recovers on its first drain, and queued captures are consumed.

The tray logs a refresh failure as `tray-refresh-failed: <exception type>: <message>` (at most 200 characters; the data directory, the user-profile directory, drive, UNC and Unix paths, including ones with spaces and apostrophes, and the current user name are replaced; a single-quoted segment that starts at a path root is masked through the last closing quote on its line, so text between two quoted paths on one line may be masked too) at most once every 10 minutes for each distinct reason, and at most eight distinct reasons are remembered per interval (further new reasons are suppressed behind one `tray-refresh-failed: further reasons suppressed` line per interval, so there are at most nine failure or suppression lines per 10 minutes whatever the reasons), and `tray-refresh-recovered` on the first success after a logged failure (at most one recovery line per logged failure, so at most 17 lines per 10 minutes in all, however failures and successes alternate). On transitions only (a logged failure starts the record, the recorded reason changes at most once per 10 minutes, or a failure window has lasted 30 seconds, even when its own line is suppressed) it writes `refresh-health.json` in the data directory (`failingSince`, `reason`, `lastSuccess`). `bell-tower doctor` reports a `state` section: `state.json` size and budget, live and ended counts (overall and per provider) from a read-only snapshot, the retention policy and the refresh health. A failure is `persistent` when `failingSince` is more than one minute old while the tray is running. A missing state file or health record is reported as such, never as a failure of doctor.

Attachment health and title refresh share one policy across Claude Code and Codex. Launch-shell ownership survives palette consumption. The tray's asynchronous checkout cache supplies overview and change-driven desired title values; a bounded isolated writer receives only the desired title/palette and verified destination. The writer revalidates ownership under the detach presentation lock, and failed destinations use bounded backoff. Timeout cleanup terminates and joins only the owned writer. See [health, controls and compatibility](attachment-health.md).

Foreground activity, known background tasks, and outstanding attention are independent. Acknowledgment belongs to an episode; metadata updates never reset it. Completed operation IDs/fingerprints prevent delayed permission observations from reviving known completed calls. Provider-native turn IDs protect turn boundaries where available. Synchronous bounded hooks reduce delivery races when a provider lacks turn IDs.

Identity is stored independently under a hash of provider plus session ID. Manual name overrides the session-selected change, which overrides the directory default. A bounded selection reader recognizes literal OpenSpec invocations from main-session Bash hooks. Pre-tool operation receipts establish the latest pending selection; a matching post-tool completion requires structured OpenSpec success or a verified local scaffold and success marker. A bounded history of operation hashes suppresses replay. Atomic identity read/merge/write preserves concurrent manual edits. Raw command text and output are not retained. Initial launch metadata is optional. Color is generated once and persists. The planning root/store is separate provenance; Git inspection continues to use the verified session checkout and a bounded cache.

Codex footer configuration uses Tomlyn 2.10.1 to replace only the native `tui.status_line` value while preserving unrelated TOML text. Prior/installed expressions are owned in the integration manifest and restored only while unchanged. Updated local launchers create one capability-authenticated loopback app-server per attachment. A hidden runtime host starts without inherited handles, joins the verified shell console, and drains provider output without retaining it. This avoids leaking launch-pipeline handles while preserving backend/shell console membership. The native TUI remains a direct shell child. The wrapper requests owned-runtime cleanup only after the TUI exits; ordinary detach/tray management never stops the server. The runtime also monitors shell liveness and removes its token/record on exit. Shutdown authority is explicit: an access record never stops anything. The only stop path is an attachment's `CodexRuntime` record whose manager Bell Tower started, plus the stop marker (`CodexRuntimeStore.Stop`), which sends no signal and only asks that owned manager to end. The manager then terminates the backend it started together with that backend's descendants (tool, MCP and agent-started processes, so none is orphaned); .NET's process-start-time check keeps a reused PID from being matched. A failed or cancelled prepare terminates the manager's tree the same way. Detach, setup removal, tray exit, update and rollback never stop, signal or reconfigure a shared or private Codex backend, a user's Claude or Codex client, or their shell, including when a stale or reused-PID record names one; only the tray holds observer connections (the native-name and permission readers), and it releases them when it exits. Every process Bell Tower terminates is a handle it created in the same operation, or a descendant of one (probe and helper children, the runtime manager, its backend and their descendants); `ProcessStopAuthorityTests` pins the known terminating API call sites, a tripwire for new ones rather than a proof of completeness. The owned loopback transport never uses a proxy, so the bearer token only travels the direct connection.

The native-name pump targets the exact thread in its verified runtime. It reads metadata without transcripts, suppresses duplicate writes, bounds requests, and records the last applied name. A differing existing/native name pauses writes until explicit takeover/resume. Derived names reserve room for a linked-worktree suffix while branch uses its native field. No native database/JSONL writes or production terminal-input injection are used. Explicit standalone/remote sessions without an owned runtime report unavailable native sync while retaining tracking. A shared-backend Codex conversation (hook classified as shared backend) is reached through the same opener: `CodexRuntimeOpener` selects an owned runtime record or, for a proven shared backend, `CodexSharedAccess` for the resolved Codex home (`CODEX_HOME` or `~/.codex`), and returns an already connected client to both the name service and the permission pump. The shared path is observer-only: the backend process is derived from the connected socket, must be a live non-elevated `codex` shared backend (each failure has its own reason, shown in the native-name status), and the thread read must return exactly the requested id (the actual proof, together with the peer-verified backend) or the operation is refused as a mismatch. A thread that reports a fork, parent, agent or other-session field is also refused, as an explicitly conservative policy (status \"fork or delegated thread mapping unverified\"), not a proof: which session id a fork's or delegated thread's hook carries is not yet observed (task 6.1 probe). Concurrent failed opens count one backoff failure per home per window (a per-home generation changes on every recorded failure and success), and the shared open's own budgets (1 s connect, 1.5 s handshake) end before the services' 3 s operation timeout, so a stalled backend is recorded once as a timeout and backs off both services. Reads use `thread/read` with `includeTurns: false`; no resume, turn or approval request is ever sent, and responses are not retained or logged.

Audio runs on one STA worker. Alerts carry their reason to the sink, which selects the bundled event tone unless a custom WAV or the classic 880 Hz, 400 ms chime is selected. PCM normalization bounds both source and converted size. Aggregated alerts use the highest-priority reason's tone. SAPI prefers an installed Zira voice and falls back to tone-only; no invariant-globalization switch is set. Tests never invoke the physical sink.

Distinct blockers at the visible attention priority renew the episode; exact duplicate waits retain it. The persisted episode start determines new-notification eligibility independently of the oldest outstanding wait. This prevents a stale unmatched wait or an earlier viewed/dismissed chip from silencing the next permission request, while preserving silent restoration and duplicate suppression. Provider command fingerprints use Bash/apply_patch command content across hook stages; other tools retain canonical complete inputs.

For managed Codex sessions, a separate bounded metadata poll reads the owning runtime's thread status without loading turns or responding to approvals: `waitingOnApproval` is the human-approval signal, and `waitingOnUserInput` (probe-verified at 0.164.0 for question dialogs in Plan mode and in Default mode with `default_mode_request_user_input`) is read as confirmation evidence for a pending question and never gates or delays it. Fresh non-waiting approval status suppresses permission attention during automatic review and command execution. A confirmed human wait receives a five-second grace from its confirmation. The same read works on a shared backend with the checks above. Verification is bound to the exact runtime, thread, attachment, and attention episode; cached status expires after five seconds and is never persisted as authoritative across restarts.

Human-wait confirmation is one shared policy (`WaitState.Confirmation`, `SessionState`) with thin provider adapters. `PermissionRequest` only starts an approval flow, so a permission wait is created **provisional** and is never a chip, sound, reminder or escalation by itself, however long an automatic review lasts. A permission wait becomes attention when a supported signal confirms a human wait: Claude's `Notification` `permission_prompt` (the hook adapter marks it `HumanPrompt` and credits the provider's own notification delay, a 5-second floor below Claude's documented notification delay of about 6 s and the 6.1 to 6.3 s observed at 2.1.310), or Codex's fresh owning-runtime `waitingOnApproval` status. The shared 5-second grace counts delay already elapsed, so a Claude prompt is eligible on arrival with no extra debounce, while Codex's immediately observed status keeps the 5 seconds from its first report. Waits that have no supported signal are **unverified**: after 15 seconds a session without a supported signal (Codex without a verified owning runtime or with a failed status read, or Claude where no `permission_prompt` has been observed in the session, which the provider's `CLAUDE_CODE_DISABLE_PERMISSION_PROMPT_NOTIFY_HOOKS` setting can cause; the Claude adapter supplies that fact through `ClaudeConfirmationSignal` from `SessionState.PromptObserved` and Core applies the same policy) shows a visibly unverified \"possibly waiting for approval\" chip (`SessionState.PossiblyWaiting`, `UnverifiedGrace`), which is silent, outside `RequiresAttention` and `EffectiveConfirmation` (so no sound, reminder or escalation), never labelled confirmed, dismissible, and cleared by the correlated resolution, stop or end (this includes snapshots written before this policy, which are migrated as unverified and never newly announced); `bell-tower doctor` reports per provider what is configured, observed and unavailable (`confirmationCoverage`). Resolved waits leave bounded receipts (cleared at the next prompt, stop, interrupt, end or replacement attachment) so a late `permission_prompt` cannot recreate them: an unattributed prompt within 30 s of a resolution, or after the turn stopped, is ignored when no pending request could be its source (30 s is a Bell Tower heuristic, not a provider contract); shuffled or duplicated delivery is replayed by time; and several same-fingerprint requests without IDs are confirmed only as a set and never resolved or assigned arbitrarily. A prompt can only confirm requests whose start is at or before the prompt minus Claude's documented notification delay (about 6 seconds, floor 5), so a request that began moments earlier is never confirmed by it; an unattributed prompt arriving within 2 seconds of a resolution while other requests remain marks them ambiguous instead of confirming. An unattributed prompt that arrives while a question and a permission are pending is never credited to the permission, including by elimination after the question resolves (an isolated capture showed the question's own dialog emits that prompt, and Claude presents a following permission dialog sequentially); the permission is confirmed only by its own later prompt. Codex runtime confirmation takes the same stored transition: the pump publishes a runtime-approval observation that the shared reducer applies (identical episode and receipt handling on the causal and unordered paths, the observation keeps its own journal time and carries `RestoredSince` so waits restored from before the tray run are confirmed back-dated and restore silently; while a confirmed permission wait is outstanding a continuing positive status is that wait's evidence and is credited to no newer request), and the transient runtime flags remain only for freshness and negative-status suppression. Producers older than these fields (a cached ingress image) are recognized by a missing `adapterRevision`; their legacy `permission_prompt` shape (a permission observation with neither a tool ID nor a fingerprint) is re-derived as a prompt, and `bell-tower doctor` reports the outdated image (rerun setup). A confirmed Claude wait persists its confirmation time so a tray restart restores it silently. Each distinct episode has its own audio deadline; duplicates do not extend it. A provisional request takes the episode only when nothing else is actionable, so a newer unconfirmed or auto-approved request never re-announces or un-dismisses an older wait, and resolving a newer request restores an older outstanding wait's original deadline without replaying its sound. Confirming a request that was only provisional starts a fresh attention episode, so a dismissed unverified chip never hides the later confirmed wait. Elapsed time remains anchored to the original wait. Questions/errors remain immediate, completion retains its twenty-second grace, and restored already-due waits remain silent even after fresh native verification. `SessionState.EffectiveConfirmation` and `RequiresAttention` are the confirmed-eligibility contract used by reminders and escalation candidate tracking.

Codex runtime queries capture the opaque identities and revision of all permission waits present when each status read starts. A wait's scope combines its stable episode identity with a hash of its current unresolved candidate membership, so partial resumption invalidates evidence even when the wait episode remains. The pump accepts a cached positive status only while its attachment, episode, inspected wait set and revision still match. It includes the wait scopes and revision in the persisted runtime observation; Core confirms only when the complete unresolved permission set matches that captured set and revision. The revision increments only when the permission-wait scope set changes, so an A→A+B→A transition cannot revive old transient or persisted evidence, while unrelated events do not make a valid result stale. A fresh query receives a new observation ID, so an earlier rejected event cannot dedupe later valid evidence. Older queued runtime observations without scope or revision are ignored. Legacy waits without episodes receive a stable hash of their normalized wait identity; candidate membership is canonicalized and hashed without exposing operation metadata.

Question tools (`AskUserQuestion`, `request_user_input`, `request_user_input_async`) stay question waits. Claude runs the question dialog through its approval flow (`PermissionRequest` without `tool_use_id` but with the same tool name and input, then a `permission_prompt` about 6 s later, in auto and default modes); the adapter marks these `QuestionTool`/`HumanPrompt` and shared policy treats them as confirming evidence for the one pending question (by tool name plus input fingerprint, or the turn scope), never as a new permission wait, announcement or dismissal. When a question and an uncorrelated permission request are both pending, an unattributed prompt is recorded as ambiguous and assigned to neither and not reassigned later. Codex emits no approval hook for `request_user_input`; a Default-mode call rejected without a dialog (`PreToolUse` then `Stop`, no `PostToolUse`) clears at `Stop` with nothing restored, reminded or escalated.

The VS Code bridge registers its extension-host process creation time, current terminal shell PIDs, a protocol version and, once its window has gained focus, window evidence (handle, owner identity and class of the foreground window sampled by `bell-tower foreground-window` while the bridge's window reported focus before and after). It accepts only its window instance's unexpired requests, verifies shell creation time, and acknowledges only the exact terminal reveal. `VsCodeWindowOwnership` accepts evidence only when the owner identity matches, the handle is a live visible editor-class window of that owner, the owner is in the bridge's process lineage and no other fresh bridge claims the handle; otherwise nothing is activated. `VsCodeNavigator` activates that window first (`WindowActivator` restores only a minimized window and confirms the actual foreground window), then requests the reveal (naming the activated handle so a bridge whose own window is unfocused can discard a wrong record), then re-confirms the foreground. Samples are discarded and repeated when any focus or blur event occurs during sampling. Tray precision uses a registration snapshot reused for about one tick and never past the 15 second freshness; the tray removes request and receipt files on read and on timeout and sweeps receipts older than a minute. Bridge writes use unique temporary files that are removed on failure; a registration write failure is retried on later ticks without starving focus requests, and expired ownership is never used. Windows Terminal activation validates its window owner and restores only minimized windows. A bounded disposable helper marks the verified session console's title, selects a unique matching live UI Automation tab, and restores the prior title under the presentation lock. Ambiguity falls back to the verified window. No saved tab index or friendly name identifies a session. Split-pane focus remains separate.

Desktop ownership stores optional project directories and selected providers. Setup generates named project profiles additively and supplies explicit Windows Terminal starting directories. The PowerShell session functions accept a directory, invoke the native agent there, and restore the invoking shell's location afterward. Scoped console presentation applies the stored identity palette only when the launch opted into background ownership; the wrapper resets configured profile colors on exit.

The packaged application uses immutable versions beneath a stable launcher and atomically selected current.json. Shared launch/lifetime leases protect old runtime processes against cleanup. Background release discovery is independent of monitoring; explicit update activation restarts only the selected data-directory tray, validates readiness, and restores the prior version on failure. Hook ingestion remains available during restart. Contract 1 retains existing shared state/runtime/integration formats. Owned integration refreshes occur only during explicit setup/update, preserving user edits and selected providers. See [release operations](releases.md) for migration, rollback, and bootstrap maintenance.

The desktop workflow is terminal profile -> PowerShell role function -> native agent. The executable launcher is optional. The bundled shell module sets attachment metadata, resolves the native command, starts the tray separately, and restores shell environment/title on exit. Hook observations bind the provider session ID to that attachment. Local Codex role functions use its dedicated mode so the backend does not inherit another session's terminal metadata.

Title synchronization runs in a separate short-lived helper. It validates both the shell and agent creation times, checks both processes belong to the attached console, and sets only the title. It never injects text/keystrokes, changes foreground focus, or modifies global themes. Detachment and title writes share a presentation lock so the module restores the old title after pending writes finish. Plain/native sessions without managed-title metadata remain untouched.
