# Development conventions

Bell Tower follows WorkLog's small-helper structure: application folders by responsibility, one top-level type per file, and a command class per CLI verb. A small stable launcher and shared distribution-contract library support immutable versioned payloads; xUnit and packaged acceptance projects verify their behavior. WorkLog is a style reference, with no project or runtime dependency.

Repository implementation uses the shared [agent workflow](agent-workflow.md): the main agent plans and orchestrates through OpenSpec, the developer changes implementation, and QA plus the code analyzer independently review and report inside the corresponding change.

## CLI commands

Use `System.CommandLine` 2.0.13, matching WorkLog. `CliApplication` registers commands; command classes declare typed options, validation, and their action. `CommonOptions` owns shared option definitions. The library generates help and handles invalid commands, required options, and typed values. See Microsoft's [parsing and invocation documentation](https://learn.microsoft.com/en-us/dotnet/standard/commandline/how-to-parse-and-invoke).

Commands delegate to application services. Do not add another parser or move service logic into `Program`. `Program` owns UTF-8 console setup, the STA entry point, and top-level error reporting. Keep tray invocation synchronous so WinForms runs on that STA thread.

For `launch`, only Bell Tower's prefix is parsed. Strings after `--` pass directly to `ProcessStartInfo.ArgumentList`, including spaces, option-like values, and literal `@` arguments. Response-file expansion is disabled. Hook invocations have a dedicated failure boundary: malformed input or options produce a sanitized log code and a successful empty JSON response, without provider decisions or raw payload logging.

## Responsibilities and dependencies

- `Core`: session data, the observation reducer, attention policy, identity text, and palette rules. Keep provider JSON, disk access, native windows, and UI controls out of this layer.
- `IO`: local persistence, atomic writes, locking, process inspection, hashes, and read-only Git queries. `StateStore` coordinates replay and state transactions; `StateSnapshotStore` reads/writes snapshots; `AttachmentStore` owns attachment files.
- `Providers`: bounded hook input, normalization, ingestion, and status-line rendering. Adapter output is the provider-neutral `Observation` model.
- `Sessions`: agent launch/lifecycle and session queries/metadata actions, shared by the command layer.
- `Hosts`: attachment capture and terminal navigation. `Navigator` validates process identity and delegates to `ITerminalNavigator`; each host implementation owns its protocol or native window calls.
- `Tray`: UI lifetime, controls, view projection, and audio. `SessionViewFactory` creates presentation records. `AudioQueue` depends on `IAudioSink`; physical playback and silent/test substitutes remain separate.
- `Setup`: plan construction, verified immutable ingress provisioning, direct provider hook commands, structural handler ownership and edited-entry migration, application of file changes, and explicit legacy import. Keep these separate from ordinary startup. Development-only normalized event checks retain the encoded legacy command.
- `Integration/BellTower.psm1`: embedded PowerShell support for native session launches. Setup supplies stable executable/data paths and exports the selected provider functions plus legacy aliases. Directory selection, optional background ownership and restoration belong here. Do not replace the direct native invocation with a call to the executable launcher.
- `Diagnostics`: read-only reports of observations and capability limitations.

Add interfaces where there are actual alternate implementations or a replaceable boundary, as with terminal hosts and audio sinks. Do not add base classes or interfaces just to wrap individual concrete services. Small functions and data records do not need inheritance hierarchies.

Managed console-title writes run only in the isolated helper process, with process identity and console-membership checks. Keep that console attachment code out of hooks and the tray process itself. Detachment shares the presentation lock so shell restoration happens after outstanding writes. Desktop setup must preserve unrelated settings and track adopted profiles/settings for conditional restoration; removal ownership is committed after extension actions succeed so failed removals can be retried.

Tab selection also runs in a bounded helper. Resolve a fresh random console marker through UI Automation, preserve the previous title in a finally block, and fall back when the target is not unique. Keep UI Automation separate from selection policy through the replaceable tab source. Never derive tab identity from a saved position or friendly name. Detached tray/helper processes use the executable directory rather than retaining a project as their working directory.

## Development builds

Maintainers try unreleased builds on their own versioned installation with `scripts/package.ps1 -Dev` and `scripts/install-dev.ps1`. The same procedure is available to Claude Code and Codex as the identical `install-dev-build` skill (`.claude/skills/install-dev-build/SKILL.md` and `.agents/skills/install-dev-build/SKILL.md`); a test fails if the two copies differ.

- **Version range.** A dev build is `MAJOR.MINOR.PATCH` with PATCH of 9000 or higher (`ReleaseContract.IsDevVersion`), built from the base version in `Directory.Build.props` (for base `0.1.8`: `0.1.9001`, `0.1.9002`, ...). The format stays the strict three-number form that installed launchers parse, and the version is still the payload folder name. Stable packaging refuses the range.
- **Marker.** `release.json` carries an optional `build` object: `channel` (`dev`), `commit`, `dirty`, `builtAt` and `baseVersion`. The executables carry the informational version `0.1.9001-dev+b74a12b` (`.dirty` appended for a dirty tree). `VersionDisplay` formats one text, `0.1.9001 dev b74a12b (2026-10-24 21:30 UTC)` (`dirty` follows the commit), used by the tray tooltip and menu, the Sessions window title, `doctor` (`version`), `update --status` and `bell-tower --version`. A dev-range payload without the marker reads `dev (unmarked)`. Stable builds show their plain version.
- **Build.** `./scripts/package.ps1 -Dev [-DevVersion 0.1.9005]` writes `artifacts/dev-builds/bell-tower-<version>-win-x64.zip` with its `.sha256` and `.release.json`. The number is the next one above everything in that folder and in the default installation's `versions/` (`-TargetInstallation` overrides the installation). Only the `src`, `tests`, `scripts`, `vscode`, `docs` and top-level build files decide the dirty flag. `-PlanOnly` prints the plan without building. The script finds `vswhere.exe` (Visual Studio Installer folder, or an explicit `-VsWherePath`) and the Windows SDK itself and prepends the installer folder to PATH for its child processes only; a missing toolchain fails with a message naming the Build Tools workload or the Windows SDK, and there is no managed fallback.
- **Updates.** While a dev build is selected, `update --check`, tray discovery and `UpdateTransaction.Stage` compare stable offers with its base version (`Installation.EffectiveVersion`; an unmarked dev-range payload counts as `MAJOR.MINOR.0`). A stable `0.1.9` is therefore offered and installable over dev `0.1.9001`. Published offers in the dev range are rejected. `previous` in `current.json` may name a dev version.
- **Install.** `./scripts/install-dev.ps1 -Action Preflight|Switch|Rollback|Retire`:
  - `Preflight` (read-only apart from the private operation record) verifies the package hash and contract, requires a marked dev build, refuses a stale build (package commit differs from HEAD, or sources newer than the Release assemblies; `-AllowStaleBuild` overrides), derives compatibility from the installed and candidate contracts (`CaptureCompatibility`), and prints `operationManifest`.
  - `Switch -OperationManifest <path>` snapshots the selection and `state.json`/`state.json.bak` into the private workspace (default `artifacts/dev-builds/operations`, restricted to the current user, SYSTEM and Administrators), installs the payload beside the others, stops only the verified tray, selects the build (recording the original as `previous`) and restarts the tray through the stable launcher. An operation-owned restart marker and a temporary tray-instance reservation fence new and in-flight starts while the selection changes, without holding the hook launch gate during copy or verification. It refuses changed tray owners, selections, original payload bytes, unrelated coordination markers or startup processes whose identity cannot be verified.
  - `Rollback -OperationManifest <path>` restores `current.json`, `state.json` and `state.json.bak` from the snapshot and restarts the tray. It restores the selection from immediately before this switch, so rollback is one level. Matching dead-operation records can be recovered from the same manifest; unrelated marker bytes are preserved. The original tray's automatic cleanup may then reclaim the dev payload when no longer selected, previous or otherwise retained. Nothing else is restored.
  - `Retire -Version <v>` removes only a dev-marked payload that is not selected, not `previous`, not leased and not needed by an unfinished update. It uses the same retention and file-integrity checks as the tray's automatic cleanup.
  - The disposable-test switches `-Disposable`, `-NoTray` and `-SkipProbe` only work for installations, data and workspaces under the repository `artifacts/` folder.
- **Legacy dev payloads.** The earlier trial payloads `0.1.9` and `0.1.10` have no marker and collide with future stable releases (a stable `0.1.9` fails as already selected or superseded, and a stable `0.1.10` as an existing folder). `Retire` refuses unmarked payloads because their identity cannot be distinguished safely from stable releases. The tray's automatic cleanup reclaims verified unmarked payloads once they are neither selected nor retained; after the first marked dev install, this may take a later dev switch or stable update. Automatic cleanup also reclaims a dev payload after rollback when it is no longer retained.
- **Recovery.** If Switch or Rollback refuses or fails after it stopped the tray but before the selection or monitoring state changed (for example a live process that stays unclassifiable until the 30 s drain deadline), it restarts the tray it stopped through the stable launcher (when the tray did not exit or another tray owns monitoring, nothing is launched), clears its own records and reports that. A failed Switch that touched nothing else (no candidate payload and no monitoring snapshot folder) can then be retried with the same manifest; once something else was touched, the restarted operation is terminal: Switch and Rollback both say to run Preflight again. If the automatic restart fails before launching, the message says the tray is stopped and `Rollback -OperationManifest <path>` recovers it, including before the candidate payload copy. If it fails after launching, the records are kept and the message says a tray may be running unverified. A live process that cannot be classified yet is re-scanned within the same deadline instead of refusing at once. The classifier knows every CLI verb (a drift test enforces it), including `statusline`, so a Claude status-line payload process classifies at once instead of staying unclassifiable for its whole lifetime. The restarted tray is launched without inheriting the installer's standard handles, so a captured shell returns when the script ends. `Rollback` reverts a switch; if the script stops midway, keep the operation folder and `artifacts/dev-builds/operations`, read `operation.json` (`state`), and see [release operations](releases.md) for manual recovery of `current.json`. Running the same `Rollback -OperationManifest <path>` again also resumes an interrupted rollback. It does not restore monitoring a second time once that step is recorded. Before it rewrites `current.json`, it records the exact old and new selection hashes (`rollbackPointerTransition`), and a retry accepts only those bytes. Any other selection, record or phase combination is refused and left untouched. Before Rollback stops a candidate tray, it re-reads the tray's live activation and compares it with the activation recorded at Switch, then rechecks immediately before the stop signal; a mismatch is refused without signalling. An older tray started after rollback shows a dev payload as a plain version because older code cannot read the marker.

## Formatting and checks

`.editorconfig` defines the whitespace and C# style. C# uses four spaces, file-scoped namespaces, braces for control flow, readable statement blocks, and normal single-line auto-properties. XML project/solution files and JSON use two spaces. Keep statements on separate lines, break up long expressions, and group tests under the area they exercise.

After restoring dependencies:

```powershell
./scripts/format.ps1
./scripts/format.ps1 -Verify
dotnet build -c Release --no-restore
dotnet test -c Release --no-build --no-restore
node --test vscode/service.test.js vscode/focus.test.js
```

The formatting script runs the SDK formatter for C#. Keep XML/JSON readable using their `.editorconfig` indentation settings. Tests use isolated data/configuration and silent audio sinks. Fake agent subprocesses exercise launching without authenticated Claude or Codex sessions. Live hook coverage and desktop focus acceptance remain separate work in the compatibility matrix.
