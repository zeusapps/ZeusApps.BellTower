## Installed field acceptance harness

`scripts/field-acceptance.ps1` runs scenario-based acceptance against real packaged installations under disposable roots. It complements `scripts/update-acceptance.ps1` (which reprovisions the ingress right after an update) and is the foundation later field-acceptance tasks extend: each scenario is a class in `tools/BellTower.FieldAcceptance/Scenarios` registered in `ScenarioCatalog`, built on `Instance` (a sandbox install, data directory, fake user home, fake provider binaries and child environment).

```powershell
./scripts/field-acceptance.ps1 -EvidenceOut openspec/changes/<change>/evidence/harness-<task>.md   # default scenario: upgrade-without-setup
dotnet tools/BellTower.FieldAcceptance/bin/Release/net10.0-windows/BellTower.FieldAcceptance.dll --list
```

- **Baseline.** The historical baseline is the archive GitHub published for the tag (`-BaselineTag`, default `v0.1.9`), downloaded with `gh release download` into `artifacts/field-acceptance/baseline/` together with its `.sha256` and release descriptor. The harness recomputes the archive's SHA-256 and requires it to match at least two of the published `.sha256`, the descriptor `archiveHash` and the GitHub asset digest recorded in `provenance.json`; otherwise the run stops. The baseline is never rebuilt from source.
- **Candidate.** Until the version declarations are synchronized for the release (task 4.4) the candidate is the fixture-version package `scripts/package.ps1 -FixtureVersion 0.1.11 -OutputDirectory artifacts/update-acceptance/packages` (built on demand, or with `-RebuildCandidate`). It is labeled a fixture-version candidate in every result, is never a release candidate and is installed only under harness sandboxes.
- **Isolation.** Each instance lives under `artifacts/field-acceptance/runs/<timestamp>/sandbox/<name>/` with its own `install`, `data`, `home` (fake `~/.claude`, `~/.codex`, AppData), `temp` and `fake-bin`. Child processes get an allow-listed environment (sandbox `USERPROFILE`, `HOME`, `APPDATA`, `LOCALAPPDATA`, `TEMP`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `BELLTOWER_DATA_DIR`; PATH entries inside production locations are dropped; no other variables are inherited) and every Bell Tower command carries an explicit sandbox `--data-dir`. `ProductionGuard` refuses (and fails the run on) a sandbox inside or around `%LOCALAPPDATA%\ZeusApps.BellTower`, `%LOCALAPPDATA%\Programs\ZeusApps.BellTower`, `~/.claude`, `~/.codex`, `~/.vscode`, `%APPDATA%\Code` or any root named by `BELLTOWER_DATA_DIR`, `CLAUDE_CONFIG_DIR` or `CODEX_HOME`; an executable outside the sandbox other than Git Bash, Windows PowerShell, PowerShell 7 (`pwsh.exe` at its fixed path), `schtasks` and `cmd`; an argument or environment value naming a production location or the user's own profile folder; and a Bell Tower command without a sandbox `--data-dir`. A guard self-test proves these refusals against the real production locations at the start of every run. Before and after, the run fingerprints the setup-owned provider and VS Code settings and Bell Tower manifest files, the whole production installation tree, the Bell Tower scheduled tasks and the running production Bell Tower processes; any difference fails the run (directory totals are informational because the user's live tray and agents write there). Two effects reach outside the sandbox directories. First, the on-demand tray-start task that `setup` registers per data directory in the user's Task Scheduler; the run deletes it and fails if it remains. Second, by product design a tray started by a hook is a child of the desktop shell and runs with the real profile environment (`USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `TEMP` and any global `CODEX_HOME` or `CLAUDE_CONFIG_DIR`); only its `--data-dir` is the sandbox. The harness requires the recorded start route to be `started-via-shell` (not the scheduled task, which has the same exposure), exits that tray right after its probe and restarts it silently under the sandbox environment, and verifies both steps (the `hook-started-tray-replaced` check requires the hook-started tray to have stopped after `exit` and a tray to be running after `start --silent`; if `exit` did not stop it, its processes are ended directly and the check fails), so no later step runs a tray with the real environment. Neither the guard nor the snapshot can see this exposure (reads change no watched file), so each instance guards it itself, as a mechanism and not a convention. Starting a Codex session without `--no-daemon` marks that instance as using a shared-backend Codex, and every hook compares the recorded tray start attempt (`HookTrayStart.LastAttempt`) before and after: a new `Started` outcome marks the instance as having a hook-started tray. Both marks in one instance throw an isolation refusal and immediately end that instance's tray processes, because a shared-backend Codex could let a real-environment tray reach the user's live Codex backend. The marks are sticky for the instance's whole life and scoped to the instance, so the same pair in two instances (separate data directories) is allowed and `--scenario all` stays workable: a scenario that needs a plain shared-backend `codex` session must use an instance of its own, apart from any instance in which a hook may start a tray (every instance that runs hooks while its tray is stopped, as the hook-started-tray probe and the tray-downtime and update cases do). Until a product seam passes `CODEX_HOME` and `CLAUDE_CONFIG_DIR` through, or a separate sandbox Windows user exists, scenarios must not combine the two in one instance.
- **Interrupted runs.** Cleanup is per instance (one failing step cannot skip the rest or `result.json`). Ctrl+C only signals: it sets a run-wide stop request and ends the in-flight sandbox processes, and the one main thread then refuses new work (`Instance.Run`, a session start, a hook, a wait), unwinds through its `finally` block (one cleanup, the production comparison and the result file) and exits 130 with a failing `run/interrupted` check; nothing else touches the report, so the result is always complete. An interrupted run never writes the committed evidence file. A second Ctrl+C takes the default action and ends the process at once (the preflight sweep below then recovers). A closed console arrives on .NET 10 as `SIGHUP` (`CTRL_CLOSE_EVENT`, which the runtime no longer handles by default): its handler signals the same way, runs the same cleanup under a lock the main thread's cleanup shares, and gives the main thread a few seconds to write `result.json`; Windows ends the process shortly after the handler starts, so this is best effort, and when it does not finish the next run's preflight sweep covers it. A forced kill cannot be covered in process, so every run starts with a preflight sweep, before the "before" snapshot, that removes only what an earlier run of this harness left: `\ZeusApps.BellTower\HookStart-*` tasks whose exported definition runs `tray --data-dir` for a directory under `artifacts\field-acceptance\`, and processes whose image is under `artifacts\field-acceptance\runs\`. Each removal is reported in the isolation section. The user's own task and tray never match either rule. Only one harness run can be active: it holds the named mutex `Local\BellTower.FieldAcceptance` for the whole run, so a second run (and `scripts/field-acceptance.ps1`, before it builds) stops at once with exit code 2 and a clear message (the script returns 1, 2 and 130 with `exit` after printing the message, so they reach `pwsh -File` callers; a setup failure such as a failed download or build still throws and exits 1). Exit codes of a completed run: 0 every check passed; 1 a check or the isolation comparison failed; 3 no check failed but unfinished parity items remain, reported as `PASSED WITH UNFINISHED ITEMS` in the console, `summary.md` and the evidence file (open release work that a release gate must not read as acceptance; `scripts/field-acceptance.ps1` passes the code through with a warning instead of throwing); 130 interrupted. A mutex and not per-run owner records, because concurrent runs cannot work even with precise sweeping: each run's before and after comparison of the Bell Tower scheduled tasks would count the other run's task as a production change. Windows releases the mutex of a killed run, so a forced kill never locks later runs out. Manual cleanup is the same selection: delete a leftover `HookStart-*` task whose definition names a data directory under `artifacts\field-acceptance\` (`schtasks /query /tn <task> /xml`, then `/delete`) and end processes whose image is under `artifacts\field-acceptance\runs\`.
- **Provider model.** `Harness/ProviderModel` (claude, codex) owns the per-provider hook behavior so scenarios avoid provider-name branches: settings path, owned hook command lookup, agent arguments (and whether they use a shared backend), hook shell, event payload and the acceptance predicate. A few provider-name branches remain in `upgrade-without-setup` (seed data, the native-adoption expectations and the stale-state fallback wording); a new scenario takes these from the model rather than copying them. Payloads are the field sets of the captured native payloads in `tests/BellTower.Tests/Fixtures/native` (copied next to the harness) with the session id, working directory and transcript path replaced by sandbox values; no field a native capture lacks is added, and a unit test compares the field names. Claude Code runs hooks through Git Bash. Codex shell discovery follows `shell_detect.rs` at `rust-v0.164.0`: `pwsh.exe` anywhere on `PATH`, then PowerShell 7 at its fixed path, then `powershell.exe` anywhere on `PATH`, then Windows PowerShell at its fixed path, then `cmd.exe`; so PowerShell 7 wins even when Windows PowerShell comes first on `PATH`. One deliberate difference: a PowerShell found on `PATH` counts only when it is one of the two system PowerShells the guard allows, and a skipped hit is reported in the run notes with the edition Codex would have used. Every Codex capture records the shell executable it ran through.
- **Providers.** `claude.exe` and `codex.exe` are copies of the harness executable. A fake session stays running like a provider session and runs each installed hook command as its child (Git Bash for Claude Code; the discovered PowerShell for Codex), so hooks see real process ancestry. `codex exec` answers the setup hook probe by running the SessionStart hook through the same discovered shell. No real Claude or Codex binary, credential or model request is involved. Trays run with `--silent` and a muted configuration with update checks disabled.
- **Output.** `artifacts/field-acceptance/runs/<timestamp>/result.json` (`verdict` and `exitCode` as the console reports them, so a reader never has to combine `passed` with the unfinished count; `passed` means no failures; every check with scenario, provider `claude`, `codex`, `mixed` or `harness`, evidence label `Fixture`, `InstalledHarness` or `Live`, result, an `expectedFailure` flag and detail, plus baseline and candidate provenance and the isolation report) and `summary.md`. `-EvidenceOut <file>` writes the same summary with repository, profile, temp, user and host names replaced by placeholders; the harness refuses to write it if a private value remains. The harness only ever produces `Fixture` and `InstalledHarness` evidence; `Live` is reserved for user-controlled checks recorded elsewhere. `-KeepSandbox` keeps the sandbox files for inspection.
- **`upgrade-without-setup` (tasks 2.1, ledger U1).** Installs the published 0.1.9, runs 0.1.9's own `setup`, seeds identity stores, color pins and palettes through 0.1.9 commands (two sessions per provider, one with a name, change association, working checkout and color pin), upgrades to the candidate through the real update transaction without rerunning setup, then runs `setup --host-bridge --apply` in the sandbox home. After the upgrade and again after the setup rerun it checks, for Claude Code, Codex and a mixed run: hook captures through the installed commands are accepted; `doctor` reports `hookStart.ingressImage` `stale` with its advice (then `current`); the baseline data reads back unchanged; and the post-0.1.9 hook-side features (native adoption of plain `claude` and `codex --no-daemon`, the hook-started tray, the PowerShell-safe Codex hook command) are inactive with the old image and active with the new one. In the stale state the Codex outcome is the known defect: the 0.1.9 Codex hook command does not parse under PowerShell, so the primary Codex capture check (`stale/captures-default-shell`) runs under the default PowerShell shell and expects every capture to fail with the parser error. It is reported as an expected-failure check, separate from harness failures; the run's summary counts both. In plain words, Codex hooks fail after an upgrade until setup is rerun. The cmd captures that let the tray see Codex sessions for the other stale checks are labeled "modeled cmd fallback" (`stale/captures-modeled-cmd-fallback`); they model a Codex whose PowerShell discovery failed and are not a claim that Codex falls back to cmd. The mixed row reports both counts. Hook-side features that need hooks installed by a real Codex or Claude Code remain live checks.
- **`five-conversations` (task 2.2, ledger rows F7, F8, F9, B and G3).** Three instances, each with the candidate installed (`setup --host-bridge --apply`, muted tray running): Claude Code alone, Codex alone, and both together. In each, five conversations per provider launch in one main checkout (a real Git repository in the sandbox, created through the allowed Git Bash) while their work lives in ticket worktrees with branches and OpenSpec change folders (change names are lowercase kebab-case, which the product requires). They differ by modeled transcript history (one successful write or `apply_patch` into their own worktree's change folder), a pinned change, a manual name, a deprecated role argument (ignored: role-free naming) and a Claude custom-title record, and by palette control: named (`blue`), hex, random, and a color followed by reset. The scenario then reads, per conversation, the badge (the installed `statusline` command, the only installed output among the surfaces), the tab title, the chip inputs (identity name and git details) and the spoken phrase (the product's title and phrase builders evaluated in-process with the harness build over the installed state; the checks say so), and verifies that tab, chip and speech each differ across all conversations of the launch directory with none exempt (a spoken-phrase collision is a product finding, not a harness error), after the initial setup, after a resume of the same conversations (`SessionStart` with source `resume`), after read-only `openspec status` and `instructions` for another conversation's change (modeled `PostToolUse` events), and after `git switch -c` in four of the five worktrees (automatic work evidence is invalidated and each conversation keeps its verified ticket worktree as working checkout with the refreshed branch and worktree, task 2.8; pinned change, manual name, Claude custom title, colors and the untouched conversation stay), including that the invalidated work does not return after another resume. Expected names are literal consequences of the shared naming precedence in the release handoff; nothing in the harness computes a name. Not performed, and said so in the run notes: a real terminal tab write, rendering a chip (it exists only while a session waits for attention), audio (the silent sink records nothing), and Codex explicit native names (a Codex thread name lives in a Codex runtime the sandbox does not run, and the shipped policy does not promote it to the explicit-title tier). That item is its own counted outcome, `UNFINISHED` (`native-title-tier`), never a pass and never a restriction; it does not fail the run, but the verdict becomes `PASSED WITH UNFINISHED ITEMS` with exit code 3, and the run summary counts it separately. Transcripts and inspection events are labeled models, not authenticated provider captures.
- **`packaged-hook-benchmark` (task 2.3, ledger row F1).** One instance with the candidate installed and its tray running (so no hook starts a tray; the run fails that check otherwise). The installed `UserPromptSubmit` hook command runs as a child of a fake `claude.exe` through Git Bash and of a fake `codex.exe` through the discovered PowerShell, with the native capture's field set as input: per provider one serial first sample plus 120 samples in concurrent batches of eight, with two controls in rotating legs of the same batches: the contract control `echo 1` and an informational neutral leg (the shell starting a native no-op: `/usr/bin/printf 1` for Git Bash, `[Console]::Out.Write('1')` for PowerShell) (the sampling plan and statistics come from `tools/Shared/HookTiming.cs`, the same source `tools/BellTower.Ingress.Bench` compiles), then a mixed run of 120 hooks with both providers and both control legs in the same batches, each through its own provider's shell. Each hook records in-agent milliseconds (measured by the fake provider process), round-trip milliseconds and durable completion: the moment its capture file first appeared in the inbox, observed while the tray consumes it, matched to its own hook by session and ingress time. Gates: the ingress contract (mean full hook minus mean `echo 1`, below 300 ms, round trip and in-agent; negative estimates stay visible), no raw hook of three seconds or more, every capture durable within 3 s and exact counts (hooks accepted equal capture files equal envelopes found in the tray's applied session journals, inbox drained, no rejection recorded by the product). The raw median, p95, p99 and max are retained and reported as informational raw values (not relabeled as the estimate), and hook-minus-neutral is reported as informational (PowerShell's `echo` is an alias that auto-loads a module, so it is not a neutral baseline). The Codex PowerShell argument vector (`-NoProfile -NonInteractive`) is modeled and unverified for Codex 0.164.0. The raw samples of every hook are in `result.json` under `measurements`. The numbers are installed-harness measurements on one machine and the run notes record that machine's load (processor busy share, logical processors, process count; no names); a failed gate is reported as it is. Hooks go through `AgentSession.Hook`, the only path that observes hook-started trays (ANALYSIS-142); parallel hooks on different sessions are safe, `Instance.WithProcessEnvironment` stays single-threaded by contract.

- **`faults-and-rollback` (task 2.4, ledger rows F2, F4 and upgrade risk U1).** Three instances (Claude Code, Codex, both together), each its own installation that starts as the published 0.1.9 with live fake agents and its tray running (a one-minute attachment grace, the product's minimum), and runs five phases. (1) 0.1.9: a conversation with historical work in its own ticket worktree and a conversation with one resolved operation and one pending wait. (2) The real update transaction upgrades to the fixture-version candidate with the tray running while post-only hooks keep arriving (every one must be accepted and applied exactly once), then `setup --host-bridge --apply` makes the hooks name the candidate's ingress image. (3) Fault injection on the candidate: null-process startups (a fake agent image the product's ancestry walk cannot recognize as the provider; one conversation is repaired by a later hook from the identifiable process, the other must read unavailable after the grace, never working), lost, late and duplicate pre hooks against the running tray (a post-only call; a pre hook and permission request after the post; a duplicated pre and post), tray downtime (the user's Exit, so no hook starts a tray; the captures must wait durably, then the spool is shuffled and three captures are delivered twice before the tray drains it; the final state must be the causal one with the journal gaining exactly the hooks sent), and a branch change that leaves a retained checkout. (4) Rollback to the real 0.1.9 while the hooks still name the candidate's ingress image: the tray exits, the retained 0.1.9 payload is selected by the documented manual selection of `current.json` with the product's own capture-compatibility check (the product has no rollback command), and the first reads are 0.1.9's own `list`, `doctor` and `statusline` before any 0.1.9 tray pass (identity fields, names, colors, pins, the `retained` checkout source and the stored `checkoutWork` field must read back; no candidate type or policy judges 0.1.9 state). The 0.1.9 tray then drains captures written by the candidate's ingress, consumes the faults again, and must keep every pending wait, resurrect no resolved wait and read liveness as repaired or unavailable. The expected one-way effect on a retained checkout (ANALYSIS-186) is recorded as an expected result: 0.1.9 records the launch checkout on its first passes (it has no retained input), keeps the additive `checkoutWork` field, and upgrading again does not restore the retained checkout. (5) The candidate is selected again and the checks repeat. The group ends with stable-state, no-process-termination (every fake agent, including the process-less ones, is still running; the harness ends only trays) and real-environment-exposure checks. Provider differences come from `ProviderModel` (the approval-flow tool events are modeled payloads in the documented shapes, `PermissionRequest` without a tool use id; Codex's 0.1.9 hooks run through the labeled modeled cmd fallback). Spool shuffling and duplication are delivery faults injected into the capture spool while the tray is stopped; the envelopes are untouched. Documented limitation (user decision 2026-11-26, not fixed in 0.1.11): a plain `codex --no-daemon` conversation that 0.1.9 registered keeps its `codex-session-<hash>` attachment; once its hooks run the candidate ingress (after `setup --host-bridge --apply`) the ingress emits the process id and the reducer ignores every non-registration event of that conversation, in the candidate tray and in a rolled-back 0.1.9 alike, until it registers again. Recovery: rerun setup (the matching version's), then resume or restart that conversation. Bell Tower standalone-launched (`--no-daemon` with the marker) and shared-backend Codex and every Claude Code conversation are followed in both directions. The default Bell Tower Codex launch (an owned `app-server` runtime, `BellTower.psm1:97-106`) is followed by the candidate, but a rolled-back 0.1.9 drops its candidate-image hooks (the candidate emits the provisional shared wire id, which 0.1.9 cannot promote): a rollback-only loss, declared an expected failure and documented for 0.1.11 (user decision 2026-11-26, ANALYSIS-240): after a manual rollback to an older version following a 0.1.11 setup, rerun the older version's setup, then resume or restart the open Codex conversations. The automatic rollback of a failed update never leaves the hooks on the candidate image: the update never rewrites hook commands (`Setup/IntegrationRefresh.cs:16-35`), only an explicit setup does. Two null-process outcomes are reported as expected failures too, with different histories. (1) A Bell Tower standalone-launched Codex conversation whose first hook found no agent process: 0.1.9 keeps the managed id on every hook (`v0.1.9:src/BellTower.Ingress/Program.cs:33`, `Hosts/AttachmentCapture.cs:41-44`) and repairs it from the later identified hook; the candidate registers it under the shared id (`NativeAdoption.cs:101,106,130`) and drops the later hooks (ANALYSIS-241): a change in 0.1.11, not pre-existing: a known 0.1.11 regression documented with a follow-up (user decision 2026-11-26, ANALYSIS-265); the workaround is to restart the conversation. Claude Code is repaired. (2) A plain Claude Code launch whose hooks find no agent process gets a fresh random id per hook in 0.1.9 and the candidate alike (ANALYSIS-242): pre-existing. Plain Codex gets the stable shared id. The null-process agents are started through a detached spawner so the product's ancestry walk above them is empty whatever launched the harness (QA-260), and a check reports the ancestry it relied on. The expected-failure checks are declared as such: `upgrade/` and `reupgrade/candidate-hooks-applied-after-setup-refresh/wait-plain`, `rollback/candidate-hooks-applied-by-0.1.9/wait-plain`, `rollback/candidate-hooks-applied-by-0.1.9/wait-owned-runtime` and `.../wait-fresh-owned-runtime`, `candidate/null-process-later-hooks/heal` (Codex and mixed groups), and `candidate/null-process-plain-startup/ghostplain` (Claude Code and mixed groups). Each passes only while the loss is observed by its exact mechanism (the probe event in the tray's journal, not applied, the session and the event carrying exactly the documented attachment ids) and fails if it stops or changes (the documented limitation then needs revisiting). `FIELD_ACCEPTANCE_GROUPS=claude,codex,mixed` (any subset) is a developer filter. The surfaces reader (`ConversationSurfaces`) supports only an installation whose launcher reports the candidate version and fails with a clear message otherwise, and `Instance.WithProcessEnvironment` is enforced by `ProcessEnvironmentSwap`: while an in-process call swaps the process environment, another thread that creates an instance, runs a process or starts a session gets an exception.

Run the unit tests for the harness logic with `dotnet test -c Release --no-build --no-restore --filter FullyQualifiedName~FieldAcceptance`.
